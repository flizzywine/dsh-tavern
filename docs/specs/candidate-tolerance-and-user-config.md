# 候选项容错与用户配置保留需求

## 1. 目的

本文记录两个彼此独立的需求。外部补丁只提供问题线索，不作为实现基础；每个需求单独设计、实现、测试和提交。

实施顺序：

1. 候选项超额输出容错；
2. 更新时保留用户自定义配置。

完成一个需求并验证后，再开始下一个需求。

## 2. 需求一：候选项超额输出容错

### 2.1 问题

自由故事要求模型返回 4 个行动候选和 1 个场景候选，剧本模式要求返回 1 个候选。模型偶尔会返回超过要求的有效候选；当前严格数量校验会把整批结果作废，让用户重新等待一次生成。

超额输出不影响 Tavern 满足界面数量契约，不应作为整批失败处理。

### 2.2 行为契约

- 先执行现有的类型识别、空文本过滤和文本去重。
- 自由故事至少需要 4 个有效 `action` 和 1 个有效 `scene`。
- 数量充足时，分别按模型原始顺序取前 4 个 `action` 和第 1 个 `scene`，最终仍输出严格的 `4 + 1`。
- 剧本模式至少需要 1 个有效候选；存在多个时取原始顺序中的第 1 个。
- 任一必需类型数量不足时继续失败，不用无效内容补位。
- 发生裁剪时记录诊断信息，但不向用户报错，也不自动再次调用模型。

### 2.3 范围边界

- 本需求只改变候选项数量校验与裁剪。
- 不改变提示词、候选排序算法、模型参数、剧本游标或保存结构。
- 不改变后台 Agent participant、Session 同步或失败恢复语义；相关问题需要独立诊断和设计。

### 2.4 验收标准

- `5 action + 1 scene` 成功保存为前 4 个 action 和 1 个 scene。
- action 与 scene 交错输出时，仍按各自原始顺序裁剪并返回 `4 + 1`。
- 重复项和空项先过滤，再计算有效数量。
- `3 action + 2 scene`、`5 action + 0 scene` 等缺项输出仍然失败。
- 剧本模式的多个有效候选只保留第 1 个；没有有效候选时失败。
- 裁剪不会产生第二次模型调用，也不会推进两次剧本游标。

## 3. 需求二：更新时保留用户自定义配置

### 3.1 问题

用户可能在 Tavern Profile 中安装额外插件或添加个人配置。更新 dsh-tavern 时，如果安装器直接用项目模板覆盖整个 Profile，这些用户扩展会丢失。

另一方面，Profile 同时包含 dsh-tavern 必须管理的基础配置。无条件保留旧文件会阻止新版修复、依赖调整和废弃插件清理。

### 3.2 配置所有权

更新流程必须区分两类配置：

- **项目管理配置**：运行 Tavern 所需的基础 bundles、依赖、Cordis 条目、`dshTavern` 元数据和宿主配置。新版项目定义具有权威性，可以新增、修改或删除。
- **用户扩展配置**：用户明确额外安装的插件和与项目管理项不冲突的个人配置。更新后继续保留。

不能仅通过“旧版里存在、新模板里不存在”判断用户所有权，因为该项目可能正在主动删除一个旧的项目管理项。

### 3.3 行为契约

- 全新安装继续获得完整、可直接运行的项目默认 Profile。
- 普通更新应用新版项目管理配置，同时保留可识别的用户扩展。
- 项目明确废弃的 bundle、依赖或配置条目必须能够被删除，不能被并集合并重新带回。
- 项目管理条目的新版字段必须能够升级，不能因为 id 相同而永久保留旧内容。
- 修改 YAML 时进行结构化解析与校验，不使用正则或文本分块推断配置结构。
- 写入前保留可恢复备份，写入使用原子替换；配置解析或 DSH 校验失败时不宣告更新成功。
- Android 的 3088 由 Android 宿主和安装脚本明确传递；CLI 继续默认 3081。用户配置保留机制不负责推断宿主端口。
- 保持 Tavern-only：不修改 DSH 本体。

### 3.4 已确认的实现边界

审计 Profile 的写入者和升级流程后，采用以下所有权边界：

1. `dsh-tavern-plugin` bundle 的 patch 承载项目管理的 Cordis 配置；Profile 根目录的 `cordis.patch.yml` 只承载用户覆盖。
2. 首次升级按 YAML 结构精确移除旧项目模板条目；用户修改过的同 id 条目和其他用户条目继续保留。
3. Profile manifest 记录上一次由项目管理的 bundles 和 dependencies。更新时先移除旧管理清单，再应用当前项目清单，因此项目项可以新增、升级和退役，用户额外项不会被并集合并误删。
4. CLI、Desktop 和 Android 共用配置所有权与迁移规则；端口仍由各宿主明确管理，配置合并层不读取或推断端口。

写入 manifest 和首次迁移后的用户 patch 前创建备份并使用原子替换；依赖安装或 DSH 配置校验失败时恢复原文件。迁移完成后，后续更新不再读写用户 patch。

### 3.5 验收标准

- 全新安装结果与项目模板一致。
- 未做用户定制的旧 Profile 更新后与新版项目管理配置一致。
- 用户额外安装的受支持插件更新后仍存在且可加载。
- 项目修改同 id 配置时，新版必要字段能够生效。
- 项目删除旧 bundle 或依赖时，更新不会把它恢复。
- 格式合法但排版不同的 YAML 不影响合并判断。
- 配置损坏、合并失败或 DSH 校验失败时保留原配置和备份，并返回明确错误。
- CLI 更新后仍使用 3081；Android 更新后仍由正式 Android 流程启动 3088；Desktop 行为不变。

## 4. 实施门禁

每个需求遵循同一流程：

1. 用回归测试复现目标行为或现有缺口；
2. 用户确认该需求的具体实现方案；
3. 只实现当前需求；
4. 运行针对性测试、全量测试及相应运行时验证；
5. 单独提交，再讨论下一项。

## 5. 实施状态

- 需求一已实现：超额候选按类型和原始顺序裁剪，缺项仍失败，并保留诊断信息。
- 需求二已实现：项目配置迁入插件 bundle，用户配置通过一次性安全迁移进入独立覆盖层，后续更新只维护显式项目清单。
- 两项均通过针对性测试、全量测试；配置迁移另通过隔离 DSH Profile 的全新安装、旧版升级、用户覆盖和失败回滚验证。
