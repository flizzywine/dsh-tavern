### 卡片 Agent：用户偏好问卷与用户建模（2026-09-01）

- [ ] 整体流程严格分为两个由用户主动触发的阶段：① 用户主动建立画像；② 用户在具体游玩中手动开启画像注入。默认不建立画像，也不自动向任何游玩对话注入。
- [ ] 第一步“主动建立画像”：卡片 Agent 通过调查问卷了解用户，分析其创作与游玩偏好，形成可持续修正、跨卡复用的个人偏好档案；不要求用户先把偏好写成 Skill。
- [ ] 问卷可通过对话分批完成，结合选项、具体示例比较和开放回答，了解题材、人物类型、关系互动、剧情节奏、文风、玩家参与方式及不喜欢的内容；用户可跳过问题，Agent 根据回答追问，不一次堆出大量问题。
- [ ] 分开记录用户原始回答、Agent 的偏好分析和用户已确认的结论；分析保留回答依据、适用场景与待确认项，不把一次选择当作永久偏好，不从虚构角色设定推断用户真实身份或心理诊断。
- [ ] 向用户展示偏好分析供其确认、纠正和补充；用户同意记录后持久化。用户可查看、修改、删除档案中的记录；后续问卷或写卡反馈可用于修正档案，不静默覆盖已确认偏好。
- [ ] 写新卡或修改其他卡时，按需读取与当前任务相关的偏好，并说明如何用于写卡；当前明确要求优先，支持本次不使用档案，单张卡的临时要求不自动变成长期偏好。
- [ ] Skill 可作为问卷、总结和更新画像的方法，或将已确认偏好转化为写卡规则的复用载体；用户画像是用户可管理的数据，不预先等同于 Skill，也不自动写入人物卡。
- [ ] 第二步“手动开启画像注入”：画像建立后仍保持关闭；用户在具体游玩对话中明确开启，才把已确认且长度受控的画像摘要注入前台游玩上下文。允许随时关闭，当前指令和本场临时要求始终优先，不把游玩内容静默写回画像。
- [ ] 画像注入状态属于对话配置并可追溯；原生游玩和兼容游玩分别投影到各自请求链路，不改写已经存在的 Frame 或历史消息，不向 MVU、变量结算等后台确定性任务注入。
- [ ] 验收第一步：完成一轮问卷后，用户能核对回答与偏好分析并确认保存；关闭对话并重启后，新卡片对话仍能复用档案；纠正和删除在后续读取中生效，未确认的分析不作为确定偏好使用。
- [ ] 验收第二步：未手动开启时最终游玩请求不含画像；开启后只包含已确认摘要并记录所用版本；关闭后下一轮停止注入；原生与兼容模式行为一致，后台结算请求始终不含画像。
