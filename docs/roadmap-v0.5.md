# dsh-tavern v0.5 路线图

## 版本主题

v0.5 的主题是：**让 Agent 负责判断，让程序负责状态、注入与呈现。**

本版本继续围绕真实工作流微调，不扩建通用 Agent 平台。世界书、状态 UI、文风 Skill 和破甲提示词都应形成小而稳定的 interface；README 与选择人物卡界面在功能稳定后统一收尾。

## v0.4 基线

v0.5 在以下已验证能力上继续开发：

- 卡片模式以 DSH 极简会话为底座，并叠加 Tavern 专属工具；
- 修改人物卡、从资料新建、从预设提取破甲和空白开始共用同一个卡片 Agent；
- 人物卡库与资料库独立于“酒馆状态”侧栏；
- 人物卡和资料支持导入、查看、重命名、引用与原版恢复；
- 世界书支持常驻与关键词触发，剧本游标按成功正文单调推进；
- 新开游玩在创建 Session 前选择开场白；存在多条有效开场白时可以预览并左右切换，确认后才创建对话，剧情开始后不再切换。

## 版本范围

### 1. 世界书动态召回与注入

#### 目标

大型世界书不再主要依赖固定数量常驻条目或简单关键词匹配。后台 Agent 根据本轮玩家输入、最近剧情和紧凑目录渐进读取相关条目，直接加工出当前正文需要知道的上下文，再由 Context Planner 注入前台主 Agent。

#### 设计

新增深模块 `World Book Recall`：

```text
recall({ card, recentStory, userText, budget })
  -> { context, sourceEntryIds, audit }
```

执行流程：

1. 根据人物卡内容生成紧凑的世界书分类与条目目录，并按卡片内容哈希缓存。
2. 正文生成前，后台 Agent 执行独立的 `worldbook-recall` 任务，按需读取相关条目。
3. 后台 Agent 筛选、组织和压缩条目内容，直接形成当前正文需要知道的上下文，同时返回来源条目编号。
4. Context Planner 校验结果和预算后，把加工后的上下文注入前台主 Agent。
5. 召回失败时使用确定性的安全回退，不阻止正文生成。

#### 第一版边界

- 不引入向量数据库。
- 不修改世界书原始文件；后台 Agent 只加工本轮注入内容。
- 不把完整世界书发送给前台或后台 Agent。
- 保留 SillyTavern 字段兼容；是否允许 Agent 忽略 `constant` 条目，实施前单独确定迁移规则。
- 先验证动态召回，再决定是否彻底替换现有关键词召回。

#### 验收标准

- 100 条以上世界书只暴露紧凑目录，不整本注入。
- 与本轮剧情相关的远端条目能够被召回，并加工为正文真正需要的上下文。
- 加工结果忠于原始设定，不因压缩产生新的世界事实。
- 无关条目不会因同名、重复 `comment` 或旧目录顺序进入注入内容。
- 召回失败、超时或返回无效内容时，正文仍可生成。
- 注入结果可在审计信息中看到来源条目编号、加工内容、原因和字符预算。

### 2. 结构化状态与前端美化

#### 决策

不采用“前台 Agent 在正文末尾输出状态块，再由正则解析”作为权威状态方案，但第一阶段允许用正则兼容酒馆人物卡已有的正文格式和前端表现。

正则只负责展示：识别成功就把命中片段从可见正文移到独立展示区，失败就完整显示原文；原始回复仍作为内部源文本保存，不得被展示结果覆盖。权威状态继续由独立结算维护。后续再把卡片专属的前端生成拆到人物卡导入或准备阶段，并与正则共用统一展示接口。完整设计见[回复展示与状态栏兼容](design/status-bar.md)。

#### 设计

扩展现有后台状态结算任务，让它提交结构化 `Status Projection`：

```text
settle({ timelineRevision, latestTurn, previousStatus })
  -> {
       location,
       time,
       characters: [{ name, position, posture, appearance }],
       summary
     }
```

- 状态结算继续与候选任务复用同一个后台 Agent，但使用独立 operation 权限。
- Story Timeline 保存状态投影，并让它随正文替代和回退一起恢复。
- 前端优先渲染已校验的权威状态；正文解析只作为酒馆兼容展示，不反向修改状态，也不直接执行人物卡中的 HTML 或脚本。
- 结算失败时保留上一版状态并显示“尚未同步”，不把原始 JSON 或错误写进正文。

#### 第一版 UI

右侧“酒馆状态”优先展示：

1. 当前地点与时间；
2. 在场人物；
3. 每个人物的位置、姿势和必要外观；
4. 当前状态是否已经与最新正文同步。

第一版先支持常见标签、可安全适配的正则，以及人物卡已经携带的 HTML 界面。HTML 从正文和主 Agent 历史中分离，只在隔离 iframe 中运行；暂不建设任意变量面板、MVU 或完整 Tavern Helper 运行环境。确有重复需求后，再设计可声明的状态 schema 和卡片专属展示 Adapter。

#### 后续优化：差量式界面更新

当前兼容阶段允许模型完整输出 HTML，再由回复展示模块把 HTML 从正文中分离并更新右侧界面。后续改为让模型只提交结构化界面编辑，由展示 Adapter 在已有 HTML 上应用差量，而不是每轮重新生成整份页面。

这一优化用于减少 HTML 占用的输出 token、降低标签缺失和格式损坏概率，并减轻正文模型同时生成故事与完整前端代码的压力。差量编辑协议、允许修改的节点范围和失败回退方式需要在真实人物卡兼容样本稳定后单独设计。

#### 验收标准

- 正文不包含任何为前端服务的状态格式要求。
- 正常生成、重新生成和回退后，状态与当前剧情 revision 一致。
- 状态结算失败不会破坏正文或清空上一版有效状态。
- 桌面宽度和窄屏下均可阅读；进入游玩模式时自动展开“酒馆状态”，卡片模式不自动打开。
- 浏览器中完成真实故事回合验证，控制台无错误。

### 3. 卡片模式文风 Skill

#### 目标

允许用户导入、制作和选择可复用文风，让卡片 Agent 用它分析、草拟和修改人物卡；文风 Skill 本身不是人物卡字段，也不直接改变游玩回复。

#### 第一版能力

- 内置六种差异明显的文风：克制写实、古典白描、细腻心理、悬疑压迫、轻小说对白、电影化场景。
- 从单个 Markdown / `SKILL.md` 文件导入自定义文风。
- 通过卡片 Agent 根据用户描述或样文制作文风，用户确认后保存。
- 当前卡片对话最多选择一个文风，也可以选择“无文风”。
- 选择、切换和导入属于界面操作，不为简单数据绑定额外启动 Agent。

#### 模块

`Style Skill Catalog` 负责目录、解析、校验、来源合并和保存：

```text
list()        -> 紧凑目录
load(name)    -> 已校验正文
import(file)  -> 自定义文风
save(draft)   -> Agent 确认后的文风
remove(name)  -> 删除自定义文风
```

只有选中的 Skill 正文进入当前卡片对话上下文；未选择时只提供紧凑目录。Skill 不得扩大工具权限或覆盖当前用户要求。

#### 第一版边界

- 不接入用户的全局 DSH Skill 目录。
- 不支持附件、脚本、命令和任意 HTML。
- 不建设复杂 Skill 编辑器、版本历史或组合多个文风。
- 文风必须通过现有人物卡确认流程，才能转化为长期卡片规则。

#### 验收标准

- 导入、制作、选择、切换、清除和删除自定义文风均可完成。
- 同名文件不会静默覆盖，内置文风不可被自定义文件遮蔽。
- 只注入当前选中的一份完整正文，切换后旧文风不再出现。
- 重新打开会话后能够恢复选择；Skill 缺失时安全回到“无文风”。

详细设计见[卡片工作台文风 Skill 设计](design/writing-style-skills.md)。

### 4. 破甲提示词与卡片工作台整合

#### 目标

破甲提示词不建设孤立的制作流程。酒馆预设原样进入预设库，由统一卡片 Agent 阅读、讨论和提取；结果保存为 `data/boundary-prompts/*.md`。破甲库只负责查看文件、为当前会话选择一个文件、开启或关闭，并显示注入状态。

#### 第一版能力

- 卡片模式增加“从预设提取破甲”起始任务，但继续使用同一个 `card` Agent；
- 酒馆预设原样进入预设库，不在导入阶段运行正则筛选或自动写入；
- 卡片 Agent 通过专用工具创建和修改破甲 Markdown 文件；
- 当前会话开启后，同一个文件注入正文、候选项、状态结算和其他模型任务；
- 不建立方案数据库、推荐模型属性或模型自动匹配；可以内置一到两个推荐配置，推荐模型只通过文件名表达，并且默认关闭。

详细设计见[破甲提示词设计](design/boundary-prompts.md)。

破甲功能先完成接口、文件、侧栏和全局注入，不在当前阶段展开特定模型与成人卡片的长期适配。Gemini 3.7 Flash、《东淫航空》和 SillyTavern 成功基线的三段对照方案已经记录，待高 ROI 兼容工作稳定后再执行，见[破限模块测试计划](design/boundary-module-testing.md)。

### 5. 选择人物卡界面精简

#### 游玩模式

- 一个标题、一个搜索框、一张紧凑人物卡列表。
- 点击人物卡直接开始游玩。
- 只显示人物名、文件名和“已绑定剧本”小标签。
- 导入、编辑、删除等管理操作统一留在人物卡库，不塞进新开游玩界面。

#### 卡片模式

保留四个清晰入口：

1. 修改人物卡；
2. 从资料新建人物卡；
3. 从预设提取破甲；
4. 空白开始。

四个入口仍使用同一个卡片 Agent、工具和系统提示词，只追加不同的起始任务。修改人物卡时再显示搜索与卡片列表；人物卡抽取和破甲抽取时才显示对应资料选择，避免同一面板同时展示全部状态。

同时拆分右侧资源管理：

- “人物卡库”只管理人物卡，并提供“加入当前对话”；
- 右侧分为人物卡库、预设库、破甲库和资料库；资料库只管理素材、剧本、设定和其他普通参考文件；
- 人物卡不再在两个栏目中重复出现。

#### 验收标准

- 新用户无需理解“Workspace”“资源身份”或 Agent 模式即可开始。
- 从进入选择界面到开始游玩最多两次点击。
- 四个卡片任务入口语义清楚，且不产生新的会话模式。
- 人物卡库与资料库内容不重复，但都能把各自文件加入当前卡片对话。
- 不改变人物卡详情和剧本手动绑定的职责。

### 6. README 与安装说明重写

README 在上述功能和 UI 定稿后更新，避免截图与流程再次过期。

#### README 结构

2. 五项核心体验；
3. 三分钟开始使用；

详细的手动安装、国内网络失败处理和开发者说明可以移入独立安装文档；README 保留最短成功路径。

#### 验收标准

- 所有功能描述与 v0.5 实际界面一致。
- 所有截图来自真实 v0.5 工作流，不保留旧版 UI。
- Windows、macOS / Linux 的全新安装各验证一次。
- 启动、停止、重启、更新、日志位置和数据目录能够快速找到。
- 文档链接和安装命令自动检查通过。

## 后续路线：酒馆生态兼容桥

v0.5 稳定后，下一阶段的核心目标是：**全面兼容 SillyTavern 的成熟生态，但不复制其动态拼接超大上下文的底层架构。**

dsh-tavern 尽可能保留原有资源格式、创作者成果和可观察效果，再通过兼容层把它们转换为 DSH 的追加式 Agent 行为。主 Agent 与后台子 Agent 继续维护各自稳定的上下文前缀；酒馆的插入位置、插入深度和脚本接口只作为输入语义解释，不反向主导核心架构。

### 兼容路径

1. 人物卡、世界书和预设等声明式资源：直接解析原格式，转换为 Agent 上下文、规则与后台任务。
2. EJS 模板和兼容脚本：在隔离的 QuickJS 环境中执行，通过受控接口读取和提交数据。
3. 显示正则：进入独立输出管线，单条规则失败不影响正文和会话。
4. Tavern Helper、MVU 和轻量 HTML：分别通过受限脚本接口与 iframe 桥接，不直接获得 DSH 宿主权限。

### 实施原则

- 兼容生态资源及最终效果，不复刻传统提示词拼接器。
- 每项能力标明“原生支持、转换支持、沙箱支持或暂不支持”，不笼统宣称完全兼容。
- 优先覆盖真实人物卡中高频、高价值的能力，再逐步扩展兼容 API。
- 单条模板、正则或脚本失败不得中断正文生成和会话。
- 使用真实酒馆资源建立兼容样本与回归测试，区分格式可读取、行为可运行和效果已验证。

## 实施顺序

### 阶段 0：冻结 interface 与基线

- 用现有真实人物卡分别建立：大型世界书、自由游玩、剧本游玩、卡片编辑四条回归流程。
- 记录当前延迟、上下文大小、召回条目和状态结算结果。
- 验证重新生成正文会正确遮蔽并替代原正文，同时恢复候选、状态和剧本进度。
- 先确定 `World Book Recall` 与 `Status Projection` 的 interface，再改宿主适配器和 UI。

### 阶段 1：世界书召回

- 实现目录缓存、渐进读取、后台加工、上下文注入、失败回退和审计。
- 先通过行为测试，再用大型真实人物卡验证召回质量。

### 阶段 2：结构化状态与 UI

- 扩展后台结算和 Story Timeline。
- 先验证生成、替代、回退的一致性，再实现右侧状态 UI。

### 阶段 3：文风 Skill

- 先完成 Catalog 和文件安全规则。
- 再接入卡片上下文、保存工具和选择界面。

### 阶段 4：界面精简

- 先完成破甲目录、卡片 Agent 写入工具和侧栏调控的完整流程。
- 精简人物卡选择流程。
- 统一卡片模式四个入口与新增文风、破甲栏目的视觉层级。

### 阶段 5：发布收尾

- 跑完整回归流程并修复阻塞。
- 重写 README、安装说明和截图。
- 验证全新安装、更新安装、服务重启和数据保留。

## v0.5 明确不做

- 向量数据库或通用长期记忆系统；
- 任意人物卡 HTML、脚本或正则驱动 UI；
- MVU、通用变量管理 Agent 或人物卡编译器；
- 多文风组合、Skill 附件和版本历史；
- 全站前端重写；
- DSH Desktop 打包或新的发行体系。

## v0.5 之后的 Backlog

以下方向保留，但不进入 v0.5：

- 增加后台变量管理 Agent，用于更新声明式 UI 与变量；不采用正则或 MVU。
- 增加人物卡编译能力，把变量管理和 UI 管理从人物卡中抽离。
- 评估 DSH Visualize 对结构化状态 UI 的复用价值。
- 在真实设备和当前版本兼容后，评估 DSHA 与 DSH Desktop 的正式支持。

## 发布门槛

每个阶段都必须满足：

1. 行为测试覆盖成功、失败、重试和旧数据迁移；
2. 完整测试通过；
3. Tavern 重启后真实浏览器验证通过；
4. 不破坏现有自由故事、剧本游标、人物卡原版和历史会话；
5. 新提示词和新上下文都有明确的功能理由与字符预算。

只有以上阶段全部完成并经过真实工作流验证，才发布 v0.5。
