# dsh-tavern 产品设计原则

本文统一记录 dsh-tavern 的使命、不可放弃的体验和产品取舍。功能表现与安装方式以项目 [README](../README.md) 为准，领域词义与实现分层见[架构](architecture.md)。

## 产品使命

dsh-tavern 是一个基于 DeepSeek Harness（DSH）的类 SillyTavern 文字游戏 Agent。最终目标不是复刻现有酒馆，而是成为一个好玩、有趣、精彩，并且能够长期保持故事连续性的文字游戏产品。

DSH 已经提供会话、模型、工具、重试和上下文管理等 Agent 基础设施。dsh-tavern 只建设文字游戏领域能力，不在项目内复制通用 Agent 平台。

## 不可放弃的核心体验

1. **候选项生成**：玩家大多数时候可以点选或微调下一步行动，同时始终保留自由输入。
2. **剧本模式**：用外部剧本支撑长线结构、场景转换和主线推进。
3. **对话式人物卡准备**：通过同一个卡片 Agent 新建、阅读、讨论和修改人物卡，并且只在用户确认后写入。

## 产品承诺

- 在恰当的地方注入尽可能少、但足够完成任务的上下文。
- Tavern 持有权威剧情进度；模型会话只是内容生产者，不是最终状态。
- 剧本提供长期方向，玩家决定人物如何经历它；剧本不是不可违背的选项菜单。
- 技术复杂性由系统承担。对用户优先展示能做什么、解决什么问题和真实游玩体验。
- 组合优先于自建：通用能力尽可能复用优秀的 DSH 插件和运行环境，Tavern 专注文字游戏领域功能。
- 提示词是用户可维护的产品内容；未经明确要求，不用默认内容覆盖用户修改。

## 组合优先：尽可能复用 DSH 生态

DSH 的价值不只是自由，而是组合。dsh-tavern 集中注意于文字游戏的产品功能；遇到侧栏、结构化 UI、跨平台运行、桌面封装、数据库或记忆等通用需求时，先寻找和评估 DSH 生态中的成熟能力，再决定是否自行建设。

职责必须保持清楚：

- **Tavern 持有领域真相**：人物卡、世界书、剧情时间线、剧本进度、上下文策略和文字游戏交互。
- **生态插件提供可替换能力**：界面容器、可视化、平台运行环境、存储和其他通用基础设施。

当前和未来重点关注：

- **Better Sidebar**：已经作为右侧工作台底座使用，Tavern 只注册酒馆状态、人物卡库和资源库。
- **DSH Visualize**：可评估用于把已校验的结构化模型结果渲染为原生前端 UI。模型输出不能直接成为可执行代码，也不能重新把小说正文与 UI 格式绑定在一起。
- **DSHA**：可评估为 Android 运行环境。能够启动不等于达到原生可用质量；必须真实验证窄屏、触控、输入法、返回导航、文件选择和休眠恢复。
- **DSH Desktop**：可评估为免命令行的桌面入口，降低普通用户安装和启动门槛。优先适配其 Profile、运行时和发行能力，不维护 Tavern 专属桌面分叉。

引入生态能力前必须满足：

1. 解决已经出现的真实产品问题，而不是为了使用插件而使用插件；
2. 不夺走 Tavern 的权威领域状态，也不要求 Tavern 复制插件内部实现；
3. 通过清晰 adapter 接入，未来可以升级或替换；
4. 检查当前版本、维护状态、依赖和安全权限；
5. 经过完整真实工作流验证后，才能写入官方支持范围。

## 用 Agent 解决提示词工程问题

传统酒馆倾向于把正文、候选项、状态总结、人物约束和格式要求同时交给一次模型生成。对话变长后，容易出现失忆、人物姿势矛盾和格式失控；继续叠加提示词又会稀释模型注意力。

dsh-tavern 把不同目标放到明确的流程中：正文专心写故事，候选和状态结算由后台任务完成，世界书与剧本按需读取，权威进度由程序保存。DSH 提供会话、工具、重试和上下文基础设施，Tavern 只处理文字游戏领域问题。

## 上下文要少而准确

第一性原则是：**在恰当的地方，注入恰当的上下文和提示词。**

每次扩大上下文前都应回答：

1. 不注入是否会造成明确功能缺失？
2. 能否缩短、延后或改为按需读取？
3. 能否由独立流程完成，而不是继续增加正文负担？

只有确实支撑当前任务的内容才进入模型上下文。

## 候选项是核心交互

多数时候，玩家希望点选或稍微修改下一步行动；只有偶尔才完全自由输入。因此候选项不是正文后的装饰，它的质量直接决定游玩节奏。

正文与候选分开生成，可以让正文不承担选项格式，让候选稳定显示在独立面板。选中候选只会填入输入框，玩家仍可修改或忽略它。自由故事提供四个人物行动和一个场景变化；剧本模式只推荐一个更贴近主线的行动。

## 子 Agent 只用于隔离冲突

子 Agent 的价值是隔离互相干扰的目标，而不是为了拆分而拆分。只有共享同一思考过程会造成上下文污染、目标冲突或质量下降时，隔离才值得额外成本。

候选任务会研究尚未发生的后续走向；状态结算追求短而稳定的结构。两者不应挤占正文写作的注意力，但又需要共享同一份剧情理解，因此由同一个持续后台 Agent 以不同任务承担。

## 剧本提供方向，不替玩家做决定

自由故事负责创造故事，剧本模式负责演绎故事。剧本确定长期方向、关键事件和因果关系；玩家决定人物的行动、对白、关系、情绪和到达关键节点的路径。

剧本还提供局部叙事参考。当前片段中的节奏、动作组织、对白密度和场景细节会自然影响生成，比维护禁用词表或事后检查更能减少模板化的“AI 味”。

## 不做无差别的生成后精修

自动追加一轮全文润色会接近翻倍消耗时间和 Token，却没有获得新信息。它往往只替换措辞，也可能抹平人物口吻、削弱节奏或改坏剧本细节。

因此正文第一轮就按成稿标准生成。结果不满意时，用户可以带着具体意见只重写当前正文；明确目标比无差别润色更可控。

## 不提供 SillyTavern 式全局预设

传统预设常把三类内容混在一起：

1. 流程控制，例如候选、状态结算、剧本召回和格式约束；
2. 内容偏好，例如叙事视角、人物口吻和行为边界；
3. 质量控制，例如减少重复和保持格式。

dsh-tavern 把流程控制交给 Agent 工作流，把内容偏好放回人物卡，把格式和连续性问题交给结构化状态与独立任务。换一张人物卡，内容偏好自然随卡切换；改变流程，则修改 Tavern 的领域模块和提示词，不需要维护全局预设集合。
