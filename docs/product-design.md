# dsh-tavern 产品设计原则

本文统一记录 dsh-tavern 的使命、不可放弃的体验和产品取舍。功能表现与安装方式以项目 [README](../README.md) 为准，领域词义与实现分层见[架构](architecture.md)。

## 产品使命

dsh-tavern 是一个基于 DeepSeek Harness（DSH）的类 SillyTavern 文字游戏 Agent。最终目标不是复刻现有酒馆，而是成为一个好玩、有趣、精彩，并且能够长期保持故事连续性的文字游戏产品。

DSH 已经提供会话、模型、工具、重试和上下文管理等 Agent 基础设施。dsh-tavern 只建设文字游戏领域能力，不在项目内复制通用 Agent 平台。

## DSH 原生，酒馆生态兼容

> **兼容酒馆的生态语义，不继承酒馆的运行时架构。**

- DSH 是唯一的 Agent 运行平台。会话、追加式历史、模型调用、工具、重试和上下文生命周期均以 DSH 为基础，不为兼容酒馆另建一套生成循环。
- dsh-tavern 在 DSH 之上持有人物卡、世界书、剧情时间线和剧本进度等文字游戏领域状态；不再并行维护一份 SillyTavern JSONL、聊天历史或运行时作为另一套权威来源。
- SillyTavern 是需要兼容的外部生态协议。人物卡、预设、世界书、正则和脚本进入系统后，应翻译为 DSH 预设、Agent 上下文、后台任务、输入输出生命周期或受限动作适配器。
- 无法直接翻译的动态能力，应通过隔离、可诊断、可替换的兼容层逐步接入；单项暂不支持，也不应迫使主体架构退回酒馆式运行时。
- 兼容以用户可观察效果为标准，不要求复刻酒馆内部实现。每增加一种酒馆能力，都应沉淀为 DSH 原生的通用能力，而不是扩大第二套系统。

### 兼容性研究参考

[LingyeSoul/dsh-tavern](https://github.com/LingyeSoul/dsh-tavern) 对酒馆预设、世界书、宏、正则和 STscript 的格式与运行阶段进行了较完整的拆分，对兼容性研究具有重要参考价值。项目将其作为酒馆可观察语义、生命周期位置和测试样本的参考实现，用于理解一种资源在酒馆中何时读取、如何转换、作用于哪层状态，以及失败时应如何隔离。

借鉴范围包括格式解析、中间表示、纯语义执行器、生命周期划分和差异测试；不直接采用其酒馆生成循环与 DSH AgentLoop 并存的双运行时结构，也不把它作为正式运行依赖。参考结果最终仍需翻译为 DSH 原生能力，并通过真实酒馆资源和可观察效果独立验证。

[Liyuan](https://github.com/weidu12123/Liyuan) v1.5 则是 Agent 原生兼容路线的重要参考，尤其验证了酒馆预设可以保留原文，并按历史前、Agent 原生历史、历史后三段接入，而动态世界书继续由独立召回流程负责。预设方面主要参考其文档层、结构化装配、宏求值和兼容诊断，见[酒馆预设与 DSH 预设](design/native-preset.md#参考实践liyuan-v15)；上下文投影、长局记忆、分支状态、多 Agent 和工具层方面的借鉴范围，见[梨园架构研究](research/liyuan-architecture-reference.md)。

## 不可放弃的核心体验

1. **候选项生成**：玩家大多数时候可以点选或微调下一步行动，同时始终保留自由输入。
2. **剧本模式**：用外部剧本支撑长线结构、场景转换和主线推进。
3. **对话式人物卡准备**：通过同一个卡片 Agent 新建、阅读、讨论和修改人物卡，并且只在用户确认后写入。

## 产品承诺

- 在恰当的地方注入尽可能少、但足够完成任务的上下文。
- Tavern 持有权威剧情进度；模型会话只是内容生产者，不是最终状态。
- 剧本提供长期方向，玩家决定人物如何经历它；剧本不是不可违背的选项菜单。
- 技术复杂性由系统承担。对用户优先展示能做什么、解决什么问题和真实游玩体验。
- 组合优先于自建：通用能力尽可能复用优秀的 DSH 插件和运行环境，Tavern 专注文字游戏领域功能。
- 兼容 SillyTavern 生态：现有资源应当无缝导入；处理方式可以和酒馆不同，但用户体验应当无差别、无感知。
- 提示词是用户可维护的产品内容；未经明确要求，不用默认内容覆盖用户修改。

## 组合优先：尽可能复用 DSH 生态

DSH 的价值不只是自由，而是组合。dsh-tavern 集中注意于文字游戏的产品功能；遇到侧栏、结构化 UI、跨平台运行、桌面封装、数据库或记忆等通用需求时，先寻找和评估 DSH 生态中的成熟能力，再决定是否自行建设。

职责必须保持清楚：

- **Tavern 持有领域真相**：人物卡、世界书、剧情时间线、剧本进度、上下文策略和文字游戏交互。
- **生态插件提供可替换能力**：界面容器、可视化、平台运行环境、存储和其他通用基础设施。

当前和未来重点关注：

- **Better Sidebar**：已经作为右侧工作台底座使用，Tavern 只注册酒馆状态、人物卡库、预设管理器、世界书库和剧本库。
- **DSH Visualize**：可评估用于把已校验的结构化模型结果渲染为原生前端 UI。模型输出不能直接成为可执行代码，也不能重新把小说正文与 UI 格式绑定在一起。
- **DSHA**：可评估为 Android 运行环境。能够启动不等于达到原生可用质量；必须真实验证窄屏、触控、输入法、返回导航、文件选择和休眠恢复。
- **DSH Desktop**：作为免命令行的桌面入口，降低普通用户安装和启动门槛。命令行版与 Desktop 版共用同一个 Tavern Profile，只在宿主启动和安装方式上使用不同 Adapter，不维护 Tavern 专属桌面分叉。

引入生态能力前必须满足：

1. 解决已经出现的真实产品问题，而不是为了使用插件而使用插件；
2. 不夺走 Tavern 的权威领域状态，也不要求 Tavern 复制插件内部实现；
3. 通过清晰 adapter 接入，未来可以升级或替换；
4. 检查当前版本、维护状态、依赖和安全权限；
5. 经过完整真实工作流验证后，才能写入官方支持范围。

## 用 Agent 解决提示词工程问题

传统酒馆倾向于把正文、候选项、状态总结、人物约束和格式要求同时交给一次模型生成。对话变长后，容易出现失忆、人物姿势矛盾和格式失控；继续叠加提示词又会稀释模型注意力。

dsh-tavern 把不同目标放到明确的流程中：正文专心写故事，候选和状态结算由后台任务完成，世界书与剧本按需读取，权威进度由程序保存。DSH 提供会话、工具、重试和上下文基础设施，Tavern 只处理文字游戏领域问题。

### 传统酒馆与 dsh-tavern 架构对比

| 维度 | 传统酒馆架构 | dsh-tavern 架构 |
| --- | --- | --- |
| 上下文组织 | 每轮根据人物卡、世界书、变量、预设和历史动态拼接一个超大上下文 | 主 Agent 与后台子 Agent 持续存在，各自维护追加式历史 |
| 前缀缓存 | 动态插入和顺序变化容易破坏稳定前缀，重复计算大量既有内容 | 主要通过末尾追加新信息维持稳定前缀，提高缓存利用率 |
| 任务执行 | 一个模型在一次生成中同时承担正文、召回、状态和格式等任务 | 主 Agent 专注正文；程序匹配世界书，后台子 Agent 承担候选和状态任务 |
| 注意力 | 多种目标和大量上下文互相竞争 | 每次只处理目标明确、上下文最小的任务 |
| 世界书与状态 | 依赖插入位置、深度、变量和提示词共同驱动 | 世界书由确定性规则投影，状态由后台任务结算，再把必要结果增量回写主 Agent |
| 生态资源 | 资源格式与传统提示词拼接器紧密结合 | 通过翻译桥转换为 DSH 原生产物，必要的动态能力进入隔离兼容层 |
| 局部失败 | 模板、格式或脚本问题可能污染整轮提示词与输出 | 模板、正则、脚本和后台任务分别隔离，单项失败不应中断会话 |

新架构形成两项核心优势：

1. **成本优势**：追加式历史提高缓存前缀稳定性，减少重复计算，从而降低费用与等待时间。
2. **质量优势**：把一个混杂的大任务拆成多个目标明确的小任务，使模型注意力集中，并允许每项任务独立验证和失败回退。

当前实现使用一个持续存在的后台子 Agent 承担多种后台任务；架构允许在出现明确的职责隔离需求时扩展为多个，而不是为每项任务固定创建一个 Agent。

## 上下文要少而准确

第一性原则是：**在恰当的地方，注入恰当的上下文和提示词。**

每次扩大上下文前都应回答：

1. 不注入是否会造成明确功能缺失？
2. 能否缩短、延后或改为按需读取？
3. 能否由独立流程完成，而不是继续增加正文负担？

只有确实支撑当前任务的内容才进入模型上下文。

## 候选项是核心交互

多数时候，玩家希望点选或稍微修改下一步行动；只有偶尔才完全自由输入。因此候选项不是正文后的装饰，它的质量直接决定游玩节奏。

正文与候选分开生成，可以让正文不承担选项格式，让候选稳定显示在独立面板。选中候选只会填入输入框，玩家仍可修改或忽略它。自由故事提供四个人物行动和一个场景变化；剧本模式只推荐一个更贴近主线的行动。

## 子 Agent 只用于隔离冲突

子 Agent 的价值是隔离互相干扰的目标，而不是为了拆分而拆分。只有共享同一思考过程会造成上下文污染、目标冲突或质量下降时，隔离才值得额外成本。

候选任务会研究尚未发生的后续走向；状态结算追求短而稳定的结构。两者不应挤占正文写作的注意力，但又需要共享同一份剧情理解，因此由同一个持续后台 Agent 以不同任务承担。

## 剧本提供方向，不替玩家做决定

自由故事负责创造故事，剧本模式负责演绎故事。剧本确定长期方向、关键事件和因果关系；玩家决定人物的行动、对白、关系、情绪和到达关键节点的路径。

剧本还提供局部叙事参考。当前片段中的节奏、动作组织、对白密度和场景细节会自然影响生成，比维护禁用词表或事后检查更能减少模板化的“AI 味”。

## 不做无差别的生成后精修

自动追加一轮全文润色会接近翻倍消耗时间和 Token，却没有获得新信息。它往往只替换措辞，也可能抹平人物口吻、削弱节奏或改坏剧本细节。

因此正文第一轮就按成稿标准生成。结果不满意时，用户可以带着具体意见只重写当前正文；明确目标比无差别润色更可控。

## 兼容 SillyTavern 生态，实现无痛过渡

SillyTavern 的内部架构不是本项目要复制的技术路线，但它拥有高度繁荣的人物卡、世界书、预设、正则、脚本和前端内容生态。一个文字游戏项目如果无法承接这些现有资源，就很难被广泛使用。因此，dsh-tavern 应当尽可能兼容 SillyTavern 生态，再利用 DSH 和自身工作流改善实际运行方式。

兼容的核心原则是：**外部协议兼容，内部架构重写。** SillyTavern 的资源格式是需要承接的生态协议，不是必须照搬的执行引擎。

实现兼容功能时，可以研究并借鉴 [`dsh-agent-rp`](https://github.com/hewzhew/dsh-agent-rp) 等成熟项目的数据边界、兼容策略和失败处理，但不照搬其完整架构、功能范围或用户界面。参考实现用于减少重复研究，不代替对 dsh-tavern 产品目标和现有架构的独立判断。

人物卡等生态资源采用 **raw 无损保留、内部按需投影** 的原则：完整原始数据是兼容与再导出的事实来源；运行时只把当前功能需要的字段投影为稳定的内部模型。编辑已支持字段时，应回写或合并到完整数据中，未知字段和扩展命名空间不得因为导入、编辑或导出而丢失。业务代码不直接依赖一团 raw JSON，新能力也不靠不断扩大字段白名单实现。

世界书、预设、显示正则和候选项等具体概念的对应关系，统一记录在[SillyTavern → dsh-tavern 翻译设计](design/sillytavern-translation.md)中。

dsh-tavern 应当保留：

- 人物卡、世界书、预设、正则和 MVU 等资源格式与字段；
- EJS 模板语法、兼容脚本接口及用户可观察到的效果；
- 现有资源无需作者重写即可导入和运行的体验。

dsh-tavern 可以彻底替换：

- 提示词拼接、插入位置和插入深度的实现；
- 世界书召回、变量绑定与状态更新方式；
- 脚本执行、任务调度以及前后台 Agent 的协作方式。

具体实现上，世界书常驻条目进入稳定前缀，非常驻条目按关键词确定性匹配并增量注入；正则进入独立输出管线，EJS 与兼容脚本在 QuickJS 沙箱中运行，MVU 状态通过受控接口管理，轻量 HTML 放入 iframe 并通过桥接接口通信。单条模板、正则或脚本失败不得中断正文与会话。

### 概念对照驱动的翻译流程

生态兼容不一次性照抄全部字段，而是逐个研究酒馆概念，再建立对应翻译器。每个概念都按以下顺序处理：

1. 收集真实资源，确认它在 SillyTavern 中的格式、执行时机、输入输出、状态变化和失败行为。
2. 区分资源格式、可观察语义与酒馆内部实现，确定真正需要兼容的契约。
3. 设计 dsh-tavern 中对应的原生产物，明确由主 Agent、后台子 Agent、程序状态、输出管线或隔离运行环境中的哪一部分负责。
4. 确定翻译方式：静态转换、语义转换、运行时沙箱适配，或明确暂不支持。
5. 实现翻译器，并用真实酒馆资源对照验证导入结果和运行效果。

每项概念都应形成一份对照记录：

| 项目 | 内容 |
| --- | --- |
| 酒馆概念 | 名称、资源格式和典型样本 |
| 酒馆语义 | 何时执行、读取什么、产生什么效果 |
| DSH 对应产物 | 原生文件、状态、任务、规则或界面 |
| 翻译策略 | 静态、语义转换、沙箱适配或暂不支持 |
| 验证结果 | 格式可读取、行为可运行、效果已验证 |

翻译桥采用“导入时翻译，运行时原生”的原则。导入文件作为不可变原版保存；完整工作 raw 是用户实际编辑和导出的权威人物卡；稳定投影只向 UI、游玩和后台任务提供当前需要的字段。标准字段与未知扩展的修改都回写工作 raw，本地修改历史单独保存。经过统一中间模型生成 dsh-tavern 原生产物时，还应记录原始文件哈希、翻译器版本、生成产物和兼容诊断。只有无法预先确定结果的动态脚本，才保留运行时兼容层。

### 概念对照：世界书

#### 概念

世界书是与人物卡或会话绑定的外部知识集合。它由多个独立条目组成，用于保存人物、地点、组织、事件、规则和背景设定等无法全部放入基础提示词的信息。

#### 目的

世界书解决的核心问题是：**信息总量很大，但模型在当前回合只需要知道其中一小部分。** 因此它本质上是一种渐进式披露机制，而不是“在提示词某个位置插入文字”本身。

#### SillyTavern 的实现

SillyTavern 保留世界书条目及其关键词、常驻、顺序、位置和深度等配置。每轮组装提示词时，常驻条目固定进入上下文，其他条目根据关键词等条件触发，再按照配置插入本轮提示词的不同位置。它通过动态拼接解决召回和注入问题。

#### dsh-tavern 的实现

dsh-tavern 直接复用酒馆世界书的确定性语义，不为召回创建 Agent 或知识 Skill：

- 常驻条目在会话建立时进入稳定前缀，与人物卡基本信息一起保持；
- 非常驻条目对上一轮已完成正文执行关键词、辅助关键词和正则匹配；
- 命中条目按顺序取最多三条，注入下一轮正文一次；
- 实际注入的条目冷却十个已完成剧情回合，条目内容修改后解除冷却；
- 匹配结果与冷却状态绑定剧情 checkpoint，回退时一并恢复；
- 世界书不进入候选、状态结算或后台 Agent 历史。

这种实现保留创作者依赖的常驻、关键词、顺序和辅助逻辑，同时避免额外模型调用、上下文污染和剧透。尚未支持的插入深度、递归扫描、概率与分组等字段保留在原始数据中，并通过兼容诊断明确报告。

#### 翻译器

世界书翻译器无损保留原始文件，并投影运行时需要的确定性字段：

| 酒馆字段或语义 | 翻译结果 |
| --- | --- |
| 世界书基本信息 | 保留绑定关系和完整原始数据 |
| 条目编号、名称和正文 | 保持原文，用于稳定前缀或本轮注入 |
| 常驻 | 会话稳定前缀 |
| 关键词与辅助关键词 | 本地确定性匹配条件 |
| 顺序、优先级 | 命中条目的排序依据 |
| 插入位置、插入深度 | 当前不复刻，保留原值并报告兼容状态 |
| 未识别字段 | 原样保留，并明确报告兼容状态 |

翻译器同时记录原始文件哈希、翻译器版本、条目映射和诊断信息。原世界书变化后重新投影；翻译结果必须通过真实世界书验证条目完整性、关键词命中、排序、冷却和失败回退。

兼容不能只以“文件能够读取”为标准。最终标准是：**现有酒馆资源不需要修改，就能在 dsh-tavern 中产生基本一致的可观察效果，而底层继续使用 DSH 的追加式 Agent 架构。** 后续任务见[TODO 中的酒馆生态兼容](todo.md#p3酒馆生态兼容)。
