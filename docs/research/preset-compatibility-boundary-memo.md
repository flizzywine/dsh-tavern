# 酒馆预设兼容边界备忘

> 状态：核心产品发现，记录于 2026-08-27。本文用于收敛 dsh-tavern 的预设兼容范围。

## 核心发现

酒馆预设可以从产品意图上分为三部分：

1. **流程控制和系统规则**：规定模型如何思考、如何组织一轮生成、执行哪些步骤，以及按什么格式完成任务。
2. **内容偏好**：规定文风、篇幅、人称、叙事节奏、描写倾向和其他创作偏好。
3. **破限方案**：用于改变模型内容边界的提示词及其必要请求结构。

dsh-tavern 已经拥有自己的内置预设。它负责 Agent 身份、前后台任务分工、正文生成、候选项、状态结算、工具调用、输出契约和上下文生命周期。因此，酒馆预设中的流程控制、系统规则和内容偏好不能直接叠加到 dsh-tavern 的运行时，否则两套控制系统会同时争夺同一轮生成。

由此得到明确结论：

> **dsh-tavern 不兼容酒馆预设的完整运行流程。它只从酒馆预设中抽取并兼容破限方案。**

## 三部分的处理决定

| 预设部分 | dsh-tavern 的处理 | 原因 |
| --- | --- | --- |
| 流程控制和系统规则 | 不进入运行时 | DSH 内置预设已经持有 Agent 流程和任务输出控制权，重复注入必然冲突 |
| 内容偏好 | 不从外部预设迁移 | dsh-tavern 使用自身的内容设计、人物卡规则和后续独立文风能力，不让外部预设整体改写生成目标 |
| 破限方案 | 抽取为独立资源并兼容 | 这是外部预设中 dsh-tavern 仍然需要、而自身内置预设不应固定承担的能力 |

这里的“不进入运行时”不等于删除。导入的酒馆预设原文件仍然无损保存，可以查看、导出和重新抽取；只是前两部分不会被投影到模型请求。

## 产品对象重新定义

### 外部预设

用户导入的 SillyTavern 预设原文件。它是只读来源和生态资产，不是可以直接激活的 dsh-tavern 运行配置。

### DSH 内置预设

dsh-tavern 自己维护的 Agent 运行规则。它是流程控制、系统规则、任务分工和输出契约的唯一权威来源，不允许外部预设整体覆盖。

### 破限方案

从外部预设中明确选择并独立保存的可运行资源。它是酒馆预设唯一允许进入 dsh-tavern 模型请求的提示词部分。

因此，产品链路不是：

```text
导入酒馆预设 → 激活整份预设 → 覆盖 DSH Agent
```

而是：

```text
导入酒馆预设 → 阅读和选择 → 抽取破限方案 → 投影到 DSH Agent 请求
```

## 为什么完整预设兼容不可取

酒馆预设通常把流程、内容、格式、破限和上下文拼接混在同一个提示词体系中。传统酒馆每轮重新构造请求，DSH Agent 则拥有持续会话、追加式历史、工具消息、后台任务和自己的系统规则。两种架构对上下文的所有权不同。

如果要求完整兼容酒馆预设，dsh-tavern 就必须在 Agent 内部重新建立一套酒馆式流程控制，并处理两套系统规则之间不断出现的优先级冲突。即使文件字段全部读取，也无法保证两套架构产生相同效果。

放弃前两部分不是兼容失败，而是主动划定边界：保留 dsh-tavern 的 Agent 架构，只兼容真正不可替代的破限能力。

## 破限方案不是一段普通文本

既有实验已经表明，相同提示词内容在不同消息结构中可能产生完全不同的结果。因此，破限方案需要保留的不只是文字，还可能包括：

- 原始条目及启用状态；
- 条目顺序；
- `system`、`user`、`assistant` 角色；
- 历史前、历史中、历史后的位置关系；
- assistant prefill、占位消息、消息合并和角色转换；
- 适用的请求阶段与 Agent 范围；
- 对效果确有影响的模型请求参数。

破限方案更准确的含义是“可执行的请求投影方案”，而不是“复制出来的破限提示词”。普通用户不需要理解这些结构，系统负责保存、投影和诊断。

## 兼容承诺

dsh-tavern 可以承诺：

- 无损保存用户导入的外部预设；
- 允许用户从中选择并抽取破限方案；
- 在不替换 DSH 内置流程的前提下，把方案投影到 Agent 请求；
- 保存真实请求并提供可复现的差异诊断；
- 用普通语言说明未能兼容的结构和实际影响。

dsh-tavern 不承诺：

- 完整运行酒馆预设中的流程控制、系统规则和内容偏好；
- 让 DSH Agent 的每轮请求与酒馆逐字节相同；
- 自动准确识别所有预设中哪些条目属于破限；
- 在所有模型、供应商和审核链路上保证同样的破限效果。

## 验证标准

破限兼容是否成立，不以“提示词已经注入”为标准，而以固定条件下的可重复效果为标准：

1. 固定模型、供应商、人物卡、用户输入和破限方案；
2. 保存最终发送给提供商的完整请求；
3. 对照角色、顺序、位置、消息变换和相关参数；
4. 分别测试兼容模式和 DSH Agent 模式；
5. 每次只改变一个结构变量，记录成功、拒绝、传输失败和重试；
6. 只对已经重复验证的组合标记“已验证有效”。

## 一句话结论

> **酒馆预设是破限方案的来源，不是 dsh-tavern 的运行时；DSH 内置预设负责流程与内容，外部预设只贡献经过明确抽取的破限方案。**
