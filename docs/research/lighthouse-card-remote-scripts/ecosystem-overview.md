# SillyTavern 可编程人物卡生态：人物卡、酒馆助手、MVU 与模板语法

## 结论

这套生态表面上由人物卡、世界书、酒馆助手、MVU、ST Prompt Template、正则和状态栏等许多零散部件组成，实际目标却很统一：**在 SillyTavern（ST）里运行一个具有内容、状态、规则、界面和资源的互动叙事程序。**

它并不是由一个团队自上而下设计出来的应用框架，而是社区围绕“人物卡”这个原本偏静态的数据格式逐层扩建：ST 提供聊天宿主；酒馆助手让卡片能够携带脚本；MVU 维护剧情状态；ST Prompt Template 根据状态加工提示词；世界书、正则、状态栏和 CG 再补齐规则、显示与素材。最终做出的已经不只是“一个角色”，而是一个借人物卡安装和启动的小型应用。

理解这套体系最重要的一点是：**人物卡不是旁支，也不只是给模型看的设定文本；在复杂卡中，它是整个应用的编排文件、内容包和交付载体。**

## 人物卡究竟携带了什么

普通人物卡可以只有角色设定和开场白；复杂人物卡则可能把一整套应用所需的声明集中在一起：

```text
人物卡：应用编排与交付载体
│
├─ 静态内容
│  ├─ 人物设定、背景、开场白
│  └─ 示例对话与基本提示词
│
├─ 世界书与 MVU 协议
│  ├─ 世界设定、剧情规则、变量列表
│  └─ 变量初始化、更新规则与输出约定
│
├─ Tavern Helper 脚本入口
│  ├─ MVU 加载入口
│  └─ 动态世界书、变量守卫、开场白管理等卡片脚本
│
├─ EJS / ST Prompt Template 模板
│  └─ 根据当前变量决定本轮提示词内容
│
├─ 正则、状态栏与交互界面
│  └─ 清理模型输出、呈现状态和提供卡片操作
│
└─ 资源声明
   └─ 立绘、CG、音频或其他外部素材的位置与索引
```

因此，导入一张复杂人物卡，在产品意义上接近“安装一个应用描述包”。卡片本身负责声明这个应用有哪些内容、需要哪些能力、加载哪些脚本以及如何组织它们；真正的执行能力则由 ST 及其扩展提供。不同卡片可以选用不同组合，并非所有人物卡都需要 MVU、酒馆助手或模板语法。

## 各组件如何分层

```text
SillyTavern：宿主、聊天界面、模型连接和扩展系统
│
├─ Tavern Helper（酒馆助手）：人物卡脚本运行平台
│  ├─ MVU：结构化状态管理框架
│  └─ 卡片脚本：动态世界书、变量守卫、状态栏等
│
├─ ST Prompt Template：提示词模板与加工扩展
│
└─ 人物卡：声明内容、依赖、规则、脚本和资源并把它们编排成玩法
```

ST 是最底层宿主，负责对话、历史消息、人物卡、世界书、预设和模型调用。酒馆助手是安装在 ST 上的扩展，但它自身又提供了一套脚本装载与运行能力，使卡作者可以让程序随人物卡分发，而不必把每个功能都开发成独立的 ST 扩展。

MVU 运行在酒馆助手提供的环境中。它把时间、地点、关系、物品、任务等持续状态结构化保存，并在每轮剧情后解析、校验和记录变化。它回答的是：**这一轮结束后，世界变成了什么。**

ST Prompt Template 与酒馆助手平级，是一个独立 ST 扩展。它通过 EJS 模板读取当前变量，进行条件判断、循环和文本组合，决定本轮真正加入模型上下文的内容。它回答的是：**在当前世界状态下，这一轮应该让模型看到什么。**

人物卡则把两端接起来：它提供 MVU 所需的变量结构和更新规则，同时提供模板读取这些变量的方式，还可以附带动态世界书、正则、状态栏和资源索引。酒馆助手与模板扩展是通用基础设施；卡片决定这些基础设施在某个具体故事中如何协作。

## 从导入到运行的数据流

```text
导入人物卡
→ ST 读取人物设定、世界书和扩展声明
→ 已安装的酒馆助手发现并启动卡片声明的 Helper 脚本
→ MVU 初始化该卡定义的结构化状态
→ ST Prompt Template 识别卡内模板并等待生成阶段处理

用户开始一轮对话
→ ST 汇集人物卡、历史消息、世界书和预设
→ 模板根据 MVU 当前状态裁剪、组合本轮提示词
→ ST 将最终上下文发送给正文模型
→ 模型生成剧情
→ MVU 从正文或额外模型结果中提取状态变化
→ 卡片规则与守卫约束更新，并将新状态保存到当前消息分支
→ 正则整理显示内容，状态栏和 CG 界面读取新状态进行呈现
→ 下一轮继续读取更新后的状态
```

这个闭环已经具备典型应用程序的特征：输入是用户行为，业务状态由 MVU 保存，规则由世界书和卡片脚本表达，模板把状态投影为模型上下文，模型承担叙事计算，状态栏和素材构成界面输出。

## 软件工程视角：一个程序如何被“魔改”出来

从产品能力看，这套生态非常有创造力。它让内容作者在没有改动 ST 主程序的情况下，做出了持续状态、条件剧情、动态上下文、分支回复、可视化面板和大型素材库。社区以很低的进入门槛快速验证了“可编程人物卡”的真实需求，这是它能够流行的根本原因。

但从软件工程视角看，它的实现路径与常规应用架构明显相反。正常程序通常先定义应用边界、模块接口、依赖清单、权限模型和发布方式，再把代码、数据与资产交给统一运行时管理；这套生态则是从一个内容文件出发，缺什么就向外再叠一层能力，最终形成“扩展之上再运行脚本，脚本再加载框架，框架再解释卡内协议”的多层结构。

主要偏离体现在：

- **模块边界模糊**：内容、配置、业务规则、界面和可执行代码共同寄存在人物卡及世界书中，职责容易重叠。
- **依赖管理隐式**：卡片依赖哪些扩展、脚本和外部资源，往往要运行后才显现，版本关系也缺少统一约束。
- **权限与安全模型粗放**：人物卡从“内容”升级成了“程序”，但安装与授权体验没有同步升级，用户难以判断它能够读取或修改什么。
- **可复现性不足**：远程脚本和素材可能随上游变化；同一张卡在不同时间、设备和扩展版本下不一定表现一致。
- **测试与兼容治理分散**：每张卡都组合自己的脚本、模板和协议，升级任意一层都可能影响其他层，缺少统一兼容契约。
- **资产管理非正式**：CG 等大型素材通常外置是合理的，但常缺少正式的资源清单、版本、完整性校验、来源和离线安装机制。
- **发布与升级边界混乱**：更新人物卡、脚本仓库、框架或图床都可能改变应用行为，却没有一个统一的应用版本负责描述最终成品。

如果采用常规工程化形态，它更可能被描述为：一个有明确清单和版本的“互动应用包”，其中内容、状态模型、业务脚本、界面和素材各有边界；宿主提供受控 API、权限声明、依赖解析、完整性校验、本地缓存以及统一升级机制。人物卡仍可作为内容入口，但不会独自承担安装器、配置中心、脚本启动器和资源索引等多重职责。

所以，对这套生态最公平的判断不是“技术毫无价值”，也不是把现状合理化。它是**局部能力很强、整体治理很弱**的社区工程：通过连续魔改，勉强把静态人物卡演化成了完整程序；它证明了需求和产品方向，却也暴露了缺少统一软件工程设计后，模块、依赖、权限和发布体系会如何层层缠绕。
