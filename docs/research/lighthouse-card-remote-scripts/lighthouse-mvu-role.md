# 《灯火阑珊》的 MVU 主要在干嘛

## 结论

MVU 在这张卡里相当于一套“剧情状态数据库 + 模型更新协议”。它把自然语言剧情中已经发生的变化，转换成结构化状态，按消息楼层和 swipe 保存；下一轮再把当前状态交给模型、世界书路由器和状态栏使用。

需要把四层东西分开看：

1. **通用 MVU 引擎**：负责初始化状态、读取模型给出的更新指令、执行增删改、触发扩展事件，并把新状态保存到当前消息/swipe。它也支持另请一个模型只做变量解析。
2. **本卡变量结构**：一份 Zod Schema，定义《灯火阑珊》允许保存哪些字段、字段类型、默认值、数值边界和派生计算。
3. **本卡变量更新规则**：写在人物卡世界书里的提示词，告诉模型“剧情出现什么情况时，应该更新什么，幅度多大，哪些不能更新”，并强制输出合法 JSON Patch。
4. **本卡变量守卫**：模型输出之后的第二道保险，统一路径和角色别名，禁止直接修改只读派生字段，保护部分等级数据，最后再用 Schema 整体校正。

所以，**MVU 本身不知道修仙、红颜或任务是什么；这些业务含义由《灯火阑珊》的 Schema、世界书规则和守卫共同赋予。**

## 它主要维护哪些状态

- **世界状态**：世界时钟、地图区域与危险度、世界事件、地点、宗门势力。
- **玩家状态**：等级、修为与突破阶段、灵根、体质、功法、神通、身份、当前位置、灵石、背包、法宝、战斗和渡劫状态。
- **人物关系**：红颜角色资料、修炼状态、好感度、关系及关系上下文，以及普通 NPC 图鉴。
- **剧情进度**：进行中的任务、声望、当前处境、下一轮可参与机遇。
- **规则与缓存**：难度系统、系统版本、好感度快照、宗门推断等供脚本计算使用的内部字段。

其中境界描述、寿元、修炼进度等很多展示值不是让模型直接填写，而是根据等级、修为等基础值自动计算；好感度、修为增长、突破、物品得失和任务流转也都有专门限制。

## 一次变量更新怎么走

1. **读取旧状态**：从上一条有效消息的当前 swipe 取得 `stat_data`；开场白中的 `<initvar>` 提供初始值。
2. **让模型提出变化**：正文模型直接输出，或者额外解析模型根据本轮剧情生成 `<UpdateVariable>`，里面是简短分析和 JSON Patch。
3. **通用引擎解析**：MVU 把 patch 转成 `replace`、`delta`、`insert`、`remove` 等命令，并发出 `COMMAND_PARSED` 事件。
4. **本卡守卫修正**：统一繁简字、路径和双魂角色别名；拦截只读字段；保留需要保护的等级值。
5. **Schema 验证与归一化**：逐条模拟命令，丢弃会使状态不合法的更新；再补默认值、限制范围、计算派生字段和清理无效任务。
6. **保存新快照**：把完整新状态写进当前消息的当前 swipe；必要时同步聊天变量。状态栏据此显示，动态世界书脚本也据此决定下一轮启用哪些世界书条目。

简化成一条线就是：

`本轮剧情 → 模型给出 JSON Patch → 守卫纠错 → Schema 验证/计算 → 保存到当前消息与 swipe → 状态栏和下一轮提示词读取`
