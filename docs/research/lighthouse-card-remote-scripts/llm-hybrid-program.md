# 在混乱中诞生的 LLM 混合程序

## 引言

SillyTavern 生态看起来非常混乱：人物卡里塞着世界书、正则、脚本入口和远程资源；扩展之上又运行 Tavern Helper，Helper 之上再运行 MVU 和人物卡专属脚本；模型输出既是故事，又可能夹带变量更新、状态标签和界面指令。

如果只用传统软件工程的标准观察，这很容易被理解为缺少整体设计造成的技术债。但这只能解释表象。

更深层的原因是：**SillyTavern 原本只是一个面向大语言模型的聊天前端，社区却在持续扩建中，无意间创造出了一种超出其原始架构规划的新程序类型——LLM 混合程序。**

原有系统没有为这种程序准备正式的应用模型、运行时、状态系统和发布格式。于是，新程序所需要的各种能力只能寄生在人物卡、聊天记录、世界书、正则、扩展和远程脚本之中。今天看到的架构混乱，本质上是“新物种被迫寄生在旧架构中”产生的类型错配。

## 什么是 LLM 混合程序

传统程序通常由确定性代码驱动：输入经过预先编写的逻辑，产生可以重复预期的结果。

LLM 混合程序则同时拥有两种执行机制：

- **语义执行**：由 LLM 理解自然语言、判断开放情境、推进剧情、生成内容并提出状态变化。
- **确定性执行**：由传统代码完成数据校验、数值计算、状态保存、资源加载、文本转换和界面渲染。

两者之间还必须存在一套协作协议，规定 LLM 怎样读取当前状态、怎样表达决定，传统代码又怎样解析、验证和提交这些决定。

它的基本运行闭环是：

```text
用户输入
  → 读取状态与知识
  → 组装本轮上下文
  → LLM 进行语义计算
  → 输出正文或结构化操作
  → 传统代码解析、校验和执行
  → 保存新状态并渲染界面
  → 新状态进入下一轮
```

因此，LLM 在这里不再只是被应用调用的一项能力，而是应用运行时的一部分；提示词和自然语言规则也不再只是配置，而是由 LLM 解释执行的“软代码”。

## 人物卡如何越过原来的边界

人物卡最初主要是一份角色描述：告诉模型角色是谁、如何说话、身处什么场景。它并不是为承载完整程序设计的。

但用户很快不再满足于一次性的角色扮演。他们希望世界持续变化、角色记住关系、物品可以获得和消耗、任务能够推进、不同地点加载不同资料、状态可以显示为面板，甚至希望加入图片、按钮和小游戏式交互。

这些需求共同指向的已经不是“更丰富的角色描述”，而是一个有状态、有规则、有界面、有资源的应用。由于 SillyTavern 没有对应的正式应用抽象，社区只能利用已有机制逐层扩展：

```text
静态人物设定
  → 世界书补充知识
  → 特殊标签规范模型输出
  → 正则解析、隐藏和渲染标签
  → EJS 根据变量动态生成提示词
  → Helper 脚本加入事件与业务逻辑
  → MVU 管理结构化状态
  → 动态世界书按状态加载资料
  → HTML、CG 和按钮组成应用界面
```

每一步在当时都解决了真实问题，但这些能力不是在统一规划下形成的。它们不断叠加，最终让人物卡从“模型输入资料”变成了“应用编排文件和交付载体”。

## 一种程序，被分散在整个酒馆生态中

从 LLM 混合程序的角度重新观察，酒馆生态中的各种东西并非毫无关联。它们分别承担了一个应用原本应该具备的职责。

| 程序职责 | 酒馆生态中的实际载体 |
|---|---|
| 应用定义 | 人物卡描述、场景、开场白、作者说明 |
| 领域知识 | 人物卡字段、世界书、外部资料库 |
| 语义规则 | 提示词、预设、世界书中的自然语言规则 |
| 确定性逻辑 | 正则、EJS、Helper JavaScript、MVU、变量守卫 |
| 状态 | 聊天上下文、特殊状态标签、聊天变量、MVU 变量 |
| 上下文编译 | ST 提示词管理、世界书激活、模板语法、动态世界书 |
| LLM—代码协议 | 特殊标签、固定输出格式、JSON、JSON Patch、MVU 协议 |
| 生命周期 | ST 事件、Tavern Helper 事件和脚本监听 |
| 持久化与分支 | 聊天消息、消息楼层、swipe 和附属变量 |
| 用户界面 | 聊天窗口、正则渲染、HTML 状态栏、按钮和 CG |
| 资源分发 | 人物卡内嵌资源、GitHub、CDN、Cloudflare R2 |
| 包与依赖 | 人物卡扩展字段、远程 `import` 和安装说明 |

问题不在于这些职责不存在，而在于它们没有形成清晰、稳定的模块。

人物卡同时充当应用说明、初始化数据、依赖清单、脚本入口和资源索引；世界书同时充当知识库、提示词模块、业务规则和条件路由；聊天记录同时充当对话界面、LLM 上下文、事件历史和状态数据库；正则同时充当协议解析器、文本处理器和界面模板；Tavern Helper 同时充当脚本加载器、运行环境和宿主能力桥梁；GitHub 与 CDN 则被临时当作包管理器、更新渠道和资源服务器。

这些角色叠加在一起，才形成了今天所谓的“复杂人物卡”。

## 正则卡与 MVU 卡都是 LLM 混合程序

正则卡并不是无状态程序。单次正则匹配本身通常不保存状态，但整套正则卡可以把状态维护在 LLM 上下文中。

模型在每轮正文里读取并重写特殊状态块，正则负责识别、隐藏、清洗或渲染这些状态。这里的聊天上下文就是内存，状态标签就是数据格式，LLM 同时承担状态读取、业务判断和状态更新。它是一种以文本为存储介质的原始 LLM 状态机。

MVU 则进一步把状态从正文中分离出来，保存为结构化变量。LLM 不再需要重写完整状态，而是提出增量变化；传统代码解析更新、验证结构并保存结果。Schema 定义允许存在的数据，变量守卫纠正模型容易产生的错误，状态栏和动态世界书再消费这些数据。

因此，两者不是“有状态”和“无状态”的区别，而是两种不同的状态实现：

- 正则卡使用**上下文承载的隐式文本状态**；
- MVU 卡使用**程序管理的显式结构化状态**。

它们都在运行 LLM 与传统代码共同组成的程序，只是工程复杂度和确定性程度不同。

## 为什么它必然超出 SillyTavern 的原始规划

SillyTavern 原来的核心对象是聊天、人物卡、世界书、预设和模型请求。它可以很好地组织对话，却没有把人物卡视为具有代码、状态、依赖、权限和生命周期的应用。

当人物卡真正开始携带程序能力后，原来的架构缺少至少以下概念：

- 正式的应用清单；
- 统一的状态模型与迁移机制；
- LLM 与代码之间的标准操作协议；
- 受控的脚本运行环境和权限声明；
- 可锁定版本的依赖管理；
- 资源清单、缓存与完整性校验；
- 应用级错误隔离、调试和测试；
- 应用整体的安装、升级与卸载边界。

社区并没有停止等待这些基础设施出现，而是直接利用能够接触到的每一个扩展点补齐能力。结果是局部功能不断增强，整体接口却越来越模糊：扩展之上运行脚本，脚本再加载框架，框架解释卡内协议，协议又依赖模型遵守自然语言规则。

这不是一个常规软件团队会主动设计出来的架构，却是现有宿主被迫承载新需求时非常自然的演化结果。

## 如何评价这种混乱

从软件工程角度看，它确实存在明显问题：依赖隐式、版本漂移、权限粗放、状态来源不统一、模块职责重叠、调试困难、远程资源不可复现。复杂人物卡表面上是一份内容文件，实际上可能执行远程代码并修改聊天数据，但安装过程并没有提供与这种能力相匹配的安全提示和治理机制。

然而，只把它归结为“技术水平差”也不完整。

这套生态的价值在于，它用大量非正式的组合证明了一件此前并不清晰的事情：**LLM 可以与传统代码共同构成一种新的应用运行方式。**自然语言可以承担开放、模糊、难以穷举的业务逻辑；传统代码则守住确定性、状态和交互。人物卡作者即使没有完整的软件工程能力，也能够通过编写世界观、规则、模板和少量脚本，做出接近完整文字游戏的应用。

因此，对它更准确的评价是：

> 酒馆生态不是先设计出 LLM 混合程序框架，再开发人物卡应用；而是在不断制作更复杂的人物卡时，先把 LLM 混合程序这个新物种做了出来，随后才开始意识到自己缺少相应的架构。

它是局部创造力极强、整体工程治理不足的产物。混乱不是创新的理由，但确实记录了创新发生的路径。

## 下一步真正需要的抽象

如果未来要把这种能力工程化，真正需要的不是再增加一层插件，而是正式承认“LLM 混合程序”是一等对象。

一个完整的 LLM 混合应用包应当明确包含：

```text
应用清单
领域知识与资源
状态模型与初始状态
由 LLM 执行的语义规则
由传统运行时执行的确定性代码
LLM 与代码之间的协作协议
上下文编译策略
界面与交互
模型能力要求
依赖、版本与权限
状态迁移、测试与错误处理
```

宿主应当提供稳定而受控的运行时，人物卡则可以回归为应用内容的一部分，而不必继续同时承担安装器、包管理器、数据库结构、脚本启动器和资源索引等所有职责。

SillyTavern 社区已经用混乱但有效的方式完成了需求探索。下一阶段的问题不再是“还能往人物卡里塞什么”，而是：**如何为已经诞生的 LLM 混合程序建立真正属于它的应用模型。**
