# MVU 只结算、不注入前台备忘

> 决定日期：2026-09-01
>
> 状态：普通游玩编排策略的实验性架构决定

## 决定

启用后台 MVU 结算的普通游玩对话中，dsh-tavern **有意不把 MVU 变量自动注入前台剧情模型**。

每轮剧情正文提交后，后台 Agent 读取完整变量快照、最终正文、变量结构和更新规则，完成变量结算并保存结果。下一轮前台请求继续读取剧情历史、人物卡、世界书、用户指导和既有前台上下文，但不自动加入：

- `stat_data`；
- `schema`；
- `display_data`、`delta_data`；
- 从 MVU 变量自动生成的摘要或筛选结果。

这不是“变量注入尚未实现”的临时缺口，而是当前有意保留的实验行为。

## 变量的身份

在这条编排策略中，剧情正文是唯一的剧情事实来源。MVU 变量是后台根据已提交正文生成的结构化投影，用于：

- 状态栏和人物卡界面；
- 人物卡脚本；
- 统计、诊断和存档检查；
- 其他明确消费变量、但不反向改写剧情事实的后台能力。

变量不是前台剧情模型下一轮必须服从的第二份权威状态。删除或关闭 MVU 后，正文游玩链路仍应能够继续。

这一决定来自此前独立 Pi 文字游戏的实际开发与游玩经验：在原生变量结算和更新机制已经可用的情况下，把变量持续注入文字表演并没有明显改善连续性，反而让模型更关注数值、标签和状态表，限制了行文的灵动与流畅。

对于文字输入、文字输出的 LLM 游戏，原文已经是更丰富的世界模型。变量是传统程序为了计算和展示而对世界做的简化建模；把原文结算成变量，再把变量交还给 LLM，是一次有损压缩后的反馈。只要前台能够找到相关剧情原文，这层反馈通常没有增加新的信息。

持久化时也必须保留产生变量的剧情原文。每条消息和 Swipe 的变量快照可以为了展示、恢复和诊断继续保存，但其身份是可重建缓存，不得替代、覆盖或删减原文。若二者冲突，以已经提交的剧情原文为准。

## 为什么不注入

首要原因不是节省 token，而是避免低维变量投影反过来支配高维叙事。

不同人物卡的变量结构、数量和语义差异极大。平台无法可靠判断哪些字段与下一轮剧情有关：

- 全量注入会让大卡占用大量上下文，并把内部字段、数值和展示副本暴露给剧情模型；
- 按字段名或当前场景自动筛选可能静默漏掉关键状态；
- 再调用模型生成变量摘要会增加新的延迟、成本、漂移和调试链路；
- 要求所有人物卡作者维护前台投影规则，会把新的配置负担扩散到整个生态。

不注入让 MVU 模块保持较深的接口：前台只负责写剧情，后台只根据已经发生的剧情结算和展示状态，双方不需要共同理解任意人物卡的变量结构。

## 文本—注意力原理

前台剧情模型的稀缺资源不只是上下文窗口，更是对当前任务的有效注意力。

1. MVU 变量来源于剧情正文，是正文的有损压缩，不比产生它的原文拥有更高的信息保真度；
2. 当前台对相关历史拥有足够注意力时，直接阅读原文已经足够，回灌变量只会重复同一事实；
3. 当前台注意力不足时，无差别加入变量、摘要和状态表会继续争夺有限注意力，可能让模型更难关注真正相关的情节；
4. 因此前台记忆问题的主要解法应是**检索**：先根据当前输入定位相关历史，再读取命中的剧情原文，而不是把全部派生状态持续塞入每轮请求；
5. 变量可以辅助结算、展示、确定性程序和检索定位，但不能因为更短、更结构化就自动取得叙事权威。

这里反对的是无条件回灌，不是否认一切结构化查询。若前台执行某个明确任务确实需要核对精确状态，可以通过受控工具主动查询必要字段；查询结果是当轮证据，不是每轮默认注入。不过这类工具是否需要建设，仍须由真实游玩证据单独决定。

因此，普通游玩的长期记忆方向应是：保留权威剧情原文，为前台提供按需搜索与读取能力，让 Agent 自主决定此刻需要召回哪段历史。检索命中的原文进入当轮上下文；未命中的变量和历史不占用本轮注意力。

## 明确接受的代价

这项决定意味着：

- 只存在于变量、没有出现在正文或其他前台上下文中的事实，不会自动影响后续剧情；
- 好感度阈值、隐藏旗标、背包、任务进度等机制，不能仅靠变量变化驱动前台叙事；
- 脚本单独修改变量后，剧情模型不会因此自动得知；
- 某些依赖变量宏或动态提示词的传统人物卡，在普通游玩中可能与原作行为不同。

这些不是实现遗漏，而是实验需要验证的产品取舍。

## 模式范围

本决定只约束 **普通游玩编排策略 + 后台 MVU 结算**。

兼容编排策略仍以人物卡的可观察语义为准：如果外部预设、ST Prompt Template、世界书或人物卡文本显式使用变量宏，兼容 Adapter 可以按其原有位置展开变量。不能用本备忘为兼容模式缺少显式变量宏辩护。

## 当前不做

- 不向普通游玩前台注入完整 `stat_data`；
- 不按字段名、出场人物或关键词自动挑选变量；
- 不让后台 Agent 额外生成“前台变量摘要”；
- 不给前台增加按需查询 MVU 变量的工具；
- 不建立人物卡级变量白名单或投影配置。

以上能力只有在真实游玩证据证明“不注入”无法成立后，才分别立项讨论；不能作为一次 MVU 修复顺带加入。

## 验证与推翻条件

测试时重点记录以下现象：

1. 状态栏拥有关键事实，但前台正文连续多轮遗忘或与其冲突；
2. 人物卡的核心玩法必须由变量阈值、隐藏旗标或脚本变量驱动；
3. 在已经提供历史检索后，正文仍不足以维持物品、任务、关系或位置连续性；
4. 用户必须反复把状态栏内容手动告诉前台模型才能继续；
5. 同一张卡在兼容模式正常、普通游玩持续失效，且差异可归因于变量注入。

出现个别案例时先保存人物卡、最终前台请求、检索过程和可复现对话，不立即引入通用筛选算法。先区分问题来自正文没有记载、检索没有命中，还是模型已经读到原文但仍无法维持连续性。只有多张真实人物卡反复证明“检索原文、不回灌变量”破坏核心体验，才重新评估以下替代方案：人物卡显式投影、确定性有界投影、按需读取工具或后台叙事摘要。

## 后续架构含义

如果实验成立，变量结算不再是下一轮前台生成的前置依赖。前台长期记忆应围绕“搜索历史正文 → 读取相关原文 → 基于证据续写”建设，而不是围绕变量回灌建设。未来可以单独评估是否允许前台继续游玩而后台稍后完成结算；历史检索和异步结算都不是本备忘已经授权或实现的改动。
