# 酒馆超集兼容层方案

> 历史方案：顶层“兼容层”概念已被“普通游玩编排策略 / 兼容编排策略 + 酒馆脚本运行模块”取代。本文仅保留早期兼容目标和实施证据；当前架构见[编排策略与酒馆脚本运行模块架构](orchestration-strategies-and-tavern-script-module.md)。

> 决定日期：2026-08-28
>
> 状态：已确认，实施中

> 2026-08-28 进展：第一张真实卡《灯火阑珊》的纯前台 MVU、EJS 核心、发送/显示正则、常驻 Helper 脚本、动态世界书、变量守卫及消息级 Swipe 主链路已跑通；15 个开场 Swipe 已经通过浏览器 Helper 生命周期重新结算，并与一份固定 SillyTavern 开场变量基线完成局部差分。当前均为“受限支持”，固定模型输出、请求和显示的完整差分仍未完成。

## 目标

dsh-tavern 建立一套**酒馆超集兼容层**：现有 SillyTavern 人物卡、世界书、预设、正则、MVU 和 Tavern Helper 脚本应尽可能不经改造即可运行；在完整承接旧生态之后，再增加 DSH 能力。

当前阶段坚持**纯前台 MVU**：人物卡原有 MVU 提示词继续进入前台上下文，前台模型同时生成正文和标准 MVU 更新协议。暂不抽取规则给后台模型，也不设计自有变量更新方言。

这里的“超集兼容”不是文件能够导入，也不是界面大致相似，而是：

> 在相同人物卡、预设、世界书、聊天历史和模型输出下，人物卡能够观察到与目标版本 SillyTavern 生态一致的请求、消息、变量、事件、Swipe 和显示结果；DSH 新能力只能增加行为，不能破坏旧行为。

## 核心决定

1. **兼容以原实现和可观察行为为权威。** 不凭文档印象重新设计 MVU、EJS 或 Tavern Helper。
2. **优先受控移植上游代码。** 能合法、稳定复用时，使用固定版本的原实现，而不是编写“差不多”的替代品。
3. **宿主差异集中在 Host Adapter（桥接层）。** 上游运行时不直接了解 DSH；模型、会话、存储、网络和 UI 由 dsh-tavern 冒充 SillyTavern 宿主提供。
4. **SillyTavern 暂不整体搬入。** 它首先是规范来源、依赖来源和差分测试基准；只逐步收入人物卡实际依赖的语义。
5. **未知能力保守处理。** 不认识的字段、脚本和提示词原样保留；不得因优化或推断而静默删除。
6. **兼容失败局部隔离。** 单条模板、正则、世界书或脚本失败不能摧毁正文、消息和整局会话。

## 总体架构

```text
人物卡 / 世界书 / 预设 / 正则 / Helper 脚本
                        ↓
             兼容层
    ┌──────────────────────────────────────────┐
    │ SillyTavern 提示词、宏与世界书语义      │
    │ ST Prompt Template / EJS                 │
    │ 发送侧与显示侧正则                       │
    │ 官方 MVU Runtime                         │
    │ Tavern Helper Script Runtime             │
    │ 消息、变量、事件、Swipe 与 UI 生命周期  │
    └──────────────────────────────────────────┘
                        ↓
               Host Adapter（桥接层）
                        ↓
          DSH 模型调用 / Session / 存储 / UI
```

`兼容层` 是一个深模块。调用方只需要理解少量接口，酒馆生态的复杂执行顺序、错误模式和状态语义全部留在模块内部。

建议外部 seam 最终收敛为三个阶段性接口：

- `prepareTurn`：根据人物卡、聊天分支和当前状态构造本轮前台请求。
- `settleResponse`：接收原始模型输出，执行 MVU、消息变量、事件和持久化结算。
- `renderMessage`：执行显示正则、HTML 和 Helper UI 投影。

这些名称不是最终代码接口；实施前仍需结合现有数据流确定输入、输出和错误契约。

## 上游代码复用策略

“直接抄”在工程上落实为**受控移植**：

- 记录仓库、许可证、版本、提交哈希和构建产物来源；
- 优先以独立包、vendor 目录或可追踪补丁引入；
- 尽量不修改上游实现，宿主差异通过 Adapter 注入；
- 必须修改时，保持小补丁并记录原因，便于同步新版本；
- 不允许从 CDN 静默漂移到未知版本；
- 许可证不允许直接复用时，以原实现的可观察行为和差分测试进行兼容实现。

运行时现已把人物卡 Helper 脚本和显示正则中的 jsDelivr GitHub 分支、默认分支解析为 40 位提交号，并把映射独立持久化；人物卡原文不被改写。GitHub API 配额不足时使用只读 Git 后备解析。固定提交的入口 JS/HTML 还会按 SHA-256 缓存，浏览器只通过本机只读哈希地址加载；重启断网时可复用已验证内容。提交号无法解析、缓存缺失或内容校验失败时，该条运行时投影会被禁用并给出诊断。递归 import、npm CDN 和 R2 CG 仍需后续独立锁定。

### MVU

优先直接移植官方 MagVarUpdate，使其继续拥有以下语义的解释权：

- `<UpdateVariable>` 与标准更新命令解析；
- `replace`、`delta`、`insert`、`remove`、`move` 等操作；
- `stat_data`、初始化与 Schema；
- 消息和 Swipe 变量快照；
- 生命周期事件、失败处理和状态栏挂载时序。

dsh-tavern 不另造简化 Patch 方言。当前所有 MVU 规则仍由前台模型处理。

### ST Prompt Template / EJS

优先复用原模板引擎及其执行顺序，兼容变量、宏、条件、循环和脚本表达式。外围只负责：

- 提供模板运行所需上下文；
- 限制执行时间、内存、输出和外部资源；
- 将单项错误转成可诊断结果；
- 保留未处理的原始素材，避免破坏整轮请求。

### Tavern Helper

目标不是只模拟几个常用函数，而是让原有 Helper 脚本尽可能运行。应优先研究直接移植其运行时，再由 Host Adapter（桥接层）提供它依赖的宿主能力，包括：

- 聊天消息、消息编号与 Swipe；
- 全局、聊天和消息变量；
- 世界书读取与修改；
- 事件订阅与触发；
- 模型请求和取消；
- iframe、DOM、jQuery、Lodash、通知等浏览器环境；
- 脚本加载、卸载、清理与异常隔离。

### SillyTavern

当前不复制整个 SillyTavern 应用。采用“按依赖下钻”的方式：

1. 先将 SillyTavern 固定版本作为行为基准；
2. 通过真实人物卡发现缺失能力；
3. 定位该能力在 SillyTavern 中的权威实现；
4. 能复用则受控移植，不能复用则依据行为契约实现；
5. 纳入差分测试后再继续下一个能力。

优先关注人物卡可观察的语义：提示词装配、宏、世界书激活、正则、消息与 Swipe、扩展事件、变量存储和 HTML 生命周期。不得把 SillyTavern 的整个页面、账户、模型配置和应用壳无条件复制进来。

## 当前纯前台运行链路

```text
原始酒馆资源
    ↓
按 SillyTavern 语义装配前台请求
    ↓
前台 LLM 输出正文 + 标准 MVU 协议 + 卡片所需标签
    ↓
兼容层按原顺序执行发送后处理、MVU、事件与消息保存
    ↓
显示正则、Helper 脚本和状态栏读取更新后的状态
    ↓
用户看到最终消息与 UI
```

当前明确不做：

- 不把 MVU 提示词迁移到后台模型；
- 不根据正文重新推断一套自定义变量补丁；
- 不把酒馆资源预先转换成 DSH 原生格式；
- 不用“近似状态树”替代官方 MVU 的消息与 Swipe 语义。

未来即使将 MVU 指令生成迁移到后台，官方 MVU 执行器、变量结构、事件、Schema 和持久化语义也应继续复用。后台化只能改变任务由哪个 LLM 执行，不能改变人物卡观察到的协议。

## 状态与生命周期原则

兼容层必须明确区分：

- 原始模型输出；
- 清理协议后的正文；
- 每条消息、每个 Swipe 对应的变量快照；
- 显示正则和 HTML 产生的 UI 投影；
- 下一轮请求真正发送的聊天内容。

任何显示转换不得反向污染原始模型输出和权威变量。重新生成、Swipe、回退、删除消息和切换分支后，MVU 状态与 UI 必须回到相应快照，不能只维护一棵全局“当前状态树”。

## 安全与兼容等级

部分人物卡脚本默认可以访问父页面、网络、外部 CDN 和大量全局对象。完整兼容与强隔离不能同时无条件成立，因此运行时提供明确等级：

- **默认兼容模式**：限制网络、父页面和高风险能力；不支持的调用产生诊断。
- **受信任人物卡模式**：经用户明确授权后开放更接近原酒馆的同源 DOM、外部脚本和宿主能力，以换取最高兼容性。

两种模式使用同一套兼容语义，区别只在能力授权。不得用安全名义静默伪造成功，也不得在默认模式中无提示执行任意远程代码。

## 兼容性的证明方式

构建固定的真实人物卡语料库，在同一版本 SillyTavern 与 dsh-tavern 中进行差分验证。至少比较：

1. 最终发送给模型的角色、顺序与文本；
2. 原始模型输出与正文清理结果；
3. MVU 初始化、命令执行和 Schema 结果；
4. 每条消息和每个 Swipe 的变量快照；
5. Helper 事件顺序和可见宿主状态；
6. 发送正则与显示正则结果；
7. 状态栏、按钮、CG 和交互 UI；
8. 模板、正则或脚本失败后的局部降级行为。

构建通过、单元测试通过或脚本成功加载，都不能单独证明兼容。每项能力必须给出：`完整支持`、`受限支持`、`近似支持`、`不支持` 四种明确状态之一。

## 分阶段实施

### 第一阶段：固定基线

- 固定目标 SillyTavern、MVU、ST Prompt Template 和 Tavern Helper 的版本与提交；
- 完成许可证和依赖审计；
- 建立《灯火阑珊》等真实人物卡回归语料；
- 捕获 SillyTavern 的请求、变量、事件、Swipe 和显示结果。

### 第二阶段：纯前台 MVU

- 引入官方 MVU 或与其同源的受控运行时；
- 接通人物卡初始化、前台标准协议、变量结算和消息/Swipe 快照；
- 接通状态栏读取变量所需的最小 Helper 环境；
- 以真实人物卡完成端到端验证。

### 第三阶段：模板与脚本运行时

- 引入 ST Prompt Template / EJS；
- 扩展 Tavern Helper 宿主 Adapter；
- 补齐事件、世界书、消息操作、UI 生命周期和资源加载；
- 保证单个资产失败可隔离。

### 第四阶段：按缺口吸收 SillyTavern 语义

- 使用差分测试定位缺口；
- 每次只收入一项明确行为；
- 同步更新兼容矩阵和真实人物卡回归测试；
- 避免演变成不可控的 SillyTavern 整体分叉。

### 第五阶段：超集能力

在旧生态行为稳定之后，再增加 DSH 原生能力，例如后台 MVU、Agent 工具、结构化状态和原生 View。新增能力必须可关闭，关闭后仍回到完整兼容基线。

## 实施门槛

开始写代码前，需要先产出第一阶段的具体实施设计，至少回答：

- 目标上游版本分别是什么；
- 各仓库许可证是否允许当前复用方式；
- 官方 MVU 的最小宿主依赖是什么；
- 现有 dsh-tavern 消息/Swipe 数据如何映射；
- 哪个 seam 接入当前兼容请求编译器；
- 第一张端到端人物卡使用哪些可观察结果验收。

在这些问题回答前，不直接把多个上游仓库代码混入产品目录。

## 一句话结论

> **先用受控移植建立一个行为上忠于酒馆生态的兼容层，再由 Host Adapter（桥接层）冒充 SillyTavern 宿主并承接底层差异；旧卡原样运行是底座，DSH 新能力是可选超集。**
