# 从 LLM 游戏重新审视酒馆生态

> 状态：方向设计稿。本文不描述一项待立即实现的单独功能，而是把酒馆社区已经验证的需求重新表达为原生 LLM 游戏平台的领域能力。

## 核心判断

酒馆生态不是 LLM 游戏的最终形态，但它是目前最丰富的 LLM 角色游戏需求样本之一。

人物卡、世界书、预设、正则、MVU、数据库、状态栏和社区脚本，并不是偶然堆积出来的技术零件。它们是在“组织上下文、发送文本、接收文本、展示文本”这一有限宿主之上，对真实游戏需求的长期回应：人物需要持续存在，世界需要记忆，状态需要变化，知识不能一次全部注入，玩家需要界面，创作者需要规则，游戏需要存档。

问题不在这些需求，而在于它们只能借用文本、提示词和浏览器脚本来表达。社区不得不让一轮模型输出同时承担小说正文、状态协议、数据库更新、程序调用和 UI 数据源。组件可以组合运行，却缺少统一的所有权、事务、权限、生命周期和发布格式。

因此，DSH 下一阶段不应继续只问：

> SillyTavern 还有什么能力没有兼容？

而应开始问：

> 如果 LLM 游戏成为独立游戏类型，它需要怎样的世界模型、运行时、制作工具和分发格式？

酒馆生态应继续作为内容来源、需求样本和兼容入口；DSH 的内部模型则应逐渐由原生 LLM 游戏概念主导。

## 从生态零件到游戏能力

| 酒馆生态概念 | 它解决的真实问题 | 原生 LLM 游戏概念 |
|---|---|---|
| Swipe、回退、重生成 | 保存进度并尝试另一种未来 | 存档点、世界线与时间线 |
| 人物卡 | 让一个角色具有稳定身份和行为 | 人物集与角色社会 |
| 世界书 | 世界资料无法一次全部放入上下文 | 知识与上下文披露系统 |
| 状态栏、小手机、HTML | 纯聊天框无法承载完整游戏交互 | 游戏 View 与应用系统 |
| 数据库、摘要、检索 | 长程游玩会遗忘和失去连续性 | 世界连续性与记忆系统 |
| MVU、变量宏 | 剧情变化需要形成可计算状态 | 状态、事件与效果事务 |
| 预设 | 模型需要稳定的叙事规则和请求编排 | 叙事策略与 Agent 编排 |
| 正则、EJS、Helper 脚本 | 宿主缺少转换、事件和工具能力 | 受控程序能力与兼容适配器 |
| 人物卡及其配套资源 | 作者需要分享一套可以运行的内容 | 可版本化的原生游戏包 |

这不是简单改名。每一次转换都意味着重新划定权威来源、生命周期和权限边界。

## 一、Swipe 是存档机制，不是消息装饰

从玩家视角看，每个可切换的 Swipe 都是一份存档结果：它保存了在同一个剧情位置上可能成立的一种未来。左右滑动的本质，是切换当前采用的存档点。

原生运行时不需要把多个结果塞进同一条可变消息，可以把它们表达为从同一父存档点生长出的不同世界线：

```text
Checkpoint R12
  ├─ World A：正文 A + 状态 A + 人物记忆 A
  ├─ World B：正文 B + 状态 B + 人物记忆 B
  └─ World C：正文 C + 状态 C + 人物记忆 C
```

由此可以统一解释：

- **重新生成**：从同一个父存档点计算另一份结果；
- **Swipe**：在兄弟存档结果之间切换；
- **回退**：把活动世界线退回更早的存档点；
- **分支**：保留已有未来，并从历史位置继续形成新世界线；
- **确认当前结果**：选择哪一份存档成为当前活动进度。

完整存档不能只有可见正文，还必须覆盖当时的世界状态、人物状态、知识与记忆、任务和延迟事件、游戏包版本、必要的模型来源以及仍在运行的后台操作。

Agent 结果必须绑定 `game / branch / base revision / operation`。切换存档以后，旧世界线的后台任务必须取消或失去提交权，不能返回后污染新的活动世界线。

历史保持追加，活动位置可以切换。这样既支持类似 Swipe 的轻量体验，也支持真正的存档、分支、回放和世界线管理。

## 二、人物卡应升级为人物集与角色社会

人物卡以单个核心人物为外层内容容器，适合角色聊天，却不适合作为完整游戏的根对象。游戏拥有的不是一张人物卡，而是一组共同生活在世界中的人物。

原生人物集至少包括：

- 玩家角色；
- 核心人物；
- 长期配角；
- 临时人物；
- 家庭、组织与势力；
- 尚未完整设计、等待剧情升格的人物种子。

对每个人物还要区分：

1. **人物设计档案**：相对稳定的身份、经历、外貌、性格、欲望、弱点和表达方式；
2. **人物运行状态**：当前地点、健康、情绪、资源、任务和关系；
3. **人物知识与记忆**：他经历、听说、相信、误解和隐瞒的内容；
4. **人物关系网络**：人与人、人与组织之间随世界线变化的关系；
5. **表现资源**：头像、立绘、声音、服装、姿势和不同阶段的视觉版本。

人物设计档案不等于人物当前状态，也不等于人物记忆。基础人物设计可以被多个世界线复用，但某个世界线中的生死、关系与认知必须属于该世界线的存档。

人物不必在开局前全部完整生成。一个只被提到名字的路人可以先作为人物种子；当他反复出现或承担重要剧情功能时，现有后台 Agent 可以加载人物设计 Skill 和工具，在原任务内补全人物档案，无需固定创建一个额外的“人物设计 Agent”。

当人物拥有独立目标、日程、关系、知识与行动能力以后，人物集会自然发展成角色社会。是否为每个 NPC 分配独立 Agent，是运行时调度策略，不应成为人物定义本身。

## 三、世界书应升级为上下文披露系统

世界书解决的本质问题不是“把文字插入提示词的哪个位置”，而是：世界信息总量远大于一次模型调用的注意力容量，必须根据条件逐步披露。

原生系统需要把三件事分开：

1. **世界事实**：在当前世界线中什么是真的；
2. **披露状态**：玩家、人物或 Agent 已经知道什么；
3. **本轮上下文投影**：当前任务真正需要让某个 Agent 看见什么。

一次上下文选择可以表示为：

```text
完整世界知识
+ 当前世界线状态
+ 当前场景与参与人物
+ 玩家本轮意图
+ Agent 身份、职责与知识权限
+ Token 预算
        ↓
检索、过滤、排序与精度选择
        ↓
本轮 Agent 实际可见的上下文
```

披露条件不只包括关键词，还可以包括地点、人物、时间、事件、任务阶段、持有物品、语义相关性和知识权限。同一份资料可以提供索引、摘要、详述和原始档案等多个精度层级，先给模型简短索引，真正需要时再逐层展开。

同一秘密对不同主体具有不同可见性：导演可以知道，凶手可以知道，玩家角色可能尚未知道，其他 NPC 可能只知道错误传闻。检索出了信息，不等于允许把它注入所有 Agent。

传统世界书的常驻、关键词、顺序、概率、冷却和递归扫描可以成为兼容输入，但原生概念应是 **Context Disclosure System**：在有限注意力下管理知识召回、权限、防剧透、精度和预算。

其中，传统酒馆因为一次性生成而依赖宿主主动选择和注入；原生 Agent 应以自主搜索、分层读取为主要路径，只由系统提供不可遗漏的最小约束。完整原则见[《Agent 自主上下文：从“喂给模型”到“模型自己寻找”》](agent-owned-context.md)。

## 四、状态栏和小手机应升级为游戏 View 系统

状态栏、小手机、地图、任务板、关系图和经营面板都不是人物卡美化，而是游戏 UI。酒馆把正文聊天框作为主要界面，社区只能利用正则、iframe、HTML 和浏览器脚本自行扩展，因而形成大量互不兼容的方案。

原生运行时不应规定所有游戏采用同一种状态栏或手机外观，而应统一数据和行为协议：

```text
World State
    ↓
View Model
    ↓
HUD / 手机 / 地图 / 背包 / 战斗界面
    ↓ 玩家操作
Typed Command
    ↓
规则或 Agent 裁决
    ↓
Event + State Effect
```

界面只读取获准的 View Model，并提交结构化命令，不能任意修改变量、正文或数据库。

游戏 UI 可以分为：

- **HUD**：时间、地点、人物状态、任务和资源；
- **世界内应用**：手机聊天、电话、邮件、论坛、新闻、银行和地图；
- **游戏专属界面**：战斗、经营、建造、调查板和关系网络；
- **系统界面**：存档、世界线、设置、Agent 轨迹和诊断。

大多数界面可以采用声明式组件，由作者或制作 Agent 生成；复杂界面则在沙箱中运行，通过受控 UI SDK 读取状态、订阅事件、解析资源和提交命令。现有社区 HTML 与手机脚本继续由兼容沙箱承接，但不再定义原生 UI 架构。

还必须区分世界状态、玩家 UI 偏好、临时 View 状态和插件私有数据。手机当前打开哪个联系人不一定是游戏事实；某条消息是否已经发送、对方是否已读，则可能属于世界线存档。

## 五、数据库应升级为世界连续性与记忆系统

数据库真正解决的是长程游玩的连续性：一个生成式世界如何在几十、几百乃至几千轮以后，仍能找回发生过的事情并沿同一历史继续发展。

DSH 已经采用完整历史、压缩和按需检索的方向。原生化以后，需要明确区分：

- 权威事件：实际上发生了什么；
- 当前状态：世界现在是什么样；
- 情节记忆：事情如何发生及其未解决后果；
- 人物记忆：某个人经历或获知的版本；
- 分层摘要：长历史的低成本表示；
- 检索索引：重新找到相关信息的派生结构；
- 冷档案：需要核查时可以返回的完整原文与轨迹。

推荐的数据流是：

```text
原始事件时间线（权威）
        ↓
存档点与状态快照
        ↓
分层摘要与可重建索引
        ↓
按世界线、人物、场景、任务和因果关系检索
        ↓
上下文披露系统按权限与预算过滤
        ↓
注入本轮 Agent
```

摘要不能替代原始历史，向量索引也不能成为第二份真相。摘要和索引应保留来源事件、世界线、时间、知情者和可信度，以便发现冲突后回到原始记录核查，并允许压缩算法或检索模型升级后重新构建。

连续性系统负责找到可能相关的信息；披露系统负责判断当前 Agent 是否应该看到。两者不能合并成一次不受约束的 RAG 注入。

## 六、MVU 应升级为状态、事件与效果事务

当前 DSH 的叙事优先链路是：

```text
第 N 轮正文
  → 后台理解正文并结算变量
  → 提交第 N 轮派生状态
  → 状态通过确定性规则或世界书投影进入未来上下文
  → 影响第 N+1 轮正文
```

这不是完全切断状态对正文的影响，而是放弃正文与变量的即时双向绑定。状态不反向修改已经生成的正文，只通过明确的上下文投影影响后续游戏。它减少了正文、MVU、浏览器脚本和 UI 互相回写造成的循环、竞争和半提交。

但在完整 LLM 游戏中，正文不能成为唯一状态来源。购买、移动、装备、战斗、定时事件和后台世界模拟，都可能在没有先生成正文的情况下改变游戏状态。

因此，原生状态系统应允许多个受控事件源：

- 正文后的状态提取；
- 玩家从 UI 发出的结构化命令；
- 确定性规则；
- 后台世界模拟；
- Agent 的工具调用；
- 系统时间与调度事件。

所有来源最终都必须生成经过 Schema、权限、世界线和 revision 校验的 **State Effect**，再由运行时原子提交。Agent 只能提出效果，不能直接改写权威存储。

状态还应分为：

- **硬状态**：金钱、生命值、库存、位置、时间、任务阶段等，通常由程序先裁决；
- **软状态**：情绪、怀疑、关系倾向和氛围等，可以在正文完成后由 LLM 提取；
- **派生状态**：负重、关系等级、可用技能和条件判断等，由程序计算，不由 Agent 重复写入。

状态进入正文上下文时也采用混合供给：当前时间、地点、出场人物和重大事实等小型状态由程序固定 Push；交易、战斗和任务等本轮高相关状态按条件 Push；背包、完整关系、远处地点和其他长尾状态由 Agent 自主 Pull；权限、其他世界线和正文 Agent 无权知道的状态保持 Host Only。程序 Push 的是有界语义投影，不是完整变量账本；所有 Push、Pull 与行动检查必须读取同一个 branch、revision 和 checkpoint。

由此形成两种合法的运行顺序：

```text
叙事优先：玩家输入 → 正文 → 提取 Effect → 提交状态
规则优先：玩家意图 → 规则裁决 → 提交状态 → 正文表现结果
```

当前 MVU 可以继续作为 Narrative Effect Extractor：它是从正文提取状态变化的一种兼容协议，而不是未来整个状态系统的名称。

变量上下文的详细分层和工具边界见[《Agent 自主上下文》](agent-owned-context.md#变量不必整表回灌)。

## 七、预设与脚本应回到各自的职责

预设混合了文风、角色扮演规则、请求顺序、输出格式、状态协议和第三方模型适配。原生游戏应把它拆成明确资源：

- 作品的叙事策略；
- 作者的文风与内容边界；
- Agent 的职责、权限和工具；
- 上下文编译策略；
- 模型路由和采样策略；
- 兼容外部模型的 Adapter。

玩家可以切换表现风格，但不能因为换了外部预设就静默改变游戏规则、Agent 权限或状态协议。

正则、EJS 和 Helper 脚本则证明创作者需要程序能力。原生平台应提供正式的事件、命令、状态、存储、资源和 UI API，并在沙箱中按能力授权。无法预先翻译的动态脚本可以继续使用兼容层，但兼容 API 不应成为新游戏的首选开发接口。

## 八、原生 LLM 游戏运行循环

上述系统可以组成一个统一循环：

```text
玩家输入或 UI Command
        ↓
识别 Intent
        ↓
规则、Agent 或混合裁决
        ↓
生成经过验证的 Event / State Effect
        ↓
原子提交并形成新 Checkpoint
        ↓
更新人物、世界状态、记忆与 View Projection
        ↓
上下文披露系统为相关 Agent 分配知识与注意力
        ↓
正文、NPC 行动、后台模拟或界面反馈
        ↓
进入下一次循环
```

这个循环必须满足：

1. 历史和世界线具有唯一权威来源；
2. Agent 是内容与意图的生产者，不是最终状态权威；
3. 所有写入带有分支、revision、operation 和权限；
4. 失败不会留下半轮正文、半份状态或幽灵任务；
5. 摘要、索引、状态栏和 Session Surface 都可以从权威记录重建；
6. 模型、检索器、UI 和兼容 Adapter 可以替换，游戏作品仍然成立。

## 九、制作与游玩必须共享同一格式

完整平台包含两个面对不同用户的产品，但它们必须由同一份游戏格式连接。

### AI Game Studio

面向创作者：

- 通过访谈描述游戏设想；
- 用 Agent 创建和维护人物集、世界知识、规则、场景和 UI；
- 用自然语言修改结构化资源；
- 模拟事件和状态变化；
- 检查角色越权、剧透、状态冲突和不可达任务；
- 比较模型或规则版本变化后的行为；
- 发布游戏版本并迁移旧存档。

### AI Game Runtime

面向玩家：

- 启动经过验证的完整游戏包；
- 管理 Agent、状态、事件、存档、分支和回放；
- 运行正文、UI、世界模拟与后台任务；
- 管理模型成本、失败恢复和权限；
- 在桌面、移动端及其他宿主中保持一致世界语义。

制作工具不能生成一套只有编辑器自己理解的隐式配置；运行时也不能要求玩家重新完成作者已经做过的系统集成。

## 十、原生游戏包是运行制品

未来的游戏包可以围绕以下结构组织：

```text
game/
├── game.yaml
├── actors/
├── world/
├── scenes/
├── quests/
├── state/
│   ├── schema.json
│   └── initial.json
├── rules/
├── agents/
├── views/
├── assets/
├── migrations/
└── tests/
```

这只是候选组织方式，不应在领域模型稳定前过早冻结为标准。真正必须先确定的是包的行为契约：资源所有权、能力声明、版本、权限、状态迁移、测试和可复现启动。

一份游戏包应同时是：

- 内容单元；
- 运行单元；
- 配置单元；
- 权限单元；
- 版本与迁移单元；
- 测试与发布单元。

人物卡、世界书、预设、正则和脚本可以无损保留为源资产，经翻译后生成原生产物。作者也可以跳过酒馆格式，直接制作原生游戏。

## 十一、兼容生态，但不让生态决定架构

兼容仍然具有战略价值：它降低用户迁移成本，为 DSH 提供内容存量，也让原生设计能够接受大量真实资源的检验。

推荐边界是：

```text
酒馆原始资源
  → 无损保存
  → 解析真实依赖和运行语义
  → 翻译为原生中间表示
  → 报告准确迁移、推断迁移、兼容运行和暂不支持的能力
  → 由 DSH 原生运行时执行
```

只有无法静态理解的动态脚本保留运行时兼容 Adapter。兼容实现追求对现有资产的可观察行为一致；原生实现追求清晰的状态、事务、权限与生命周期。两者不能共享一团模糊的内部模型。

DSH 也不需要亲自复刻每一种社区手机、数据库或状态栏。平台需要提供稳定宿主协议，让这些资产能够安全运行；原生作者则使用统一的游戏能力构建自己的体验。

## 十二、需要避免的几个误区

### 不是把所有内容都结构化

小说正文仍然是情绪、语气、动作细节和关系张力最丰富的记录。只有未来规则、检索、界面或程序真正需要消费的信息，才进入结构化状态。

### 不是每个 NPC 一个 Agent

人物是领域实体，Agent 是按需分配的执行能力。是否独立运行取决于质量、隔离、成本和时效要求。

### 不是让 Agent 直接管理数据库

Agent 提交 Intent 或 Effect；Host 校验并提交。模型生成成功不等于游戏事务成功。

### 不是一个万能聊天界面

正文只是一个 View。地图、手机、经营、战斗和调查等玩法需要正式 UI，但共享同一套世界状态和命令协议。

### 不是先设计包罗万象的标准

格式应由不同游戏验证后逐步稳定，而不是先为想象中的全部玩法设计数百个字段。

## 十三、验证原生模型的样板游戏

至少应使用三种差异足够大的游戏检验抽象：

1. **人物关系叙事游戏**：重点验证人物集、个人记忆、软状态和长程情感连续性；
2. **调查解谜游戏**：重点验证客观事实、角色知识、防剧透、证据与分支；
3. **经营或生存模拟游戏**：重点验证硬状态、程序规则、时间推进、后台模拟和复杂 UI。

如果同一套领域模型可以支持三者，而不要求用提示词或脚本绕过核心协议，才说明抽象足够稳固。

## 十四、建议的演进路线

### 阶段一：形成统一领域语言

先稳定 Checkpoint、Timeline、Cast、Knowledge、Disclosure、Intent、Event、Effect、View 和 Continuity 等概念，避免继续用历史实现名词描述未来能力。

### 阶段二：建立原生中间表示

让现有人物卡、世界书、MVU、数据库、正则和脚本先投影到同一套内部模型，同时保持当前兼容体验。

### 阶段三：制作第一款原生样板游戏

不再以“这张人物卡能不能运行”为验收，而以“一个完整游戏能否下载、启动、长期游玩、存档、回放和升级”为验收。

### 阶段四：建设 AI 制作闭环

让创作者通过 Agent 创建、修改、测试、诊断和发布原生游戏包，而不是手工拼装提示词、正则与插件依赖。

### 阶段五：形成开放格式与生态

在多个真实作品验证后，再稳定公开格式、SDK、能力声明和发布规范，使模型提供商、UI 作者、游戏作者和工具开发者可以围绕同一运行协议协作。

## 结论

酒馆生态最重要的价值，不只是已经积累了大量人物卡，而是它在平台能力不足的条件下，提前探索了 LLM 游戏需要什么。

从原生 LLM 游戏角度重新解释以后：

```text
Swipe       → 存档点与世界线
人物卡      → 人物集与角色社会
世界书      → 知识与上下文披露
状态栏/手机 → 游戏 View 与应用
数据库      → 世界连续性与记忆
MVU         → 状态、事件与效果事务
预设        → 叙事策略与 Agent 编排
脚本/正则   → 受控程序能力与兼容 Adapter
```

DSH 的长期机会不是成为另一个更兼容的酒馆，而是成为一种新的游戏运行基础：由程序维护世界事实和事务，由 Agent 理解意图、塑造人物和生成叙事，由上下文系统调度有限注意力，由 View 系统承载真正的游戏交互，并让作品能够被制作、测试、发布、存档和长期运行。

> 酒馆生态是原始需求库和迁移入口；原生 LLM 游戏运行时才是目标产品。
