# 聊天存档：复用两个数据槽的实验

**仅供设计评审，不接入应用。** 提交候选只包含 A/B 槽实验和合成测试，不包含第一版分段原型的存储入口或迁移写入器。 现行原生聊天存档（格式 1、2）已能只写改动。格式 2 把小块放进同一个包，但每块仍要有自己的文件名，读取时靠这个名字找到包；支持硬链接的磁盘只存一份字节，不保留硬链接的备份会按名字重复复制。这不是备份造出来的问题：备份只是把原本就有的许多文件名放大成许多份字节。只取消块的名字、继续每次保存另起一个包，文件数也还是会跟着保存次数涨。

## 第一版分段原型

第一版原型让每份聊天存档只用少量分段文件。一次保存的新增块接着写进当前段，普通段按字节装满才换下一段；超大块可以独占一段。已经存过的块继续凭内容指纹复用，不改块内容和引用。每段是一份数据和一份索引，索引记「这个块从哪里读、多长」，块本身不再占文件名。楼层分页、正文候选、世界状态、历史版本和 `.dshsave` 导入导出都不改。

索引和数据一起追加，不在每次保存时重写索引。当前段的索引有大小上限，已缓存时只补读新增部分；封好的段可用按内容指纹查找的索引及由它派生的快速筛选，不逐段读完索引才找到一个块。打开最近几层只读所需的块，附近的块共用一次读取，沿用现有缓存和并发合并。段大小以实测决定，不能靠调大段把成本转到冷读或备份。

后台按现有规则保留回退、撤销和恢复用的版本；累积了足够多的废弃字节再合并稀疏段，只搬仍有用的块。先写好替换段，再核对当前入口仍是整理开始时那一个，最后切换；有并发保存就不能用旧结果盖掉它。旧段直到新入口已经可靠落盘、使用旧段的读取结束后才回收，不能只按文件年龄猜。平时只在段满时增加一对文件；整理回收后，文件数跟**还要保留的内容和历史有多大**走，不跟保存次数走。若保留了更多历史，存档当然可以变大。

## 写到一半怎么办

当前验证的替代方案采用两个可反复使用的文件与一份提交清单。文件头带校验过的代号，逻辑段可以在文件内换段，不靠新文件名发布。普通保存只追加到当前文件并同步，再把带校验的提交记录追加到清单并同步；成功返回以清单同步完成为界。记录注明有效文件、代号和已提交边界，读者按提交次序核验文件代号、边界与校验，不把部分写入或被复用文件里的旧代号当成有效版本。

后台整理在另一份文件里写出保留内容并同步，不占前台写锁；若前台已经保存，整理在锁外校验、补写已提交的增量，最后仍要核对入口没有再变化。核对失败就保留前台版本。源文件只在不再被已固定版本的读者使用后复用。单纯反复写已知落盘的文件，才能避免成功返回的保存依赖一个可能在断电后消失的文件名。

普通保存仍只追加清单。后台可把当前提交复制到清单的固定区，做两份校验副本并同步；如果入口未改变，才在提交锁内截掉旧追加区并同步。前台若已提交新版本，保留追加区。重开按提交序号选有效入口，不能仅按物理顺序选断电后残留的旧记录。

首次建档及旧档迁移另验：先建两份文件并分别同步，迁移还要把读回的新内容与源对照，最后才写入并同步第一条提交记录。原先的布局在发布验证完成前保留。Windows 文件同步无法单独证明三个新名字的目录项都已持久；测试需要覆盖同步后仍丢失任一名字的情况。这个边界未验证前，不启用新布局，也不回收源文件。

## 旧档怎么升级、怎么退回

选**逐档、可回滚的一次性升级**，不在载入或普通保存时搬整档。新版照读旧原生块、日志快照和兼容增量树；未转换的聊天在新版只读，保存时明确提示先升级。升级在现有存档写锁内锁定源版本，在旁边生成分段文件，按现有读取器可读的版本核对当前内容和保留历史，再切换入口。原生旧档保留块引用和快照身份；日志和增量树转换也保留可读版本的内容，不只搬最新一版。原型目前还没接好这一条旧日志迁移路径。

分段模块独占新版格式的编解码，普通聊天的新建、升级和后续保存都走同一个写入器；旧格式只读，旧写入器只供明确的离线降级使用，不双写。人物卡草稿不在本次范围。旧版看到新版号必须明确拒绝，不能绕到残留的旧日志继续写。

先在复制档上演练；正式升级是另一步，要先提醒备份并确认可恢复，不能随程序更新自动迁移真实存档。尚无新进度时可恢复经核对的旧备份；已有新进度则先离线把当前档及保留历史转成旧版能读的布局、验证后再切回旧版，不以恢复旧备份丢掉这段进度。迁移保留的旧文件只有在验证并确认备份可恢复后才能清理；文件数验收要单列迁移期间保留的旧文件和整理后的实际数量。

## 原型支持这个方向，但还不能启用

第一版分段原型证明单批追加、按范围校验和保留块引用可行，但它仍用改名发布，每次物理换段还会创建文件。A/B 试验把清单、楼层索引、完整聊天头部和历史核验接到了一起，尚未接入应用。最新快照放在活动文件首部；更早版本用反向差量保存，日常保存仍追加正向差量。再次整理只转换尚未整理的正向差量。最近楼层可按偏移定位并按楼解析；但重开仍核验整个活动文件的字节，两者不是一回事。

实验只用两个数据槽和清单：追加不新建文件，整理复用另一槽。测试在不同保存次数下核对恢复结果和文件数，不能据此宣称应用存档已改。长期每档不应超过旧版空间，整理可在预算内临时超出；可用空间查询不是操作系统预留。最近楼层的存储路径并非对所有档都达到旧耗时的 2/3，应用层打开、渲染和单楼保存尚未验收。

### 最近楼层的隔离验证

按范围校验的原型仍使用两个槽和一份清单。清单校验覆盖代号、已提交边界、快照原始长度及正向增量起点。快照分成连续校验页，每页的校验绑定代号和页号。楼层索引、楼层帧经过校验页读取；正向增量整帧校验并绑定代号和槽内位置，历史反向增量不参与最近楼层的读取。遇到窗口无法表达的更改时，回到同一个已选提交做全量校验，不换成更旧的窗口值。

没有采用为加快重放而额外写入完整楼层的检查点策略：它只改善特定编辑的读取，却会把该次增量写入放大数十倍。普通保存仍只追加增量。

部分读取只承诺返回的投影，不为未读范围背书。全档恢复、迁移核对和回收前的验证须覆盖完整记录；同一个部分读取接口后来碰到坏页也必须报错。测试分别回放了窗口外的页损坏、窗口内的页或已提交增量损坏、清单损坏、未发布增量和读取中途换代。代码仅在实验路径，还不接正式入口，不授权跨进程回收。

### 接入前先解决写入所有权

两份写入器从同一清单打开时，原型各自缓存同一个写入位置。实盘临时目录实验中，第一份写入器确认保存 `first` 后，第二份旧写入器把它覆盖为 `other`，重开只见后者。单实例排序、文件同步和校验都不能保护这种交错。

建议先在隔离的应用适配验证中，复用现有每档写锁，让写入、入口发布和检查点截断使用同一份权限；拿到锁后先核对当前入口与预期版本，失配就拒绝写入，不能覆盖。构建候选槽不能长期持有前台写锁。跨实例读者的固定版本和后台回收另立判据：进程内读者计数不能作为清理依据。至少用两个独立进程验证旧写入器拒写、前台保存不被整理阻塞、旧读者退出之前不会复用其数据。是否复用这把锁、哪些调用者必须参与，以及如何给固定版本的读者保留数据，接入前需要评审；暂不接触正式入口。

## 通过什么才启用

- 同一大档对照旧版，测连续增量写入、偶尔换段的耗时、冷开最近楼层、翻页和全档读取；比较耗时及实际读写字节。小改动不得读取或重写整档，写入及读取不能有可复现的性能回退。用相近的保留内容、不同的保存次数对照整理后的文件数。
- 模拟数据、索引、发布及整理各处中断，证明重开只见完整版本，成功保存的版本不会丢；旧格式读出、正向升级和有新进度的反向转换都逐条比对正文、候选、世界状态、保留历史与回退点。
- 只在调试槽用复制出来的真实存档演练，报告升级前后的文件数和大小。同一实现面向上游桌面、命令行和安卓，不引入新依赖或本机特例；真实存档不作为上游测试夹具。
