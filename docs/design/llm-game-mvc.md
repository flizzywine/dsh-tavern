# LLM 游戏的 MVC 架构备忘

## 目标

用一个简单、统一的模型解释 LLM 游戏中的正文、变量、UI 和玩家操作，避免它们各自成为一套互相争夺真相的系统。

## 核心定义

### Model（M）：叙事世界

正文及其历史是游戏的 Model，代表已经在游戏世界中发生的事情。

变量 M' 不是另一个权威世界，而是从 M 中提取的结构化投影：

```text
M（完整正文世界）
  │
  │ 有损提取
  ▼
M'（变量、索引、摘要、UI 数据）
```

M' 用于快速展示、检索和提供紧凑上下文。它可以重新结算；当 M 与 M' 冲突时，以 M 为准。

### View（V）：游戏的表现

View 包括正文界面、状态栏、手机、地图、商店和人物关系等 UI。

正文的内容属于 Model；正文如何排版、展示和交互属于 View。View 可以读取 M 和 M'，但不直接改写它们。

### Controller（C）：Intent 与 Agent 编排

Controller 将玩家的自然语言输入、UI 点击和候选项选择统一为 Intent，并协调正文 Agent 推动叙事。

```text
自然语言输入 ─┐
UI 操作      ─┼→ Intent → 正文 Agent → M
候选项选择   ─┘
```

Controller 负责意图标准化、上下文准备、Agent 调用、正文提交及投影调度，但不绕过正文直接把变量写成新的世界事实。

## 单向循环

```text
玩家输入或 UI 操作
          ↓
C：生成并执行 Intent
          ↓
正文 Agent 推动叙事
          ↓
M：提交新正文
          ↓
状态结算：M → M'
          ↓
V：刷新正文与其他 UI
```

例如玩家在商店点击“购买长剑”，View 只提交购买 Intent。正文 Agent 根据金钱、商人和剧情决定交易、议价、赊账或拒绝实际如何发生，并把结果写入正文。结算系统再从正文提取金钱和物品变化，最后刷新商店和背包 UI。

## 边界规则

1. View 只展示状态和发出 Intent，不直接修改 M 或 M'。
2. Controller 通过正文 Agent 推动 M，不跳过 M 把 M' 当成新剧情。
3. M' 是可重建的有损投影，不反过来约束 M 只能发生某种结果。
4. 同一个意图无论来自文本还是 UI，都走同一条 Controller 链路。
5. 只存在于手机记录、插件数据等非正文介质中的事实，应作为独立原始事件保存，而不是偷偷写入 M'。

## 一句话总结

> DSH Tavern 采用叙事型 MVC：正文历史是 Model，游戏界面是 View，Intent 与 Agent 编排构成 Controller；变量 M' 是 Model 的可重建、有损投影。
