# Agent 自主上下文：从“喂给模型”到“模型自己寻找”

> 状态：核心架构备忘。本文记录 DSH 相比传统酒馆上下文拼装路线的一项根本优势，并约束未来历史、世界知识、人物资料和状态查询能力的设计方向。

## 一句话结论

> 传统上下文工程替模型选择资料；Agent 上下文工程让 Agent 有能力为当前任务构建自己的上下文。

这不是关键词召回换成向量召回，也不是把上下文窗口从十万扩大到一百万，而是 Agent 获得了参与上下文选择的能力。它不要求程序放弃上下文组装，而是让程序的确定性 Push 与 Agent 的自主 Pull 可以同时存在。

## 不是放弃程序组装上下文

程序组装上下文具有不可替代的优势：

1. **可控、可调试**：相同输入和状态产生相同投影，可以解释命中条件、顺序、预算和遗漏原因；
2. **速度快**：本地关键词、条件和索引匹配通常只需要毫秒；
3. **不增加模型调用**：无需 Agent 发起工具调用、等待结果后再继续推理；
4. **成本低**：除已有正文请求外，不新增模型 Token 和调用费用；
5. **不会忘记**：不可遗漏的小型上下文可以由程序保证提供。

Agent 检索也不是免费的。即使搜索本身在本地执行，Agent 决定调用工具、接收结果并继续生成，仍可能增加模型往返、Token、延迟和行为不确定性。

因此，原生 Agent 架构追求的不是“所有上下文都必须由 Agent 自己找”，而是：

> 程序负责高确定性、低成本、不可遗漏的上下文；Agent 负责开放、长尾、难以预判的上下文。

这种组合称为 **Hybrid Context Supply（混合上下文供给）**。

## 酒馆为什么必须“喂给模型”

经典酒馆以单次文本生成为核心：

```text
玩家输入
  → 宿主预测本轮需要什么
  → 拼装人物卡、世界书、变量、摘要、历史和预设
  → 调用模型
  → 模型一次性生成最终正文
```

模型开始生成后，通常不能暂停并表示“我需要先查一下二百轮前的承诺”或者“我还需要了解这座城市的法律”。如果宿主没有提前把正确资料塞进去，模型只能遗忘、猜测或编造。

因此，酒馆生态围绕“怎样在调用模型前准备足够好的上下文”发展出大量方案：

- 滑动窗口和固定轮数历史；
- 大总结、阶段总结与递归摘要；
- 世界书关键词、递归扫描、注入位置和深度；
- 向量数据库和语义召回；
- 状态表、变量摘要和人物关系摘要；
- 把检索结果、总结和变量重新拼入每轮 Prompt。

这些方案不是没有价值。它们是在被动模型调用架构中，对有限上下文和长期失忆问题的必要补偿。问题在于，无论召回算法多复杂，最终仍然由宿主在任务开始前猜测：模型接下来会需要什么。

## Agent 改变了什么

Agent 不是一次性补全文本，而是可以在任务过程中反复观察和行动：

```text
玩家输入
  → Agent 理解当前任务
  → 发现信息缺口
  → 搜索历史或世界知识
  → 阅读少量命中资料
  → 查询当前状态
  → 必要时继续追查和核实
  → 生成最终正文
```

Agent 不要求宿主在开始前完全知道它将如何推理。宿主既可以提供高置信、低成本的确定性投影，也需要建设一个完整、可发现、可读取、受权限约束的信息环境，让 Agent 在预取不足时继续寻找。

因此，Agent 的上下文不是预先拼好的静态 Prompt，而是 Agent 在完成当前任务期间逐步建立的 **Context Workspace（上下文工作集）**。

## 上下文工程的对象已经改变

传统上下文工程关注：

- 哪些内容应该注入；
- 注入在什么位置；
- 关键词如何触发；
- 摘要保留多少；
- 超过 Token 预算时删除什么；
- 如何替模型猜测本轮相关资料。

Agent 上下文工程应关注：

- Agent 可以发现哪些信息源；
- 搜索、读取、查询和核实工具如何设计；
- Agent 如何知道什么时候应该使用工具；
- 搜索结果如何先返回目录，再逐步展开原文；
- 不同 Agent 拥有什么知识权限；
- 结果是否带有来源、版本、时间和世界线；
- 本轮资料何时退出上下文工作集；
- 不可违反的约束如何由 Host 强制执行。

设计目标从“制造一份尽可能完整的 Prompt”变成“先提供便宜、确定的最小充分投影，再让 Agent 在可探索的信息环境中补足长尾需求”。

## 历史失忆：一个检索工具改变了问题形态

传统路线面对长程历史时，通常尝试把历史压缩到可以继续注入：

```text
完整历史
  → 分段总结
  → 大总结
  → 人物摘要、事件摘要或数据库记录
  → 每轮选择一部分重新喂给模型
```

每次压缩都会损失细节，每次自动召回都可能选错资料；摘要还可能逐渐把模型的误解固化成新的“事实”。上下文越长，系统越需要猜测哪些内容值得保留。

DSH 的 Agent 路线把问题改写为：

```text
完整保存已经提交的剧情历史
  → 提供搜索入口
  → 先返回少量命中目录
  → Agent 选择需要的轮次
  → 再读取附近完整原文
```

模型不需要每轮携带整个过去。它只在当前情节真正涉及某个人、地点、承诺或事件时，自主检索相关证据。

一个简单的检索工具之所以能够解决大量复杂方案试图解决的问题，不是因为字符串搜索天然优于摘要或数据库，而是因为它利用了 Agent 的任务理解能力：

> 系统不再负责预测未来问题，Agent 在已经知道当前问题后自己寻找答案。

这是架构优势，不是某一种检索算法的优势。

## 总结、压缩和数据库仍然有价值

Agent 自主检索不意味着删除总结、压缩和数据库。它们的身份需要改变。

### 错误身份

```text
摘要或数据库
  → 被宿主认定为本轮必需上下文
  → 自动注入每次模型请求
  → 逐渐成为原始历史之外的第二份权威
```

### 正确身份

```text
完整原始历史（权威）
  ↓
摘要、索引和数据库投影（可重建）
  ↓
Agent 搜索和发现候选资料
  ↓
需要时返回原始证据或精确状态
```

摘要可以帮助 Agent 快速浏览章节，数据库可以提供结构化过滤，向量索引可以发现语义相关内容，压缩可以降低长期 Session 的维护成本；但它们都不应该未经 Agent 选择便长期占用正文上下文，也不能取代产生它们的原始记录。

## 从历史检索推广到整个游戏世界

历史检索只是第一个证明。相同模型可以覆盖所有大型信息源：

| 信息源 | Agent 需要回答的问题 | 原生能力 |
|---|---|---|
| 剧情时间线 | 过去实际发生过什么 | 搜索历史、读取原文 |
| 世界知识 | 这个世界原本如何运作 | 搜索知识、展开条目 |
| 人物集 | 这个人是谁、与谁有关 | 搜索人物、读取档案 |
| 当前状态 | 世界此刻是什么样 | 查询状态、读取字段 |
| 游戏规则 | 这个行动是否允许 | 查找规则、检查行动 |
| 资源与文件 | 是否存在相关图片、剧本或资料 | 搜索资源、读取内容 |

人物卡、世界书、数据库和变量不再主要是等待拼入 Prompt 的文本片段，而是 Agent 工作环境中的不同数据源。

原生 Agent 可以拥有一组稳定工具：

```text
recall_history
search_world_knowledge
inspect_character
query_game_state
check_game_action
read_game_resource
```

具体实现可以合并为少数深接口，但工具结果必须标明来源类型。历史证据、作者设定、人物认知和当前变量具有不同权威含义，不能混成没有来源的一段“补充上下文”。

## 世界书主动注入也是经验证的性能选择

酒馆世界书通过关键词、常驻、概率、顺序和深度主动注入，是单次生成架构下的合理方案。DSH 为兼容现有资源，可以继续复刻这种可观察语义。

DSH 曾尝试让 Agent 自主检索世界书，但真实使用中增加了明显等待：正文 Agent 需要先决定检索、发起工具调用、读取结果，再继续生成。世界书条目又具有成熟的关键词和常驻规则，大量普通回合可以由本地程序以很低成本、高确定性直接选中。因此，项目恢复了程序匹配与主动注入。

这次取舍说明，Agent 自主检索不是所有资料源的默认答案。世界书当前采用程序注入，不只是兼容历史格式，也是对速度、费用、可调试性和命中稳定性的产品选择。

原生知识系统仍应保留 Agent 检索能力，作为程序预取的补充：

1. 程序先按常驻、关键词、场景、人物和状态条件确定性预取高置信条目；
2. Agent 阅读预取结果并开始处理任务；
3. 如果信息不足或当前问题超出关键词表达能力，再搜索完整世界知识；
4. 搜索先返回短目录，由 Agent 选择少数条目展开；
5. 在需要核实时回到来源，而不是依赖无来源摘要。

传统世界书的关键词、分组、优先级和常驻字段可以继续驱动快速预取，也可以成为 Agent 搜索时的索引元数据。程序预取是快速路径，不应成为知识上限；Agent 检索是长尾补充，不应让简单回合平白增加模型往返。

## 变量不必整表回灌

变量同样可能非常庞大，但又比一般知识更直接地约束当前世界。它不适合全量回灌，也不适合全部等待 Agent 自主查询。原生变量采用 **State Context Policy（状态上下文策略）**，把状态分为固定 Push、条件 Push、Agent Pull 与 Host Only 四层。

### 固定 Push：当前场景的最小状态

每轮都需要、体积很小、遗漏后容易造成直接矛盾的状态，由程序确定性投影：

- 当前时间和地点；
- 当前出场人物；
- 玩家当前身份；
- 当前主要任务或场景目标；
- 已经确定的重大状态，例如人物死亡。

Push 的内容应优先采用自然语言语义，而不是暴露内部字段和值：

```text
当前是深夜，玩家位于城西药店，店主陈哥在场。
王夫人已经死亡，不得作为当前活动人物出现。
```

### 条件 Push：本轮高相关状态

只有当前输入、场景或行为满足确定性条件时才投影：

- 出现购买意图时提供交易协议和必须检查的约束；
- 进入战斗时提供本轮已经裁决的战斗结果；
- 讨论某项任务时提供当前阶段的语义摘要；
- 进入特殊地点时提供不可遗漏的环境状态；
- 关系跨越明确阶段时提供人物行为边界，而不是原始好感数字。

条件 Push 与世界书快速预取相同：程序免费计算、行为可复现、来源可以调试，但结果必须有界，不能借“相关”之名重新注入整张状态表。

### Agent Pull：长尾状态

大量低频、只有特定任务需要的状态由 Agent 按需查询：

- 完整背包、金钱和物品属性；
- 全部任务和远处地点状态；
- NPC 的详细关系与个人记忆；
- 组织、经济、天气和后台模拟数据；
- 某项复杂行动涉及的多个状态条件。

Agent 可以先搜索状态目录，再读取少量字段；对于购买、战斗和移动等明确领域行为，优先调用更高层的行动检查，而不是让 Agent 自己读取多个字段后计算：

```text
search_game_state("与购买治疗药水有关的状态")
query_game_state("玩家当前持有的钥匙")
check_game_action(type: "purchase", item: "healing_potion")
```

系统返回本轮需要的精确事实或裁决结果，而不是要求 Agent 理解整套任意变量 Schema。

### Host Only：不向正文 Agent 暴露

安全权限、其他世界线、内部 operation、隐藏随机种子、防作弊数据和正文 Agent 无权得知的秘密，不进入 Push，也不能通过通用查询工具读取。它们只供 Host、规则系统或具有明确权限的 Agent 使用。

### Push 语义，不 Push 账本

例如关系状态是：

```yaml
trust: 72
fear: 8
resentment: 31
```

程序可以投影为：

> 她目前信任玩家，愿意透露部分私人信息；她并不畏惧玩家，但仍对上次的争执心存芥蒂。

原始数值继续供 UI、确定性规则和按需查询使用。数字表达出来的游戏意义可以进入正文上下文，整份内部账本不进入。

### 所有状态必须来自同一个存档版本

同一轮中，程序 Push 的状态投影、Agent Pull 的查询结果和行动检查必须绑定同一个 `branch / revision / checkpoint`。查询结果应返回版本；活动世界线或 revision 改变后，旧结果失效，不能让一轮正文同时看到修改前后的两份状态。

变量查询是只读证据；状态写入仍通过受控事件、Effect、权限与 revision 校验完成。Agent 忘记查询购买、攻击、解锁等硬规则时，Host 必须在提交边界拒绝不合法结果。自主获取上下文不等于 Agent 可以自主篡改世界。

变量的混合供给可以概括为：

```text
完整变量状态
  ↓ 状态上下文策略
  ├─ 固定 Push：小型基础状态
  ├─ 条件 Push：本轮高相关状态
  ├─ Agent Pull：长尾状态
  └─ Host Only：内部或受限状态
```

> 程序确定性投影本轮不可遗漏的最小状态，Agent 按需查询其余状态，Host 独立校验所有硬规则。

## Push 与 Pull 的边界

Agent 自主上下文不等于初始上下文完全为空。

上下文供给应当分为三层：

```text
稳定核心
  身份、协议、工具和不变量

确定性投影
  程序按当前输入、场景和状态免费计算的高置信上下文

Agent 工作集
  Agent 为当前任务自主搜索、读取和查询的长尾资料
```

### 系统必须 Push 的最小执行契约

- Agent 身份与当前任务；
- 当前玩家输入和最小场景定位；
- 可用工具及使用条件；
- 权限与安全边界；
- 不可违反的游戏协议；
- 已经裁决、必须遵守的本轮硬结果。

### Agent 应当 Pull 的任务资料

- 久远历史；
- 世界设定；
- 人物详细档案；
- 当前变量；
- 复杂规则；
- 与本轮有关的资源原文。

可以概括为：

> 知识由 Agent 主动获取，约束由系统强制执行。

如果一项内容遗漏后会破坏权限、安全或事务一致性，它就不是等待检索的普通知识，而应成为最小执行契约或 Host 校验。

在 Push 与 Pull 之间选择时，应同时判断：

| 条件 | 优先方式 |
|---|---|
| 相关性明确、内容很小、每轮高频使用 | 程序 Push |
| 已有成熟确定性规则且命中质量稳定 | 程序 Push |
| 遗漏会立即破坏本轮正确性 | 程序 Push 或 Host 强制 |
| 相关性依赖当前任务语义、难以提前预测 | Agent Pull |
| 内容庞大、低频、只有少数回合需要 | Agent Pull |
| 需要连续追查、比较或核实多个来源 | Agent Pull |

程序 Push 和 Agent Pull 都应接受真实延迟、Token、命中率与遗漏率验证，不能只凭架构偏好决定。

## 上下文工作集不能再次无限增长

Agent 调用工具取回资料后，如果工具结果永久留在后续每轮模型上下文中，系统最终仍会回到上下文膨胀问题。

因此，检索结果需要具有明确生命周期：

- 本次任务内可见；
- 执行轨迹保留查询、来源 ID、版本和结果摘要；
- 下一轮不默认重新注入完整内容；
- 需要时由 Agent 再次检索；
- 缓存可以减少 IO，但缓存不等于模型上下文；
- 压缩以后仍能从权威来源重新读取。

Agent 的上下文应该是任务工作集，不是不断复制整个世界的第二个资料库。

## 自主检索需要运行时兜底

这项架构优势不会自动成立。若工具难以发现、结果没有来源或者 Agent 经常忘记检索，它仍会退化成猜测。

运行时至少需要保证：

1. **可发现性**：工具名称和描述让 Agent 知道有哪些资料可以查；
2. **渐进读取**：搜索阶段只返回短目录，读取阶段才返回原文；
3. **最小充分**：单次结果具有数量、长度和范围上限；
4. **权限隔离**：调用者只能读取其角色和任务获准看到的信息；
5. **来源追溯**：结果携带游戏、世界线、revision、条目或轮次标识；
6. **提交态读取**：未完成、已回退和其他世界线的内容不能混入；
7. **强规则兜底**：交易、状态事务、秘密权限等不能只依赖 Agent 自觉；
8. **临时生命周期**：工具正文不会永久污染后续上下文。

## 为什么这是碾压级优势

“碾压级”并不意味着 Agent 每次都一定检索正确，也不意味着主动注入从此毫无价值。它指的是两种架构的扩展方向不同。

被动拼装架构中，每增加一种资料，宿主都要继续增加：

- 召回条件；
- 注入优先级；
- Token 竞争规则；
- 去重和冲突处理；
- 针对未来任务的相关性猜测。

Agent 架构中，每增加一种资料，平台主要增加：

- 一个可靠的数据源；
- 可搜索的索引；
- 读取或查询能力；
- 权限与来源信息。

然后 Agent 根据具体任务组合这些能力。历史、人物、世界知识、状态和规则不需要分别发明一整套自动 Prompt 拼装算法。

这是一种从“宿主替模型思考需要什么”到“模型拥有寻找答案能力”的代际变化。信息规模越大、游戏越复杂、游玩时间越长，这种优势越明显。

## 不可退化原则

未来新增上下文能力时，应首先问：

1. 这是 Agent 无法遗漏的执行契约，还是可以按需寻找的知识？
2. 能否保存完整来源，并提供搜索和读取工具？
3. 为什么必须自动注入，而不能由 Agent 自主检索？
4. 自动注入是否把派生摘要变成第二份权威？
5. 工具结果是否会永久累积，重新制造上下文膨胀？
6. 是否用宿主越来越复杂的猜测，替代了 Agent 已经拥有的任务理解能力？

除非有明确收益，不应建设新的全量回灌、自动摘要注入或复杂 Prompt 拼装链路；同样，如果确定性程序已经能够以更低延迟和成本稳定提供所需上下文，也不应为了形式上的 Agent 自主而强制增加工具调用。

## 验证标准

这项优势需要通过真实长程游玩验证，而不是只凭架构直觉宣称成功：

- 不调用工具时，久远历史和大型资料不进入请求；
- Agent 能根据当前问题主动发起搜索，而不是等待用户提醒；
- 搜索只返回小目录，Agent 能继续读取必要原文；
- 久远承诺、人物关系和事件细节能够从权威原文恢复；
- 更换摘要或索引实现，不会改变已发生剧情；
- 回退和分支以后，Agent 只能检索活动世界线的提交态内容；
- 相比固定注入，同等任务使用更少无关 Token；
- 工具返回的资料不会在后续回合无限累积；
- 查询失败时明确暴露失败，不以模型猜测伪装成成功召回。
- 对高频世界书等资料，程序预取相比 Agent 检索显著降低首字等待与模型调用；
- 程序预取遗漏时，Agent 仍能搜索完整来源，而不是把预取集合当作知识边界。

## 对 DSH 的战略意义

历史检索不应只被视为一个“防失忆功能”。它是 DSH 原生 Agent 游戏架构已经成立的一项证明：

> 平台不需要不断预测 Agent 将需要哪些上下文；平台需要保存完整世界，并让 Agent 有能力发现它。

这条原则应继续推广到人物集、世界知识、变量状态、规则、剧本和游戏资源。对于高频、可预测的资料，DSH 可以继续使用程序投影；对于低频、长尾和难以预判的资料，则把它建设成 Agent 可以探索的世界。

DSH 的核心优势不是比酒馆更会拼 Prompt，也不是完全取消 Prompt 拼装，而是不再被迫只依赖程序预判：程序可以走最快的确定性路径，Agent 也可以在需要时突破预取边界。

> 能确定的由程序快速准备，不能确定的由 Agent 自己寻找。
