# 破限模块测试计划

## 状态

本计划暂缓执行，但恢复测试前必须先完成自动化测试框架。正式适配不再以人工逐轮操作为主。

当前阶段只把预设导入、破甲抽取、文件保存、侧栏选择和全局注入做成功能，不宣称已经解决特定模型、人物卡或内容尺度下的拒绝问题。系统性实测工程量大、变量多，先让位于实现简单但能明显改善酒馆兼容性的工作。未来恢复时，人工只负责定义案例、检查框架无法确定的边界结果和决定下一轮方案，不再手工重复运行测试。

## 测试目标

使用一个固定案例建立可复现的三段基线，再逐项缩小 SillyTavern 与 dsh-tavern 的行为差异：

1. 接入 Gemini 3.7 Flash，使用《东淫航空》复现拒绝、空回复或其他失败表现；
2. 在 SillyTavern 中使用相同模型、人物卡和输入，确认某份预设能够成功完成同一段内容；
3. 将相同人物卡和预设引入 dsh-tavern，抽取破甲提示词并全局注入，反复测试和调整，直到达到约定的通过标准。

这个测试验证的是一条具体兼容链路，不用于证明某个提示词对所有模型和人物卡都有效。

## 自动化是前置条件

模型、人物卡、预设、输入、运行环境和重复次数会迅速形成测试矩阵。人工逐轮创建会话、复制输入、下载日志和整理结果不可持续，也很容易混淆变量。因此，破限适配开始前先建设一个本地自动化测试框架。

框架必须能够：

- 从声明式测试用例创建全新的隔离会话；
- 分别运行无破甲 dsh-tavern、SillyTavern 预设和 dsh-tavern 迁移方案；
- 对同一组合批量重复，控制并发、频率、费用上限和停止条件；
- 保存每次调用的输入、原始输出、错误、注入记录、Session Log 和环境版本；
- 自动区分明确拒绝、空回复、渠道错误、截断、疑似成功和待人工复核；
- 输出机器可读结果和人类可读汇总报告；
- 中断后能够从未完成用例继续，不重复消耗已经完成的调用。

测试框架属于开发与兼容验证基础设施，不进入普通用户的游玩界面，也不在用户会话中自动尝试不同破甲方案。

## 测试框架结构

```text
Test Case Catalog
  └── 模型、人物卡、预设、起点、输入、参数、重复次数
          ↓
Test Runner
  ├── dsh-tavern 无破甲 Adapter
  ├── SillyTavern Adapter
  └── dsh-tavern 破甲方案 Adapter
          ↓
Result Classifier
  ├── 确定性错误与拒绝规则
  ├── 内容完成度 Judge
  └── 待人工复核队列
          ↓
Artifact Store + Markdown/HTML Report
```

### 测试用例

每个用例使用 JSON 或 YAML 描述，至少包含：

```text
id
model.provider
model.name
card.path + hash
preset.path + hash
boundaryPrompt.path + hash
opening
history
userInput
generationConfig
repetitions
expectedFailureBaseline
successCriteria
```

敏感正文可以放在不进入 Git 的本地文件中，用例只保存相对引用和哈希。

### 运行 Adapter

三个 Adapter 对外提供相同接口：

```text
run(testCase, variant)
  -> { request, response, error, logs, runtime, timing, cost }
```

- dsh-tavern Adapter 直接使用稳定的会话与模型接口，不通过浏览器点击完成批量测试；
- SillyTavern Adapter 实施前先研究可用 API、消息装配与扩展行为，优先调用稳定接口；确实没有接口的部分才使用浏览器自动化；
- Adapter 必须导出实际发送给模型的消息或等价审计信息，不能只保存最终页面文本。

### 结果判定

采用分层判定，避免让另一个模型成为唯一裁判：

1. 确定性规则先识别空回复、HTTP 错误、超时、截断和已知明确拒绝文本；
2. 对剩余结果使用固定 Judge 规则判断目标内容是否真正完成、是否回避关键内容以及正文质量是否明显退化；
3. 规则与 Judge 不一致、置信度不足或结果涉及新型拒绝时进入人工复核队列；
4. 人工修正结果可以沉淀为新的确定性规则或 Judge 样本，但不能改写已经保存的原始输出。

每条结果至少使用以下状态之一：

```text
refused | empty | provider_error | truncated | passed | degraded | review
```

### 批量报告

每次运行生成：

- `results.jsonl`：每次调用一行，包含完整变量和判定；
- `summary.json`：按模型、卡片、预设、破甲方案和变体聚合；
- `report.md` 或本地 HTML：成功率、拒绝率、平均耗时、费用、失败分类和与酒馆基线的差异；
- 原始日志目录：按 `runId/caseId/variant/attempt` 保存，不覆盖历史结果。

报告必须能回答：哪个组合有效、重复多少次、失败是什么、与 SillyTavern 还差在哪里，以及结论对应哪个版本和日期。

## 为什么需要独立测试工程

一次拒绝或成功可能同时受以下变量影响：

- 模型的实际版本、提供方和当日审核策略；
- 人物卡版本、世界书、开场白与已经发生的对话；
- 预设条目的内容、角色、顺序、启用状态和条件；
- assistant 预填充、宏、正则、脚本或扩展行为；
- 采样参数、上下文长度、重试方式与空回复处理；
- dsh-tavern 把多条酒馆消息转换为单份系统提示词时发生的语义变化。

因此不能只比较“用了同一段破甲文字没有”。测试必须保留完整环境，并且每轮只改变一个主要变量。

## 固定测试资产

正式开始前建立一个本地测试包，至少保存：

- 《东淫航空》人物卡原文件及文件哈希；
- SillyTavern 预设原文件及文件哈希；
- 能稳定触发拒绝的会话起点、具体输入和前置对话；
- SillyTavern 成功时的条目顺序、角色、启用状态和相关扩展设置；
- 模型名称、提供方、测试日期和生成参数；
- SillyTavern 与 dsh-tavern 的原始回复、错误、空回复和 Session Log；
- dsh-tavern 版本、提交号、抽取后的破甲文件和实际注入记录。

测试包只保存在本地。日志可能含成人内容、API 信息或私人配置，公开反馈前必须脱敏。

## 三段基线

### A. 无破甲失败基线

由 Runner 在 dsh-tavern 中关闭破甲，固定模型、人物卡、上下文和输入，批量确认失败可以重复出现。自动记录明确拒绝、空回复、截断、渠道错误或其他表现。

如果失败无法重复，就先修正测试样本，不进入后续比较。

### B. SillyTavern 成功基线

由 SillyTavern Adapter 使用相同模型、人物卡、上下文和输入，启用目标预设并批量复现成功。完整保存预设组合与运行条件，尤其是消息角色、顺序、预填充、宏和扩展行为。

如果酒馆也无法稳定成功，这份预设不能作为 dsh-tavern 的适配基准。

### C. dsh-tavern 迁移基线

将预设原样导入预设库，通过 `tavern-extract-boundary-prompt` 分析：

1. 哪些条目可以直接转换为全局系统提示词；
2. 哪些条目依赖消息顺序或 assistant 预填充；
3. 哪些内容实际属于文风、格式、正则或脚本；
4. 哪些酒馆运行时语义目前无法无损迁移。

用户确认后保存破甲文件。dsh-tavern Adapter 为隔离测试会话选择并开启该文件，再运行相同批次；不得修改真实游玩会话的开关状态。

## 迭代方法

每个批次只改变一个主要因素，由框架自动记录结果：

1. 先验证抽取内容是否完整、顺序是否正确、是否真的完成全局注入；
2. 再处理角色消息合并造成的语义损失；
3. 然后判断是否需要新增预填充、宏或其他兼容能力；
4. 最后才调整提示词措辞。

失败必须归类为以下一种：

- 模型或渠道仍然拒绝；
- 预设内容抽取错误；
- 酒馆运行时语义没有迁移；
- 注入链路没有生效；
- 成功但正文质量明显下降；
- 结果随机，尚不能稳定复现。

测试矩阵可以同时排队多个单变量批次，但同一个对照组内不要同时改抽取内容、注入位置和生成参数，否则无法判断是哪项变化产生效果。

框架第一版只执行已经列出的候选方案，不让 Agent 自动改写破甲提示词并无限循环测试。自动搜索与自动优化会放大费用、审核风险和错误归因，只有固定评测稳定后才单独设计。

## 通过标准

第一阶段至少满足：

- 无破甲失败基线和 SillyTavern 成功基线都能够稳定复现；
- dsh-tavern 的 Session Log 能确认目标破甲文件已进入实际模型任务；
- 在相同起点的新会话中连续三次完成目标内容，没有拒绝或空回复；
- 正文仍符合人物卡和用户要求，没有因为破甲提示词明显退化；
- 候选项、状态结算和卡片 Agent 等全局注入任务没有出现新的格式或任务偏移；
- 测试结果明确绑定模型、提供方、人物卡、预设和日期，不扩大成通用兼容承诺；
- 批量运行可以暂停、恢复，并在达到调用次数、费用、连续错误或用户取消条件时立即停止。

## 当前延期边界

目前完成并保留以下功能即可：

- 原始预设能够无损导入和阅读；
- Agent 能使用 Skill 提取破甲候选内容；
- 用户确认后能够保存独立 Markdown 方案；
- 侧栏能够选择、开启、关闭并显示注入状态；
- 选中的方案能够注入全部模型任务；
- 日志足以支持未来复现与对照；
- 自动化框架的用例格式、Adapter 接口、结果分类和报告格式已经冻结后，才开始规模化破限适配。

目前不做：

- 不在自动化框架完成前开始《东淫航空》的长期适配循环；
- 不建立大规模模型与人物卡矩阵；
- 不承诺内置方案对 Gemini 3.7 Flash 或其他模型有效；
- 不为了单个案例提前复制 SillyTavern 的完整提示词运行时；
- 不让这项测试阻塞正则展示、预设阅读、导入保真和 UI 精简等高 ROI 兼容工作。

当基础兼容能力稳定，或者真实用户反馈形成足够明确的拒绝案例后，再恢复本计划。
