# 后台任务管线

2026-10-17。目标：把每轮正文写完之后的后台工作统一成一条管线，Tavern 自己的结算项和插件的任务用同一套描述、同一套顺序和开关。**第一阶段只重构，不加功能**：用新结构原样复现现有行为，所有测试和 e2e 不改断言地通过。

起因：Galgame 分支的导演 AI 本质上是一个后台 agent，但现有接口给不了它要的运行方式，作者只好改核心代码。管线理顺之后，再按同一套描述补上缺的能力（见文末「以后」），导演就能作为插件接入。

## 现状

每轮正文提交后，`runSettlementCycle`（`lib/index.js`）依次做四件事：

1. 插件的 `before` 任务（`pluginApi.runSettlementTasks`）。
2. Tavern 的结算 `runSettlement`：准备下一轮世界书 → 开始结算操作 → 按卡选一条路径（MVU 变量 / 什么都不做 / 插件替换 / 普通姿势）→ 提交；过期就重来，失败就记失败。
3. 插件的 `after` 任务（包在一个 `plugin-task` 操作里）。
4. `onSettlementSettled`：唤醒 MVU 对账、预热候选世界书、启动世界书预筛、通知插件 `onTurnSettled`、自动配图。

往结算那一次模型调用里加东西，有两个互不相干的接缝：插件的 `settlementSection` / `settlementTool`（`plugin-api.js` 的 `settlement`），和台词标注的 `castSettlement`（`domain/cast-presentation.js`）。姿势、变量、人物设计的说明和工具则直接写在 `runSettlement` 里。哪些项开着由 `normalizeBackgroundTasks`（姿势、变量；人物设计和台账固定关闭）、全局「对话头像」和每局插件设置分别决定。

## 概念

**管线**：每局每轮一次，按固定阶段运行：

| 阶段 | 内容 | 现有对应 |
|---|---|---|
| 前置任务 | 独立任务，按顺序一个接一个 | 插件 `before` 任务 |
| 主结算 | 一次模型调用，由各「结算项」拼成 | `runSettlement` |
| 后置任务 | 独立任务，按顺序 | 插件 `after` 任务 |
| 收尾 | 不等待、不影响下一轮的后续动作 | `onSettlementSettled` 里的五件事 |

**结算项**：主结算里的一项工作（姿势、变量、台词标注、插件附加的每一项……）。每一项都是独立的对象，可以单独开关、排序、换提示词；默认合在主结算的同一次模型调用里，不多花调用。一项包含：

| 字段 | 含义 |
|---|---|
| `id`、归属 | 例如 `tavern.posture`、`tavern.cast`、`plugin:xxx.anchor` |
| 开关 | 本局是否运行。玩家设置优先；插件可以开关自己的项，也可以开关 Tavern 的项 |
| 顺序 | 这一项的说明在本轮任务里的位置，也是要求模型调用工具的先后（例如台词标注在姿势之前） |
| 要求（提示词） | 写进本轮任务的说明文字，可以被替换 |
| 协议 | Tavern 固定的几句：用哪个工具提交、提交后是否结束本轮。替换提示词不会改掉它，避免插件的提示词把工具约定弄坏 |
| 工具 | 固定在缓存前缀里；本轮能不能调用写在说明里 |
| 必须运行 | 只开了这一项时，结算也要跑 |
| 完成条件 | 例如姿势提交后本轮结束 |
| 运行方式 | 默认「合并」进主结算；以后可选「单独」：自己跑一次调用（多花一次调用，换来不受其他项影响） |

提示词和顺序都写在每轮追加的任务文字里，不在缓存前缀里，所以改它们不会让缓存失效；只有工具定义在前缀里，固定不动。

**触发方式**：结算项分两种触发：

- **每轮自动**：每轮正文写完后跑，合并进主结算（姿势、台词标注、插件附加的说明与工具），或由自己的引擎承载（MVU 变量）。
- **手动**：玩家点了才跑，单独作为一次后台任务、在共用的后台会话里运行（人物设计、游玩台账；插件的 `manualTask` 也是这一类）。

同一项理论上两种触发都可以：以前人物设计、台账都能设成「每轮自动合并进结算」，现在这两个开关固定关闭，只保留手动。

现有的结算项：

| 项 | 触发 | 运行方式 |
|---|---|---|
| 姿势 `tavern.posture` | 每轮自动（可关） | 合并进主结算 |
| 变量 `tavern.variables` | 每轮自动（官方 MVU 卡，可关） | MVU 引擎 |
| 台词标注 `tavern.cast` | 已删除（cast-presentation.md 30/N）：正文模型直接写说话人 | — |
| 人物设计 `tavern.character-design` | 手动 | 单独一次后台任务 |
| 游玩台账 `tavern.ledger` | 手动 | 单独一次后台任务 |
| 插件附加的说明与工具 | 每轮自动 | 合并进主结算 |
| 插件的结算任务 / 手动任务 | 每轮（前置、后置）/ 手动 | 单独运行 |

**谁说了算**：同一项被多方调整时，玩家在本局设置里的选择优先；只有一个插件调整时自动生效；多个插件调整同一项时，要玩家选一个，选好之前用 Tavern 的默认（沿用现有 `replaceSettlement` 的规则）。现有的 `replaceSettlement` 以后就是「替换姿势这一项」的特例。

**结算引擎**：主结算怎么跑。现在有三种，按这个顺序选：

1. MVU：官方 MVU 卡有待结算的变量时。有自己的持久化提交、延后与续跑，原样保留。
2. 插件替换：只替换普通卡的姿势结算，失败退回 Tavern 自己的引擎。
3. 普通：后台 agent 跑一次，工具和说明来自各结算项。

三种引擎都没有要做的事时（所有结算项都关闭），照旧不调用模型、直接提交，让时间线前进。

**独立任务**：自己跑一段流程（可以调用自己的 agent），有名字、标题、所属阶段（前置 / 后置），每局可以单独关、可以调顺序。现有的就是插件的 `settlementTask`。

**任务的归属**：`tavern`（Tavern 自己）或 `plugin:<名字>`。以后加 `card`（人物卡声明的任务），不在这一阶段。

## 第一阶段要保持不变的行为

逐条对照，任何一条变了都算重构失败：

1. 每个后台会话只在建立时登记一次工具列表：Tavern 自己的工具、共享工具、台词标注工具、插件工具（按名字排序），**顺序与现在完全一致**，缓存前缀不变。本轮能调什么在执行时检查。
2. 结算、候选、台账、世界书预筛、人物设计共用每局一个后台会话；生图有自己的会话，但同一局的持久任务在同一个队列里排队。
3. 每局同一时间只有一个运行中的后台操作；结算待办时其他角色启动会得到 `BACKGROUND_BUSY`，世界书预筛例外（被取消而不是阻塞）。
4. 每局只有一个结算作业，重复启动会并入。
5. 下一轮发送前，等整条管线（含前置、后置任务）和手动插件任务结束；世界书预筛被取消而不是等待。
6. 插件任务每个正文版本、每个阶段只跑一次，按「每局顺序 → 插件名 → 任务名」排序；前置任务在结算待办时跑，后置任务在结算结束（完成或失败，不含延后）之后跑；插件出错不影响结算。
7. 插件替换失败退回 Tavern 自己的结算；玩家停止时不退回。
8. 提交过期就重跑；同一状态连续三次过期就中断。
9. 提交都做比较交换检查，停止、回退、编辑之后迟到的结果一律拒绝。
10. MVU 的提交先持久化再延后，续跑复用已准备的结果，不再让模型重新规划。
11. 后台会话的编号在第一次模型回复之前写进存档。
12. 停止或空闲超时会弃用后台会话，不再续用；停止不影响生图和手机。
13. 所有结算项都关闭时仍然提交，不调用模型。
14. 关闭变量结算时回执记为「已跳过」，已经在途的提交照常完成。
15. 收尾动作在整条管线之后、且没有被停止时才运行，顺序不变。
16. 压缩等结算结束后才开始，压缩进行中后台任务不能开始。

## 重构步骤

每一步单独提交，行为不变，相关单测和 e2e 全过（必要时跑全量）。

1. **补齐护栏测试**。对照上面 16 条，给还没有测试覆盖的补上，特别是：
   - 后台会话工具列表的确切顺序；
   - 一轮的阶段顺序（前置 → 主结算 → 后置 → 收尾）；
   - 只开台词标注时结算照样运行；所有项都关时不调用模型但会提交。
2. **结算项注册表**（新文件 `domain/background-pipeline.js`）。把 `castSettlement` 和插件的 `settlement` 两个接缝合成一个：注册表按「Tavern 项在前、插件按名字排序」给出工具、说明、可用名单和调用分发。`background-agent-task.js` 只认这一个接缝。台词标注变成注册表里的一项。
3. **姿势、变量、人物设计变成结算项**。把 `runSettlement` 和 MVU 结算里写死的说明、工具、完成条件，改成从注册表里的各项取，并把每项的文字拆成「要求」和「协议」两部分（第一阶段两部分拼起来和现在逐字一样）。生成的提示词逐字不变（用快照测试对比改动前后的请求）。
4. **引擎选择独立出来**。把 MVU / 什么都不做 / 插件替换 / 普通四条路径从 `runSettlement` 里抽成一个「选引擎、跑引擎」的函数，提交、过期重试、失败处理留在原处。
5. **管线外壳**。`runSettlementCycle` 改成按阶段表运行：前置任务、主结算、后置任务、收尾。插件 `settlementTask` 作为独立任务登记进同一张表，排序和开关仍读每局插件设置。

做完这五步，界面和接口都不变，但内部只剩一套描述：一轮后台做哪些事、按什么顺序、谁提供的。

进度（2026-10-17）：五步都已完成，行为不变。人物设计「每轮自动合并进结算」那一支已被固定关闭、从未执行，删掉了；人物设计和台账作为**手动**结算项定义在 `background-pipeline.js`（要求 + 协议），手动任务从这里取说明，逐字不变。变量仍由 MVU 引擎承载。代码在 `domain/background-pipeline.js`（结算项注册表、姿势项、普通引擎的请求拼装、阶段表）和 `index.js` 的 `runSettlementEngine` / `runSettlementCycle`。

## 以后（不在第一阶段）

管线稳定后，按导演 AI 的需要补能力，都作为独立任务的选项，不另起机制：

- **并行**：不阻塞下一轮，下一轮开始时自动取消（导演、世界推演）。
- **自定义 agent**：自己的系统提示词、只给自己的工具、单独选模型。
- **读正文流**：正文生成过程中拿到增量文本，用于边写边演。
- **插件调整结算项**：开关、排序、替换提示词（只换「要求」，不动「协议」），包括 Tavern 自己的姿势、变量、台词标注；结算项可选「单独」运行。
- **人物卡声明的任务**：卡只能声明「提示词 + 输出格式」，不能带代码，Tavern 负责运行，结果存成每轮数据。
- **统一的任务列表界面**：Tavern 自己的项和插件任务放在一处开关，默认只给开关，顺序收进「高级」。
