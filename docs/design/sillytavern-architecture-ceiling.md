# 酒馆架构的上限

> 状态：方向备忘。用于解释 DSH 游戏卡为什么不能只是继续增强酒馆人物卡兼容。

## 核心结论

SillyTavern 的核心运行模型是组织上下文、发送文本、接收文本和展示文本。它没有原生的 Agent 控制面、结构化工具事务和权威领域状态。

因此，社区只能把本应属于运行时的能力编码进人物卡、世界书、预设、正则、MVU、EJS、Tavern Helper 脚本和 HTML，再要求模型通过一次文本输出同时完成叙事与控制任务。

这不是社区缺少设计能力，而是底层能力决定的架构上限。社区在有限条件下创造出了一套“原始 Agent Runtime”，并提前验证了角色游戏真正需要的能力。

## 社区用文本造出的运行时

| 酒馆能力 | 实际承担的运行时职责 |
|---|---|
| 人物卡 | 角色身份、行为规则和部分控制协议 |
| 世界书 | 动态知识、记忆召回和条件触发 |
| 预设 | 上下文编排、流程控制和输出约束 |
| 正则 | 文本解析、数据提取、上下文变换和展示转换 |
| MVU | 变量、状态与 Patch 协议 |
| EJS、Helper 脚本 | 程序执行、事件响应和工具替代方案 |
| HTML 状态栏 | View 与交互界面 |
| 固定输出格式 | 结构化工具调用的文本模拟 |

这些方案具有很高的创造性。DSH 应把它们视为需求样本和迁移来源，而不是简单视为需要清理的错误格式。

## 控制逻辑为什么会碎片化

酒馆没有一个能够同时管理人物设定、状态、任务、工具和 View 的权威资源。控制逻辑只能寄存在多个可用入口中：

- 人物卡保存状态协议；
- 世界书按关键词补充规则；
- 预设要求模型遵守处理流程；
- 正则从正文恢复结构；
- 脚本接管正则无法完成的行为；
- HTML 再把恢复出的数据变成界面。

同一项能力可能跨越多个资源。例如一个人物状态栏可能同时依赖：人物卡中的字段说明、世界书中的变量定义、预设中的输出顺序、正文尾部的状态文本、显示正则和 HTML 脚本。

这些资源能够组合运行，却没有统一的所有权、Schema、生命周期和失败协议。任何一环发生变化，其他环节只能依赖约定继续工作。

## 一次文本输出承担了过多职责

酒馆通常要求主模型在一轮输出中同时完成：

- 人物扮演与剧情推进；
- 文风和篇幅控制；
- 世界书规则遵循；
- 状态理解与变量结算；
- 状态数据序列化；
- 候选项生成；
- HTML、标签或正则标记输出；
- 为下一轮保存可再次解析的协议文本。

这相当于让小说作者在写正文时，同时完成程序调度、数据库事务、后台日志和前端页面。目标之间一旦竞争，格式、叙事质量或状态一致性必然有一项被牺牲。

模型掉格式只是表面现象。根因是正文同时承担了故事、控制协议、状态传输和 View 数据四种互相冲突的职责。

## 架构上限

在纯文本协议之上继续增加提示词和正则，无法根治以下问题：

1. **没有权威状态**：状态存在于文本中，需要再次解析才能使用。
2. **没有结构化写入**：模型输出错误字段时，缺少 Schema 和原子校验。
3. **没有可靠事务**：正文、状态和 View 无法绑定同一个 branch 与 revision 提交。
4. **没有失败隔离**：一次格式错误可能同时破坏正文、状态和展示。
5. **没有职责隔离**：前台模型既是作者，也是结算器、序列化器和 UI 数据源。
6. **没有统一生命周期**：回退、重新生成和分支切换难以撤销配套状态。
7. **没有统一资源所有权**：逻辑分散在人物卡、预设、世界书和脚本中。

兼容层可以提高酒馆资产的可运行范围，但不能把文本模拟变成真正的 Agent 控制面。

## 分发上限：缺少可运行制品

酒馆生态通常分享的是人物卡、预设、世界书、正则和插件等独立零件，而不是一份经过整体验证、可以直接启动的游戏。

用户获得人物卡后，仍然需要自行完成系统集成：

- 寻找作者使用的预设和世界书；
- 安装特定插件、脚本或前端扩展；
- 调整正则、MVU、EJS 和其他功能开关；
- 复现资源加载顺序、模型选择和参数；
- 通过反复试玩判断缺失的是资源、设置还是模型能力。

创作者真正调试成功的是自己机器上的一套隐式环境，分享出去的却往往只有其中一部分。依赖关系、版本、开关、加载顺序和推荐配置没有成为正式交付内容。

结果是：

- 作者环境能够运行，用户环境无法复现；
- 同一人物卡搭配不同预设时行为完全不同；
- 插件或脚本升级后旧卡静默失效；
- 用户必须重复承担系统集成和兼容性排查；
- “下载、开始游戏”无法成为稳定的产品体验。

这不是单纯的界面问题，而是生态中缺少一个**可运行制品**。完整游戏应同时是：

1. **运行单元**：声明前台、后台、状态、工具和 View；
2. **分发单元**：封装人物卡、预设、世界书、剧本和静态资源；
3. **配置单元**：携带经过验证的默认配置和能力开关；
4. **版本单元**：声明格式版本、依赖版本和迁移规则；
5. **验收单元**：允许创作者按整体运行结果测试和发布。

DSH 游戏卡应承担这个角色。它保存资源与配置的版本快照，配置只作用于自己的 Session，不要求用户修改全局环境。启动时由 DSH 检查模型、权限和运行能力；缺少依赖时明确报告，满足条件后直接创建隔离游戏环境。

理想路径是：

```text
下载游戏卡
  → 检查格式、依赖、模型能力与权限
  → 用户确认必要的外部服务和危险权限
  → 创建隔离、可复现的运行环境
  → 开始游戏
```

模型密钥、付费服务和危险权限不能静默打包，但必须在开局前一次性说明。游戏卡的目标不是把文件放进同一个压缩包，而是把创作者已经调试成功的整套游戏环境变成用户可以下载即玩的可复现制品。

## DSH 的承接方向

DSH 的目标不是继续要求前台模型更严格地执行文本协议，而是把社区已经验证过的能力放回正确的运行层：

```text
故事正文                 → 前台主 Agent
剧情理解、总结和状态判断 → 后台 Agent
变量、候选和 View 提交   → 结构化工具
程序加载与任务调度       → Host
Schema 校验与原子提交    → Host
状态栏与交互界面         → View renderer
下一轮必要状态           → 上下文投影
```

核心原则是：

> 资源一体化，执行分层化。

资源一体化，是把人物卡、预设、世界书、剧本、后台控制和 View 封装为一份可独立运行的 **DSH 游戏卡**。

执行分层化，是让前台 Agent、后台 Agent、工具、Host 和 View renderer 分别承担适合自己的职责。游戏卡是统一资源包，不是一个更大的 Prompt。

## 从酒馆资产到 DSH 游戏卡

酒馆人物卡及其关联资产是源格式，DSH 游戏卡是编译目标：

```text
人物卡 + 预设 + 世界书 + 剧本 + 正则 + 脚本
  → 转换 Skill 分析真实语义
  → 生成前台设定、后台任务、状态 Schema、工具和 View
  → 输出迁移诊断
  → 用户确认
  → DSH 游戏卡
```

转换结果必须区分：

- 可以准确迁移的能力；
- 需要语义推断和用户确认的能力；
- 只能继续通过兼容 Adapter 运行的能力；
- 当前无法安全迁移的能力。

DSH 不静默修正源人物卡，也不通过 Host 特判掩盖源资产的问题。兼容行为应对齐 SillyTavern 语义；原生能力则通过游戏卡运行时、后台工具和权威状态实现。

## 对酒馆生态的态度

酒馆架构的上限不等于酒馆生态没有价值。恰恰相反，人物卡、世界书、MVU、正则和社区脚本记录了大量真实、反复出现的玩家需求。

DSH 应当保留、研究和翻译这些资产背后的语义：

> 酒馆社区用文本模拟 Agent；DSH 游戏卡由真正的 Agent 运行时执行。
