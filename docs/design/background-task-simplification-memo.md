# 后台任务精简与玩家参与人物设计备忘

日期：2026-09-10

状态：已讨论确定的产品方向，尚未实施。本文不代表当前运行行为；本次只记录，不改代码。

## 前台与后台的职责

**前台负责本轮演出的精彩，后台负责衔接不同轮次、维护故事的一致性。** 前台把当前这一轮写好；后台让这些轮次能够连成一个持续发展的故事。

后台按维护的时间跨度与执行成本分为两级：

- 轻量后台每轮自动执行，维护当前状态与近期行动，支持短期一致性，让下一轮接得上。
- 重型后台由玩家按需手动触发，整理长期积累、规划后续发展，支持长期一致性，让故事推进较远后仍有依据。

“总结过去”和“规划未来”是后台衔接轮次的两种手段：前者维护已经成立的事实，后者为后续发展提供依据。两者都服务于故事的连续性，而不是为了增加后台产物本身。

一致性不是禁止人物和剧情变化，而是变化有来由、发展接得上。这是职责和设计目标，不代表仅靠后台任务就能保证故事始终连贯；还需要明确产物的读取方式与玩家参与的边界。

## 为什么精简

增加后台任务会增加 token 消耗和等待时间，减少状态维护又可能损害长程游玩的连续性。取舍不是删除所有能力，而是只让必要任务自动执行，其余由玩家按需触发。

后台工作分为两类：

- 总结过去：从已发生的正文中提取外部状态。变量更新、姿势总结、台账维护属于此类。
- 规划未来：提出尚未发生的可能。候选项、人物设计属于此类；规划不能直接当成已发生的剧情事实。

姿势是当前场景快照，主要服务下一轮衔接；台账偏向跨轮累计记录，方便玩家查阅。MVU 变量虽然也是状态维护，但属于人物卡运行协议，不能直接用台账替代。

## 两级设计的原理

后台过重，会增加每轮 token 消耗和等待时间；后台过轻，又难以维持长程连贯性。因此采用两级设计：轻量任务每轮自动执行，以尽量少的 token 满足短期衔接要求；较重的历史总结和未来规划交给玩家手动触发，避免无谓消耗，同时保留长程维护能力。

“总结过去／规划未来”描述任务方向，“轻量自动／重型按需”描述执行层级，两者不是一一对应关系。自动层也可以规划近期行动，手动层也可以整理过去的历史。

| 执行层级 | 触发方式 | 主要作用 | 任务示例 |
| --- | --- | --- | --- |
| 轻量自动层 | 每轮按配置自动触发 | 维护当前状态与近期行动，保证相邻轮次衔接，控制常规 token 开销 | 姿势总结、候选项；MVU 卡所需的变量更新 |
| 重型按需层 | 玩家明确手动触发 | 在需要时整理累计历史、参与后续创作，支持长程连贯 | 台账整理、人物设计小对话 |

自动层保证日常衔接，人工层决定何时值得投入更多成本。精简的是无条件、重复执行的工作，而不是把长期总结和规划能力删除。MVU 更新受人物卡协议约束，实际成本可能较高，不能仅因放在自动层就视为天然轻量。

这一取舍意味着长期记录不必每轮保持最新，需要让玩家看见整理进度，并能主动更新。长程作用还取决于产物如何被使用：台账帮助玩家回顾和决策，已确认的人物设计供后续正文参考；保存了记录并不等于模型会自动使用它，也不改变台账暂不注入前台的边界。

## 自动流程保持最小

- 姿势总结、候选项保留在日常游玩流程。
- MVU 卡保留按配置执行的变量更新。
- 台账整理退出每轮自动结算。
- 人物设计退出每轮自动检查，不再让后台反复判断是否需要设计人物。

当前过渡状态：姿势与变量默认开启，人物设计默认关闭但允许开启；台账已退出自动结算，工具和任务提示词已移除，旧配置无法重新启用；设置及面板入口隐藏。后续按本备忘另行实施手动入口。

## 台账按需整理

玩家需要查阅和更新记录时，主动点击“整理台账”才请求模型。查看已有台账不请求模型，平时不承担台账任务的模型开销。

展示“已整理至第 N 轮”，让玩家知道记录的时效。拟采用上次整理后的正文和已有台账做增量更新，没有新增正文时避免重复请求；首次整理、长历史分批处理、回退后的整理边界仍需实现设计。

## 人物设计由玩家参与

人物是小说的核心，不宜由后台随意创造、重复设计。人物卡与独立人物档案属于两套结构，不能只靠提示词保证去重，也不急于建设复杂的人物识别系统。

在游玩中提供一个人物设计小 Agent 对话，玩家可指定希望设计什么样的人物，并反复讨论、修改。例如：“设计一位即将登场的引路人，精明但讲信用，先不要让她出场。”

- Agent 参考人物卡、相关世界书、已有剧情和人物档案，提出方案。
- 已有设定作为约束，不因开启设计对话就重新设计所有角色。
- 玩家参与讨论和修改，明确确认“采用设计”后才进入正式人物档案，供后续正文使用。
- 未确认内容只是草稿，不影响正式正文和人物档案。
- 采用设计不等于已经登场；登场安排遵循玩家指令及后续正文。
- 只有实际发送设计请求时才产生相应模型消耗，不在每轮后台自动检查。
