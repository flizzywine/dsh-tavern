# 酒馆纯兼容模式阶段备忘

> 决定日期：2026-08-28
>
> 状态：当前阶段决定

## 决定

dsh-tavern 当前优先实现**纯兼容模式**。

导入人物卡、预设、世界书、正则、MVU 和 Helper 脚本后，系统首先按酒馆原有语义运行，不在导入时把它们重写为 DSH 原生的前台、后台和 Harness 任务。

因此，兼容模式下仍允许前台 LLM 同时生成：

- 故事正文；
- MVU 变量更新协议；
- 正则依赖的标签和占位符；
- `visual_cards` 等界面协议。

原有 MVU、正则和脚本在模型输出后继续完成解析、更新和展示。

## 为什么先兼容

不同人物卡把规则分散在人物卡字段、世界书、正则、模板和脚本中，而且语义各不相同。现阶段自动拆分容易误判卡片意图，改变原作行为。

先做纯兼容可以：

- 尽快运行现有酒馆生态资源；
- 建立真实人物卡的兼容基线；
- 看清各类资源的实际输入、输出与生命周期；
- 为将来的原生转换积累案例和测试。

## 当前不做

- 不自动把 MVU 更新提示迁移到后台 LLM；
- 不把任意正则机械转换为 View 或领域动作；
- 不生成新的 DSH 原生人物卡格式；
- 不要求用户在导入时理解或确认复杂的语义迁移。

## 接受的代价

纯兼容模式会继续让前台 LLM 承担正文之外的格式任务，可能增加 token、注意力竞争和掉格式概率。这是当前为了兼容性主动接受的代价，不代表最终架构。

## 实施原则

1. 原始酒馆资源完整保留，未知字段不得丢失。
2. 兼容以真实可观察行为为准，不只判断文件能否导入。
3. 单条正则、世界书或脚本失败不得摧毁正文和整局会话。
4. 原始模型输出、提示词投影和显示投影分别保存。
5. 对不支持、近似支持和存在安全限制的能力给出明确诊断。
6. DSH 仍负责通用模型调用、Session 和生命周期，不复制一套独立 Agent 平台。

## 后续方向

LLM-Harness 的前台 LLM、后台 LLM、Harness 三层架构仍是长期方向。等纯兼容模式稳定后，再考虑按能力逐项转换，而不是一次性重写整张人物卡：

```text
酒馆源资源
  → 能准确识别：转换为原生前台、后台或 Harness 能力
  → 语义不确定：请求用户确认
  → 无法转换：继续由兼容 Adapter 运行
```

当前优先级可以概括为：

> **先让酒馆资源正确运行，再讨论如何把混合在前台的任务拆到后台。**
