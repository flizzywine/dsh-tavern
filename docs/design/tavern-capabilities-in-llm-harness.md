# 从酒馆功能到 LLM Harness：能力拆解与重新安置

> 状态：架构探索。本文讨论职责与归属，不是格式规范或实施计划。

## 1. 问题不是插件太多，而是缺少应用模型

SillyTavern 生态中的人物卡、预设、世界书、正则和 MVU，看起来像五种互不相干的资源。实际上，它们共同拼出了一种完整程序：用户输入推动故事，LLM 理解语义并生成正文，传统代码维护状态、装配上下文、校验结果和渲染界面。

这是一种 **LLM 混合程序**。它同时依靠两类计算：

- **LLM 语义计算**：理解剧情、人物关系和开放情境，完成无法穷举的判断与生成。
- **Harness 确定性计算**：管理生命周期、状态、分支、权限、校验、资源和可重复执行的规则。

酒馆原本只有“聊天前端”和“内容资源”的概念，没有完整的 LLM 应用模型。社区便把程序职责分散到现有扩展点中：人物卡兼任应用包，聊天记录兼任状态数据库，世界书兼任知识库和条件路由，正则兼任协议解析与界面生成，MVU 再补上一套结构化状态运行时。

因此，重新设计时不能把这些旧名词原样搬进新架构。应先问每项机制究竟解决什么问题，再把职责安置到正确的模块。

## 2. 酒馆生态的功能清单

围绕一局持续运行的文字游戏，现有生态实际提供了以下能力：

| 功能类别 | 用户需要的结果 | 当前常见载体 |
| --- | --- | --- |
| 应用与角色定义 | 知道在玩什么、角色是谁、故事从哪里开始 | 人物卡、开场白、示例对话、作者说明 |
| 生成行为控制 | 控制模型的身份、文风、输出方式和模型参数 | 预设、系统提示词、Prompt Order |
| 上下文装配 | 每轮选择、加工并排列模型需要看到的内容 | 预设、宏、EJS、注入深度、世界书 |
| 知识供给 | 按当前情境提供人物、地点、规则和剧情资料 | 世界书、动态世界书、外部资料 |
| 故事状态 | 记住时间、位置、关系、物品、任务和世界变化 | 聊天上下文、变量、MVU、特殊状态块 |
| 状态结算 | 从本轮剧情判断世界发生了什么变化 | 正文模型、额外解析模型、MVU 更新规则 |
| 确定性规则 | 校验数值、限制非法变化、执行可重复变换 | 正则、模板逻辑、变量守卫、Helper 脚本 |
| 对话与分支 | 保存消息，支持编辑、重生成、swipe 和回退 | SillyTavern 聊天与消息楼层 |
| 展示与交互 | 显示状态栏、卡片、按钮、CG 和其他媒体 | Markdown、正则、HTML、Helper iframe |
| 模型执行 | 连接模型，处理流式输出、重试和多模型分工 | SillyTavern 模型连接、扩展、额外模型请求 |
| 扩展与自动化 | 监听生命周期并调用宿主能力 | ST 扩展、Tavern Helper、卡片脚本 |
| 分发与资源 | 导入应用内容，加载脚本、图片和音频 | PNG/JSON、GitHub、CDN、R2 |
| 治理与诊断 | 管理权限、版本、错误、兼容性和升级 | 当前分散在安装说明、扩展设置和日志中 |

其中，人物卡、预设、世界书、正则和 MVU 是最核心、也最容易职责混杂的五种载体。

## 3. 五项核心功能的目的、原理与重新安置

### 3.1 人物卡

**目的**

人物卡让一个可游玩的角色或故事能够被描述、交换、导入并启动。普通卡主要提供角色内容；复杂卡还会声明世界书、正则、脚本、状态协议和外部资源。

**当前原理**

SillyTavern 读取人物卡字段并把它们放进模型上下文。复杂人物卡又利用扩展字段携带其他资源，由宿主扩展识别并运行。人物卡因此从“角色资料”逐渐变成了应用说明、初始化数据、依赖清单、脚本入口和资源索引的混合物。

**在 LLM Harness 中的归属**

人物卡应升级为 **LLM 应用包的源格式**，但不亲自承担运行时职责。它可以声明：

- 应用身份与角色内容；
- 初始场景、开场和示例；
- 所需的知识、状态、界面和工作流能力；
- 资源清单、版本、权限和兼容要求。

导入模块把酒馆人物卡编译为内部应用模型；运行时只消费编译结果。人物卡不再通过隐藏字段直接启动任意远程代码，也不再兼任数据库和包管理器。

### 3.2 预设

**目的**

预设控制“模型如何工作”：包括系统规则、写作要求、提示词顺序、角色位置、注入深度、宏和模型参数。它本质上是一次生成的上下文装配策略。

**当前原理**

酒馆在每轮生成前读取一组有序提示词条目，把人物卡、世界书、历史消息和动态内容插入指定位置，再执行宏和模板，最终形成模型请求。预设常把内容、装配顺序、生命周期和模型参数放在同一个 JSON 中。

**在 LLM Harness 中的归属**

预设应被拆成两个职责：

1. **语义策略**：叙事身份、文风、内容约束和输出目标。
2. **上下文计划**：哪些内容属于稳定前缀，哪些按轮投影，哪些只在本次生成末尾出现。

二者由统一的上下文编译模块执行。模型参数进入模型执行配置，不由提示词条目顺带管理。酒馆预设继续作为兼容源格式，由适配器翻译，而不是成为新运行时的内部结构。

### 3.3 世界书

**目的**

世界书解决“知识很多，但每轮只需要其中一部分”的问题。它让人物、地点、规则、事件和背景资料在相关情境出现时进入模型上下文。

**当前原理**

SillyTavern 扫描近期对话和其他允许的文本，通过关键词、常驻、递归、概率、分组、优先级和 token 预算决定激活哪些条目，再把内容注入预设指定的位置。复杂卡的动态世界书还会读取变量，由脚本启停条目。

**在 LLM Harness 中的归属**

世界书应拆成：

- **知识库**：保存可检索的事实、规则与资料；
- **上下文选择器**：根据本轮输入、领域状态和预算选择知识；
- **上下文投影器**：把选中的知识转换成适合目标 Agent 的最小表达。

关键词召回、向量召回、状态条件和 LLM 语义召回只是选择器的不同实现，不应改变知识本身。所谓“动态世界书”也不再是一个人物卡专属脚本，而是“依据权威状态选择知识”的正常规则。

世界书不能成为世界事实的权威来源。它提供模型需要知道的资料；已经发生的剧情与当前世界状态必须由领域状态和剧情时间线保存。

### 3.4 正则

**目的**

正则用于识别文本模式并进行确定性转换。在酒馆生态中，它还被扩展为特殊协议解析、提示词清理、状态标签隐藏、占位符替换和 HTML 界面生成工具。

**当前原理**

规则在用户输入、模型输出、提示词或显示等不同阶段运行，以 JavaScript 正则匹配字符串并执行替换。正则本身通常不保存状态，但正则卡可以把状态写在聊天上下文的特殊文本块中，由 LLM 读取和重写，再由正则解析、隐藏或呈现。因此，整张正则卡依然可以是有状态程序，只是状态由上下文承载。

**在 LLM Harness 中的归属**

“正则模块”不应整体保留，而要按效果拆开：

- **内容转换**：对输入或输出做纯文本规范化；
- **兼容协议解码**：识别旧卡的状态标签、占位符和控制标记；
- **展示投影**：把原始消息转换成用户看到的文本或界面；
- **领域动作**：如果正则实际表达状态修改，应迁移为明确的状态动作，不能继续靠字符串副作用完成。

每条规则必须声明执行阶段、输入和输出。原始正文、发送给模型的内容和显示结果分别保存，任何转换失败都不能破坏权威消息。正则在原生架构中是一种受限的确定性实现或兼容适配器，不是应用运行时。

### 3.5 MVU

**目的**

MVU 把散落在自然语言剧情中的状态显式化。它维护时间、地点、关系、物品、任务等结构化数据，并让下一轮提示词、世界书和界面能够稳定消费这些数据。

**当前原理**

人物卡通过 Schema、初始值和自然语言更新规则定义状态。正文模型或额外模型根据剧情生成更新指令，MVU 解析增量 Patch，变量守卫与 Schema 负责校验，结果按消息楼层和 swipe 保存。下一轮再把状态注入模型或交给卡片脚本使用。

这里混合了四种不同工作：语义理解、变更提议、确定性校验、状态持久化。

**在 LLM Harness 中的归属**

MVU 应拆入正式的领域状态体系：

- **领域状态模型**：定义字段、类型、初始值和不变量；
- **语义结算任务**：由后台 Agent 判断本轮剧情意味着哪些变化；
- **领域动作与状态机**：把变化表达为受限动作，而不是任意改 JSON；
- **校验与提交**：Harness 检查依据版本、不变量和权限后原子提交；
- **事件与分支**：每次变更绑定剧情分支、revision 和来源正文，回退或 swipe 时可以恢复一致状态；
- **上下文与界面投影**：只向前台模型和 UI 提供各自需要的状态子集。

LLM 可以提出“发生了什么变化”，但不能直接宣布新的权威事实。最终提交权属于确定性的领域状态模块。MVU 格式可以作为兼容适配器继续导入，但不再作为架构中心。

## 4. 支撑这些功能的其他能力如何安置

| 现有能力 | 新架构位置 |
| --- | --- |
| Tavern Helper / 卡片 JavaScript | 旧卡兼容运行时；原生应用改用声明式工作流与受限领域动作 |
| EJS / Prompt Template | 上下文编译模块中的确定性模板实现，只负责计算文本投影 |
| 聊天记录 | 剧情时间线的对话投影，不同时兼任唯一数据库和提示词缓存 |
| swipe、重生成、回退 | 剧情分支与 checkpoint 管理 |
| 状态栏、HTML、CG | 展示模块和资源模块，只读取 View 投影，不直接修改领域状态 |
| 额外模型解析变量 | DSH 管理的后台语义任务，共享模型路由、重试、取消和诊断能力 |
| GitHub、CDN、R2 资源 | 资源适配器；应用包记录版本、hash、缓存与离线策略 |
| 扩展安装与权限 | 应用清单和能力授权；代码默认隔离，按声明开放网络、存储或宿主动作 |

## 5. 重新安置后的 LLM Harness 架构

新架构不是“用 DSH 重写一遍酒馆插件”，而是把程序职责归并为少数深模块：

```text
LLM 应用包
  人物与内容、初始状态、知识、语义策略、View、资源与能力声明
                         │
                         ▼
Tavern 领域 Harness
  剧情时间线 ─ 领域状态 ─ 上下文计划 ─ 知识选择 ─ View 投影
       │             │             │
       └──── 统一 branch / revision / 事件依据 ────┘
                         │
                         ▼
DSH 通用 Harness
  Session、Agent、模型路由、工具、后台任务、流式、重试、取消与持久化
                         │
              ┌──────────┴──────────┐
              ▼                     ▼
       前台叙事 Agent          后台语义 Agent
       生成故事正文            状态结算、摘要与召回判断
              └──────────┬──────────┘
                         ▼
              受控动作、校验、原子提交
                         ▼
                 下一轮上下文与界面
```

各层的职责是：

- **LLM 应用包**描述“这个应用是什么”，不自行决定宿主如何执行。
- **Tavern 领域 Harness**拥有文字游戏的权威剧情、状态和上下文规则。
- **DSH 通用 Harness**提供可复用的 Agent 执行与生命周期能力，不理解人物卡、世界书或 MVU。
- **LLM**处理需要语义理解和开放判断的工作。
- **确定性模块**处理能够明确计算、校验和提交的工作。
- **兼容适配器**翻译旧酒馆资源，但不把旧架构扩散到内部模块。

## 6. 一轮游戏应当怎样运行

```text
用户输入
  → Turn Orchestrator 建立本轮 revision
  → Context Planner 读取应用策略、必要状态和相关知识
  → 前台 Agent 生成纯故事正文
  → 正文先作为候选结果绑定当前 revision
  → 后台 Agent 从正文中提出状态动作和其他语义结算
  → 领域状态模块校验并原子提交
  → 剧情时间线提交正文、状态事件与分支依据
  → View 模块从权威状态生成状态栏、CG 和交互
  → 下一轮只投影模型真正需要的状态与知识
```

这条链路把“灵动”和“可靠”放在不同位置：LLM 不必承担数据库职责，传统代码也不必穷举剧情含义。两者通过受控动作和权威状态协作，而不是通过正文中的隐藏标签彼此猜测。

## 7. 最重要的重新命名

| 酒馆中的历史名词 | 在新架构中应理解为 |
| --- | --- |
| 人物卡 | LLM 应用包的源格式 |
| 预设 | 语义策略 + 上下文计划 |
| 世界书 | 知识库 + 上下文选择器 |
| 正则 | 阶段明确的转换实现或兼容适配器 |
| MVU | 领域状态、语义结算与提交协议的旧实现 |
| 酒馆助手 | 旧卡脚本兼容运行时 |
| 复杂酒馆卡 | 被旧资源格式拆散保存的 LLM 混合应用 |

这个重命名不是术语游戏，而是在确定新的模块 seam。只有先拆掉历史载体之间的错误依赖，才能形成小接口、深实现的模块：应用作者只需描述角色、知识、状态与玩法；玩家只需导入并开始；复杂的 Agent 协作、状态一致性、上下文装配、权限和兼容性由 Harness 统一承担。

## 8. 架构原则

1. **只有一个权威剧情与领域状态来源。** 聊天、摘要、世界书、UI 和 Agent Session 都只是不同投影。
2. **语义判断交给 LLM，事实提交交给 Harness。** LLM 提议动作，领域模块验证并提交。
3. **内容、状态、上下文和显示分离。** 一种资源不能再同时充当提示词、数据库和界面代码。
4. **兼容语义，不继承旧运行时。** 酒馆资源进入编译与适配层，不反向决定原生模块形状。
5. **按生命周期安置规则。** 导入时、每轮生成前、正文生成后、状态提交后和显示时是不同 seam。
6. **原始数据始终可追溯。** 原人物卡、原始模型输出和兼容转换结果分别保存。
7. **人物卡代码默认不可信。** 网络、存储、宿主动作和界面能力必须声明、隔离并可诊断。
8. **失败按能力隔离。** 状态结算、知识召回或 View 失败不能摧毁正文与整局游戏。

## 9. 结论

酒馆生态已经验证了 LLM 混合应用的真实需求，但它使用人物卡、预设、世界书、正则、MVU 和脚本把一个程序拆散后重新拼接。新的 LLM Harness 不应继续维护这种拼接方式，而应吸收其功能、淘汰其偶然形成的依赖关系。

最终目标不是让用户学会如何组合插件，而是让应用作者明确描述内容、知识、状态、语义规则和界面，让 Harness 负责可靠地运行它们。人物卡仍然可以是用户熟悉的入口，但其背后应当是一套真正的 LLM 应用架构。
