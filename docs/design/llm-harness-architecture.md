# LLM-Harness 架构

> 状态：架构总纲。本文只定义核心分工，不涉及具体实现。

## 核心定义

LLM-Harness 由三部分组成：

1. **前台 LLM**：负责面向用户的正文与表演。
2. **后台 LLM**：负责理解正文并处理后台语义任务。
3. **Harness**：负责确定性计算、状态管理和整个应用生命周期。

```text
用户输入
   ↓
前台 LLM：生成正文
   ↓
后台 LLM：理解正文并提出结构化变化
   ↓
Harness：校验、提交、保存、投影
   ↓
更新状态、候选项、UI 与下一轮上下文
```

## 前台 LLM：负责演出

前台 LLM 直接面向用户，负责：

- 人物扮演、对白和剧情推进；
- 文风、节奏、氛围与情绪表现；
- 输出玩家真正阅读的故事正文。

它只读取本轮必要的状态与知识，不维护完整数据库，不输出变量 Patch、候选项、UI 标签或后台工具记录。

## 后台 LLM：负责语义结算

后台 LLM 不面向用户，负责需要理解剧情含义的工作，例如：

- 判断人物、物品、地点和任务发生了什么变化；
- 提议变量更新；
- 生成下一步候选行动；
- 生成摘要、人物姿势和场景标签；
- 判断需要召回的知识或展示的 CG。

后台 LLM 只提出结构化动作，不能直接修改权威状态，也不能改写前台正文。

前后台是两种职责和两套 Session，不一定必须使用不同模型。正文可以使用擅长文学表现的模型，后台可以使用便宜、快速、擅长结构化任务的模型。

## Harness：负责可靠运行

Harness 是系统的确定性核心，负责：

- 调度前台与后台任务；
- 保存权威剧情时间线和领域状态；
- 管理 branch、revision、回退与重生成；
- 组装前后台各自需要的上下文；
- 校验 Schema、领域规则和状态动作；
- 原子提交变量、候选项和 View 数据；
- 管理模型调用、重试、取消、权限、资源和诊断。

LLM 可以判断“发生了什么”，但只有 Harness 可以确认“什么成为事实”。

## 一轮运行流程

```text
1. Harness 为前台 LLM 投影必要上下文
2. 前台 LLM 生成纯故事正文
3. Harness 将正文提交到剧情时间线
4. 后台 LLM 根据正文提出状态动作
5. Harness 校验并提交新状态
6. 后台 LLM 基于新状态生成候选项等派生结果
7. Harness 生成 UI 与下一轮上下文投影
```

候选项应在变量结算后生成，避免基于旧状态提出行动。后台失败只影响对应派生能力，已经生成的正文仍然有效。

## 酒馆生态能力的归位

| 酒馆能力 | LLM-Harness 中的位置 |
| --- | --- |
| 人物卡 | LLM 应用包，提供人物、内容与能力声明 |
| 预设 | Harness 的语义策略与上下文计划 |
| 世界书 | Harness 的知识库与上下文选择器 |
| MVU 语义判断 | 后台 LLM |
| MVU 状态校验与保存 | Harness |
| 正则 | Harness 的兼容转换或展示投影 |
| 状态栏、CG、按钮 | Harness 根据权威状态生成的 View |

## 核心原则

1. 前台只负责演出，后台只负责语义结算。
2. 前后台都不能直接修改权威状态。
3. Harness 是剧情和领域状态的唯一权威来源。
4. 状态、候选项和 UI 不再混入正文协议。
5. 每项后台结果必须绑定 branch、revision 和来源正文。
6. 后台任务失败不能破坏正文与整局游戏。

一句话概括：

> **前台 LLM 把戏演好，后台 LLM 把事情看懂，Harness 把账算清并守住事实。**
