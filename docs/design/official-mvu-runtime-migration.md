# 官方 MVU 本地运行时迁移方案

> 状态：已确认的目标方案，尚未实施。
>
> 本文取代 `orchestration-strategies-and-tavern-script-module.md` 中“由 dsh-tavern 自研 MVU Core 长期解释 MVU 协议”的目标描述。普通游玩与兼容模式仍然是两种编排策略；本次迁移只改变 MVU 协议的执行所有者。

## 一句话结论

dsh-tavern 应当在本地固定并运行经过审查的官方 MagVarUpdate 代码，由 Tavern Host Adapter 为它提供 SillyTavern 形状的宿主能力；官方 MVU 是每个对话唯一的变量状态执行器，dsh-tavern 继续拥有消息、变量、世界书和 Session 的持久化权威。

这不是替换一个依赖，而是一次执行权迁移：

```text
当前
模型输出
  → dsh-tavern 自研 MVU 解析与结算
  → 模拟官方事件
  → 人物卡配套脚本
  → DSH 持久化

目标
模型输出
  → 本地官方 MVU 解析与结算
  → 官方事件与人物卡配套脚本
  → Tavern Host Adapter
  → DSH 持久化
```

## 为什么要迁移

当前 `tavern-mvu-runtime.js` 是依据固定版 MagVarUpdate 行为自行编写的兼容实现，不是官方 bundle。它已经覆盖初始化、JSON Patch、lodash 风格命令、Swipe 变量和部分生命周期事件，但兼容度依赖持续猜测、对照和补齐。

这会产生三个长期问题：

1. **语义漂移**：官方解析规则、事件参数、Zod 交接和消息生命周期变化时，本地实现需要逐项追赶。
2. **组合风险**：变量结构、变量守卫和动态世界书脚本是围绕官方 MVU 的共享运行环境编写的；只模拟事件名称并不保证共享状态、顺序和异常行为一致。
3. **维护成本**：每张复杂 MVU 卡都可能暴露新的兼容缺口，本地 MVU 会逐渐变成第二份 MagVarUpdate。

迁移目标不是让 dsh-tavern 变成 SillyTavern，而是把已经存在且不值得重复实现的 MVU 状态机交还给官方代码，同时通过 Adapter 保持 DSH 原生状态与编排。

## 设计决策

### 1. 官方代码本地化，不在运行时依赖 CDN

- 固定明确的上游仓库和 commit。
- 保存官方许可证、来源、构建方式、产物哈希和本地补丁记录。
- 优先保存可复现构建的源代码与锁文件；运行经过验证的固定产物。
- 人物卡声明的 MagVarUpdate CDN 入口由本地资源映射接管，不再重复下载和执行。
- 升级官方 MVU 必须经过差分测试，不跟随 CDN 静默漂移。

这里的“本地”指代码和执行环境都在用户机器上，不等于重新编写协议。

### 2. 每个对话只有一个 MVU 状态执行器

以下不变量必须由代码和测试共同保证：

- 同一条模型回复只结算一次。
- 官方 MVU 与旧自研 MVU 不得处理同一个回复。
- 一轮结算只产生一次带版本检查的最终变量提交。
- 任何失败都不能在部分写入后自动换另一套 MVU 再执行。
- 重新生成和 Swipe 各自拥有独立变量快照，不能覆盖兄弟分支。

迁移期间可以同时保留两份实现，但它们只能作为互斥 Adapter：

```text
                 MVU Runtime interface
                    ┌──────┴──────┐
                    ↓             ↓
          Official MVU Adapter   Legacy MVU Adapter
                 生产目标          临时回退/差分
```

当官方路径通过验收后，应删除生产环境中的旧实现，而不是长期维护双引擎。

### 3. 官方 MVU 拥有计算，DSH 拥有持久化

权威职责按下表划分：

| 状态或行为 | 所有者 |
| --- | --- |
| MVU 命令解析、校验、事件顺序、变量转换 | 本地官方 MVU |
| 人物卡变量结构、变量守卫等脚本逻辑 | 酒馆脚本运行模块 |
| 当前消息、Swipe 与变量快照 | dsh-tavern |
| 世界书、人物卡和脚本变量持久化 | dsh-tavern |
| DSH Session、模型调用、工具和压缩 | DSH Runtime |
| 一轮何时开始、何时结算 | 当前编排策略 |

官方 MVU 不能直接建立第二份聊天数据库。它看到的是 Host Adapter 投影出的酒馆消息，最终修改必须作为结构化效果提交回 dsh-tavern。

### 4. 普通游玩与兼容模式继续共享同一个 MVU 模块

普通游玩和兼容模式仍然只在请求组织方式上不同：

```text
普通游玩编排 ─┐
              ├─→ 酒馆脚本运行模块 / 官方 MVU ─→ Host Adapter ─→ DSH 状态
兼容模式编排 ─┘
```

不能为两种模式各维护一套 MVU。MVU 是模型输出后的确定性结算能力，不应知道本轮请求是用哪一种编排策略生成的。

## 目标模块关系

```text
人物卡 Helper 脚本
人物卡声明的 MVU import
          ↓ 本地资源解析
┌──────────────────────────────────────────┐
│ 酒馆脚本运行模块                         │
│                                          │
│ 每个对话一个共享脚本沙箱                 │
│  ├─ 本地官方 MVU Core（只加载一次）      │
│  ├─ 变量结构                             │
│  ├─ 变量守卫                             │
│  ├─ 动态世界书                           │
│  └─ 其他人物卡 Helper 脚本               │
│                                          │
│ 对外只暴露 MVU Runtime interface         │
└────────────────────┬─────────────────────┘
                     │ Tavern Host interface
                     ↓
              Host Adapter（桥接层）
                     ↓
┌──────────────────────────────────────────┐
│ dsh-tavern 权威状态                      │
│ 消息 / Swipe / 变量 / 世界书 / 人物卡    │
└────────────────────┬─────────────────────┘
                     ↓
                 DSH Runtime
```

### 为什么改为每个对话一个共享脚本沙箱

官方 MVU 和人物卡配套脚本原本运行在共享的 SillyTavern 页面环境中。变量结构注册、事件监听、全局对象和初始化顺序都可能依赖这种共享关系。

当前每脚本一个 iframe 的隔离方式安全性较强，但需要人为复制 `window.Mvu`、事件和状态，很容易出现“事件名称相同，实际对象和生命周期不同”。目标方案采用：

- 人物卡脚本之间共享一个对话级沙箱；
- 沙箱与 dsh-tavern 父页面仍然隔离；
- 所有宿主访问必须经过 Host Adapter；
- 状态栏、CG 和普通消息 HTML 继续使用独立展示 iframe，不加入脚本沙箱。

这样共享的是人物卡程序的 JavaScript 运行环境，不是父页面 DOM，也不是 DSH 内部对象。

## 深模块与接口

### MVU Runtime module

MVU Runtime 应成为一个深模块：调用方只需要知道对话生命周期和结算结果，不需要知道 MVU 的命令格式、事件清单、Zod 顺序或脚本初始化细节。

建议的外部接口只有三个动作：

```text
start(chatSnapshot, cardAssets) → runtimeHandle
dispatch(runtimeHandle, chatEvent) → runtimeEffects
stop(runtimeHandle)
```

其中 `chatEvent` 包含开场初始化、用户消息、助手回复、重新生成、Swipe、删除和对话切换。`runtimeEffects` 是需要 Host 执行的结构化效果，不允许直接携带可调用的 DSH 内部对象。

接口的不变量包括：

- 事件按单对话顺序处理；
- 每个输入事件都有稳定的事件 ID，重复投递必须幂等；
- 输出携带其读取的状态 revision；
- Runtime 不直接写磁盘；
- 超时或脚本失败必须指出发生在提交前还是提交后。

### Tavern Host Adapter

Host Adapter 位于脚本沙箱与 dsh-tavern 权威状态之间的唯一 seam，负责：

- 将 DSH 消息和 Swipe 投影成 SillyTavern 消息；
- 提供 MVU、Tavern Helper 和人物卡脚本需要的宿主函数；
- 将变量、消息、世界书和脚本变量修改转换成受版本保护的事务；
- 执行权限检查、超时、取消和错误归类；
- 返回提交后的最新投影。

Host Adapter 不能理解具体人物卡业务，也不能重新解释 MVU 命令。否则 MVU 语义会再次分裂到两个模块中。

### 编排策略

编排策略只负责在正确时间发送事件：

```text
模型回复完成
  → dispatch(ASSISTANT_MESSAGE_RECEIVED)
  → Runtime 内部由官方 MVU 和人物卡脚本完成结算
  → Host Adapter 原子提交 runtimeEffects
  → 编排策略继续保存和展示本轮结果
```

编排策略不能自行解析 `<UpdateVariable>`，也不能手工补发官方 MVU 的内部生命周期事件。

## 一轮回复的目标链路

```text
1. 编排策略取得模型原始输出
2. Host 提供上一楼层对应 Swipe 的变量快照和 revision
3. 对话脚本沙箱收到 ASSISTANT_MESSAGE_RECEIVED
4. 官方 MVU 解析并执行 UpdateVariable
5. 变量结构、变量守卫等脚本按官方顺序参与
6. Runtime 输出最终正文、变量、脚本效果和诊断
7. Host Adapter 使用 expectedRevision 原子提交
8. 成功后发布一次状态事件，正文和状态栏读取同一份已提交快照
```

如果第 7 步发现 revision 已变化，本轮结果必须废弃并按明确策略重新读取；不能覆盖新状态，也不能只重放部分脚本效果。

## 迁移阶段

### 阶段 0：冻结现有证据

在改变执行路径之前建立可重复基线：

- 固定当前官方 MVU commit、人物卡和配套脚本内容；
- 保存开场初始化、正常回复、重新生成、Swipe、回退和刷新夹具；
- 记录模型原始输出、事件序列、最终变量树和消息快照；
- 将目前发现的“模型输出补丁但最终变量未更新”保存为失败回归用例。

没有可重复基线时，不开始替换。

### 阶段 1：引入可审计的官方源码和产物

- 将固定版官方源码、许可证和构建元数据纳入仓库或可验证的构建输入；
- 构建本地固定产物并校验 SHA-256；
- 禁止产物在运行时访问上游 CDN 获取 MVU Core；
- 暂不接入真实对话，只验证离线加载和官方自测。

完成标准：断网状态下可以稳定加载指定版本，构建结果可复现。

### 阶段 2：建立对话级共享脚本沙箱

- 一个对话创建一个常驻脚本沙箱；
- 先加载 Host shim，再加载官方 MVU，最后按卡片顺序加载配套脚本；
- 明确 ready、failed、disposed 三种生命周期状态；
- 多窗口只能有一个脚本执行租约，其他窗口只消费已提交状态；
- 卡片 UI iframe 与脚本沙箱分离。

完成标准：变量结构和变量守卫在同一 MVU 全局环境完成注册，切换对话后旧沙箱不能继续写入。

### 阶段 3：补齐 Host Adapter

只实现官方 MVU 和目标人物卡实际调用的宿主能力，按调用证据扩展，不宣称完整 SillyTavern：

- 消息、Swipe 和变量读取；
- 变量与消息更新；
- 对话变量和脚本变量；
- 人物卡与绑定世界书读取、写入；
- 事件、Popup、按钮和运行诊断；
- 取消、超时、revision 与执行租约。

完成标准：官方 MVU 可以在不访问父页面内部对象的情况下完成整轮结算。

### 阶段 4：影子差分

在测试环境中，让旧实现和官方实现读取相同的只读输入，分别产生结果，但只有旧实现可以提交。比较：

- 最终正文；
- 最终变量树；
- 事件名称、顺序和参数；
- 脚本请求的宿主效果；
- 失败与诊断。

影子运行不能触发真实世界书、消息或变量写入。

完成标准：固定夹具达到预先定义的差分范围；不允许用 UI “看起来正常”代替变量树和事件差分。

### 阶段 5：单所有者切换

- 为内部迁移加入互斥的 Runtime owner：`official` 或 `legacy`；
- 新对话先切到官方实现；已有对话在明确的楼层边界切换；
- owner 与 Runtime 版本写入对话元数据；
- 一轮开始后 owner 不可变化；
- 官方结算失败时整轮失败并保留旧快照，不在同一轮自动调用旧实现。

完成标准：生产路径中每轮只有一个 MVU 执行记录和一次最终变量提交。

### 阶段 6：删除旧生产实现

当真实卡验收稳定后：

- 删除旧自研解析器的生产入口；
- 保留必要的历史夹具和差分测试；
- 将旧 Adapter 限时保留为开发回退后再移除；
- 更新架构文档，把 MVU 从“原生协议 module”移动到“本地官方脚本运行时”。

删除测试时遵守“替换而不是叠加”：新测试通过 MVU Runtime interface 验证可观察行为，不继续维护两套实现细节测试。

## 现有用户与数据兼容

本次迁移原则上不要求转换历史消息，因为当前消息已经保存每个 Swipe 的变量快照。迁移时需要验证并固定以下格式：

- `stat_data`、`schema`、`display_data`、`delta_data`；
- `initialized_lorebooks`；
- 每条消息与每个 Swipe 的变量数组关系；
- 当前选中 Swipe；
- 脚本变量和对话变量。

已有对话的切换规则：

1. 从当前选中 Swipe 的已提交变量快照启动官方 Runtime；
2. 不重新执行全部历史补丁；
3. 只从切换后的下一条新事件开始处理；
4. 如果启动校验失败，保持原快照并提示，不能写入半迁移状态。

因此升级不应改变旧楼层变量；风险集中在迁移后的新回合和人物卡脚本初始化。

## 失败处理与回退

### 允许回退的情况

- 对话尚未开始新一轮结算；
- 官方 Runtime 启动失败且没有产生持久化效果；
- 用户恢复到迁移前的软件版本。

### 禁止自动回退的情况

- 官方 Runtime 已经处理部分事件；
- Host Adapter 已经提交部分世界书或消息修改；
- 无法确认是否执行过人物卡脚本副作用。

这些情况必须中止本轮、保留诊断并从最后一次完整快照恢复，不能换旧引擎继续运行。

## 可观测性

每轮至少记录：

- Runtime owner 与官方 commit；
- chat ID、message ID、swipe ID 和事件 ID；
- 输入和输出变量树哈希；
- Host revision 与提交结果；
- 官方 MVU 事件时间线；
- 哪个脚本修改了命令或最终变量；
- 超时发生在加载、事件处理还是提交阶段。

用户界面只展示简洁结果，例如“本轮变量更新 8 项”或明确失败；完整证据进入 Session Log。不能再用 `<Analysis>` 美化面板推断变量是否真正写入。

## 验收矩阵

### 协议与变量

- `<initvar>` 初始化和多开场 Swipe；
- JSON Patch 与 lodash 风格命令；
- 路径修正、数值类型和表达式；
- Zod schema 注册、转换和失败；
- 变量守卫改写命令；
- 无更新、部分失败和全部失败。

### 消息生命周期

- 正常生成；
- 重新生成并保留旧 Swipe；
- 双向切换 Swipe；
- 删除、回退和恢复；
- 页面刷新和应用重启；
- 同一对话多窗口竞争。

### 人物卡集成

- 《灯火阑珊》15 个开场；
- 变量结构、变量守卫、动态世界书和开场索引；
- `visual_cards` 与状态栏读取提交后的变量；
- 外部资源断网和缓存回退；
- 无 MVU 卡不加载官方 Runtime。

### 必须成立的最终断言

1. 每条回复最多结算一次。
2. 每轮最终变量与对应 Swipe 一一绑定。
3. UI 显示的更新回执来自实际提交差异。
4. 刷新后正文、变量和状态栏来自同一 revision。
5. Runtime 失败不会污染上一份完整快照。
6. 普通游玩与兼容模式对相同 MVU 输出得到相同结算结果。

## 不在本次迁移中解决

- 完整复刻 SillyTavern 的请求编译；
- 完整实现所有 Tavern Helper 函数；
- 允许人物卡脚本直接操作 DSH 父页面 DOM；
- 将状态栏 UI 与 MVU 状态机合并；
- 使用后台模型替代前台 MVU 协议；
- 自动跟随 MagVarUpdate 最新提交。

## 迁移完成的定义

只有同时满足以下条件，才能宣布迁移完成：

- 生产回合只运行本地固定版官方 MVU；
- 人物卡中的 MVU CDN 导入稳定映射到同一实例；
- 配套脚本在共享沙箱中按官方生命周期工作；
- Host Adapter 原子提交最终效果，DSH 仍是唯一持久化权威；
- 固定夹具、真实人物卡、刷新恢复和多窗口测试全部通过；
- 旧自研 MVU 不再位于生产执行链路。
