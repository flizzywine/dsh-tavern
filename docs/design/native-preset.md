# 酒馆预设与 DSH 预设

## 背景

传统酒馆在每轮生成前重新拼接系统规则、人物设定、对话历史和末尾指令。DSH 的 Agent 架构则保留稳定前缀，并在持续会话中追加新的对话内容。两者的差异不只在预设格式，更在上下文如何随时间形成。

DSH 预设的目标不是复刻酒馆预设的完整拼接行为，而是用适合 DSH 追加式 Agent 架构的方式组织提示词。

## DSH 预设的三个部分

DSH 预设只拥有三个正式部分：

1. **稳定前缀**：在会话创建时确定，此后保持不变。每次模型请求仍会携带同一份内容，从而形成可复用的缓存前缀。
2. **每轮注入**：每轮根据当前人物卡、世界书、状态和用户指导重新生成一次，只服务当前回合。系统可以保存该轮实际使用的快照以供追溯，但旧轮快照不会作为普通消息在后续请求中重复累积。
3. **后带内容**：发送模型请求前临时追加在请求末尾，参与本次生成，但不写入 DSH Session，也不会成为下一轮历史。

DSH Session 的真实对话历史不属于预设的第四个部分。历史由 DSH 原生会话持有，预设只能围绕它装配上述三个部分，不能接管或反复重建历史。

一次请求的基本顺序是：

```text
稳定前缀
 DSH Session 对话历史
 每轮注入
 当前用户消息
 后带内容
```

这里的“会话创建时确定”是生命周期语义，不表示稳定前缀只通过网络发送一次。模型请求仍需携带它，只是内容与顺序保持稳定，以便提供方复用前缀缓存。

“每轮注入进入 Session”只表示该轮使用的内容可以作为当轮上下文快照保存，以便调试、回放和解释；它不等于把整段内容写成普通对话消息。否则人物设定和动态世界书会每轮复制并永久累积，使 Session 不断膨胀。

三部分的职责不能只按文本位置判断，还必须遵守生命周期：稳定内容不得引用每轮变化的状态；每轮注入不得污染后续历史；后带内容不得写入 Session。酒馆预设翻译器必须先判断一段内容属于哪种生命周期，再决定其具体位置。

## 当前人物卡映射

现阶段游玩请求按以下方式投影人物卡内容：

- **稳定前缀**：角色名称、场景、文风示例、常驻世界书。
- **每轮注入**：角色描述、性格、系统提示、历史后指令、动态世界书、姿势和 Guide。
- **后带内容**：暂时为空，后续用于请求级输出协议等不应进入 Session 的内容。

候选项由独立的后台生成流程处理，继续读取完整人物卡约束，不跟随正文投影拆分。人物卡稳定快照使用 v3；旧会话在下一次使用时自动重建，防止已迁移字段继续残留在稳定前缀。

## 两种预设

**酒馆预设**属于 SillyTavern 生态，建立在每轮动态拼接完整上下文的运行方式之上。

**DSH 预设**属于 dsh-tavern，建立在稳定前缀、每轮注入、后带内容与 DSH 原生历史共同组成的追加式 Agent 架构之上。它定义模型请求如何使用预设内容，但不拥有或重建历史本身。

系统首先建立和运行 DSH 预设；在此基础上，再由翻译器理解酒馆预设中条目的目的、位置和生命周期，把它们翻译为稳定前缀、每轮注入或后带内容，从而承接 SillyTavern 预设生态。

## 参考实践：Liyuan v1.5

[Liyuan](https://github.com/weidu12123/Liyuan) v1.5 对酒馆预设的处理，与本设计存在高度一致的实践方向，具有重要参考价值：

- 酒馆预设原始 JSON 不在导入时有损转换；运行时再投影为统一条目，未识别字段继续保留。
- 以 `prompt_order` 作为顺序和开关的权威来源，以 `chatHistory` marker 划分历史前与历史后。
- 按原顺序共享同一个宏变量环境完成装配，保证跨块 `setvar/getvar` 的效果。
- 历史前内容进入稳定系统提示词，历史由 Agent 原生会话持有，历史后内容按本轮输入重新求值并临时注入。
- 世界书召回独立于预设装配：预设只承接材料的位置，召回模块负责决定本轮需要什么。
- 为关闭、零字、缺失定义、marker、深度注入和不支持宏生成装配诊断，而不是静默丢失。

这项实践说明，酒馆预设不必绑定酒馆的整轮请求重建机制，也可以转换到以稳定前缀、DSH Session 历史、每轮注入和后带内容组织请求的原生架构中。dsh-tavern 将其作为预设格式层、装配中间表示和兼容诊断的参考，不直接依赖其运行时实现。

其当前边界同样需要作为反例记录：条目角色最终可能被拍平，深度注入虽被解析但未必真正进入历史，宏与采样参数只覆盖子集，全部启用块直接进入 Agent 也可能把酒馆为无状态环境模拟的流程与 DSH Kernel 重复叠加。因此，dsh-tavern 仍需建立独立的 DSH 预设语义和 Kernel 边界，而不能把结构装配等同于翻译完成。

## 待进一步思考

本设计仍有两个尚未确定的问题，暂不在本文给出方案：

1. **多 Agent 协作中的预设**：同一段故事由主 Agent、后台 Agent 或其他 Agent 共同处理时，DSH 预设应当如何作用、继承、隔离或共享。
2. **Kernel 提示词与 DSH 预设的区别**：哪些提示词属于不可缺少的运行契约，哪些属于可以选择和替换的 DSH 预设内容，两者的界线如何确定。
