# 酒馆预设与 DSH 预设

## 背景

传统酒馆在每轮生成前重新拼接系统规则、人物设定、对话历史和末尾指令。DSH 的 Agent 架构则保留稳定前缀，并在持续会话中追加新的对话内容。两者的差异不只在预设格式，更在上下文如何随时间形成。

DSH 预设的目标不是复刻酒馆预设的完整拼接行为，而是用适合 DSH 追加式 Agent 架构的方式组织提示词。

## DSH 预设的三段式上下文

DSH 预设将一次模型请求理解为三个连续部分：

1. **前缀**：系统规则、人物设定、叙事原则等稳定内容。它在会话创建时确定，此后保持不变。
2. **历史**：用户与模型真实发生的对话。它由 DSH 原生会话持有，只向后追加，不由预设反复重建。
3. **后缀**：当前状态、动态变量、世界书结果和收尾指令等本轮内容。它在请求时临时投影，不写入真实历史。

其基本形式是：

```text
稳定前缀 + 追加式历史 + 动态后缀
```

稳定前缀和不断增长的历史共同形成可复用的公共前缀；动态变化被限制在请求末尾，从而兼顾提示词能力、Agent 连续性与缓存效率。

## 两种预设

**酒馆预设**属于 SillyTavern 生态，建立在每轮动态拼接完整上下文的运行方式之上。

**DSH 预设**属于 dsh-tavern，建立在稳定前缀、原生历史和动态后缀组成的追加式 Agent 架构之上。它定义历史前后的行为，但不拥有或重建历史本身。

系统首先建立和运行 DSH 预设；在此基础上，再由翻译器理解酒馆预设中条目的目的和位置，把它们翻译到 DSH 预设的前、中、后三段，从而承接 SillyTavern 预设生态。

## 参考实践：Liyuan v1.5

[Liyuan](https://github.com/weidu12123/Liyuan) v1.5 对酒馆预设的处理，与本设计存在高度一致的实践方向，具有重要参考价值：

- 酒馆预设原始 JSON 不在导入时有损转换；运行时再投影为统一条目，未识别字段继续保留。
- 以 `prompt_order` 作为顺序和开关的权威来源，以 `chatHistory` marker 划分历史前与历史后。
- 按原顺序共享同一个宏变量环境完成装配，保证跨块 `setvar/getvar` 的效果。
- 历史前内容进入稳定系统提示词，历史由 Agent 原生会话持有，历史后内容按本轮输入重新求值并临时注入。
- 世界书召回独立于预设装配：预设只承接材料的位置，召回模块负责决定本轮需要什么。
- 为关闭、零字、缺失定义、marker、深度注入和不支持宏生成装配诊断，而不是静默丢失。

这项实践说明，酒馆预设不必绑定酒馆的整轮请求重建机制，也可以被转换到“稳定前缀 + Agent 历史 + 动态后缀”的原生架构中。dsh-tavern 将其作为预设格式层、装配中间表示和兼容诊断的参考，不直接依赖其运行时实现。

其当前边界同样需要作为反例记录：条目角色最终可能被拍平，深度注入虽被解析但未必真正进入历史，宏与采样参数只覆盖子集，全部启用块直接进入 Agent 也可能把酒馆为无状态环境模拟的流程与 DSH Kernel 重复叠加。因此，dsh-tavern 仍需建立独立的 DSH 预设语义和 Kernel 边界，而不能把结构装配等同于翻译完成。

## 待进一步思考

本设计仍有两个尚未确定的问题，暂不在本文给出方案：

1. **多 Agent 协作中的预设**：同一段故事由主 Agent、后台 Agent 或其他 Agent 共同处理时，DSH 预设应当如何作用、继承、隔离或共享。
2. **Kernel 提示词与 DSH 预设的区别**：哪些提示词属于不可缺少的运行契约，哪些属于可以选择和替换的 DSH 预设内容，两者的界线如何确定。
