# 后台结算提交协议：公开 demo / Flash 对照

日期：2026-09-12。结论：在本次 8 次正式实验中，一次提交协议将每项结算从两次请求减少到一次；没有复现诊断包中的长推理，不能据此声称已解决所有长输出。

## 固定条件

- 自创 CC0 MVU demo：`examples/manual-demo/resources.mjs` 的「灯塔小镇 · 雨夜来信」。保留全部 5 个字符串字段初值和原有更新规则。没有读取玩家存档或使用诊断包的私人正文。
- 官方 `deepseek-v4-flash`，thinking enabled，reasoning_effort high，temperature 0.1，max_tokens 20000；所有正式响应均以 tool_calls 正常结束，无截断。
- 明确场景：当晚八点、雨停、到旧花店、地址簿交林澄保管。跨日场景：数日走访后回到邮局，傍晚小雨，物品仍在；不指定具体日期。
- 每场景每协议两次，共 8 次。第一次顺序为旧→新，第二次新→旧。每次使用独立消息数组、相同初值，不沿用上一样本结果。
- 唯一提示差异：旧协议“调用 mvu_submit_update 前必须调用 posture_submit”；新协议使用当前正式代码的“在同一次回复中同时调用……两者互不依赖”。不强行限制旧协议每次只能调一个工具。其他提示、工具 schema、停止条件均相同。

## 结果

输入包含缓存 token；输出包含推理和工具参数。时间为模型 HTTP 请求耗时之和，不是产品 UI 耗时。

| 场景 / 重复 | 旧协议请求数 | 新协议请求数 | 旧输入 | 新输入 | 旧输出 | 新输出 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| 明确 / 1 | 2 | 1 | 3026 | 1404 | 463 | 516 |
| 跨日 / 1 | 2 | 1 | 3146 | 1422 | 380 | 315 |
| 明确 / 2 | 2 | 1 | 3035 | 1404 | 470 | 344 |
| 跨日 / 2 | 2 | 1 | 3112 | 1422 | 385 | 221 |
| 总计 | 8 | 4 | 12319 | 5652 | 1698 | 1396 |

- 输入减少 54.1%，输出减少 17.8%；输出中的 reasoning tokens 为 788 → 667，减少 15.4%。明确场景第一次的新协议输出反而较多，不能保证单次输出一定下降。
- 缓存命中输入为 10112 → 4480；缓存未命中输入为 2207 → 1172。缓存状态不能完全控制，token 数不等于账单费用。
- 模型耗时合计 16.403 → 9.471 秒，减少 42.3%；小样本且存在网络/缓存影响，只作观察。
- 旧协议每次先姿势、再变量；新协议每次一个响应含两个工具。正式样本均无工具重试，8/8 保存结果通过正式结算模块的变更审计，姿势非空。明确场景更新，跨日场景保持现有快照。
- 独立读回文件检查了字段集合、字符串类型、场景地点、信件/天气和姿势中的人物。文字措辞不同，没有做逐字相等检查，也不代表所有叙事细节都精确；例如明确正文的“八点”均概括成了“夜晚”。

## 执行边界与限制

使用正式 `createMvuSettlementModule` 的提示投影、工具校验、回执审计和完成条件。真实模型通过官方 HTTP 接口调用；同一步所有工具交给正式模块执行。变量执行使用实验专用的字符串字段 adapter，写入隔离目录并读回核验；这不是浏览器官方 MVU 引擎，也不是完整 DSH Agent/provider 请求链。因此结论是工具协议的受控实验，不能代替安装版端到端验收。

诊断包使用 xiaoe/V4 Pro，本实验依用户要求使用官方 Flash；demo 只有 5 个字符串字段，规则远小于诊断包，不能外推其节省比例。它证明相同 Flash 输入下提交协议有实际收益，不证明原案例的上万 token 推理已经消失。

正式样本前有 harness 调试：修正工具 arguments 的 JSON 解码、MVU wire 路径根、非法字段的回滚反馈。在调试阶段还观察到旧协议偶尔一次提交两个工具，所以不能宣称旧协议必然两步。调试数据不纳入上表。最初错误选择 Pro，用户纠正后立即停止；所有正式样本只含 Flash。没有根据输出大小挑选正式样本，冻结 harness 后连续运行以上 8 次。
