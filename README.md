# dsh-tavern

DSH 上的文字游戏 Agent——把 SillyTavern 的思路用 Agent 工程重做一遍。

## 为什么做这个项目

SillyTavern 是提示词工程思路下的产物：通过构造复杂的提示词来玩文字游戏。提示词工程的弊端很明显——难以支撑大规模、长期的任务执行。后来演化出的 Agent 思路，把任务拆成工具调用、状态持久化、结算与检索，而不是把一切都塞进一段提示词。

从 Agent 工程的视角看 SillyTavern，很多设计都很简陋：

- **候选项掉格式**：候选项和正文一起生成，经常出现“正文输出了，候选项没输出”；
- **人物姿势错乱**：场景状态全靠模型在正文里自我维持，几轮之后必然漂移；
- **失忆**：靠无限滚动的上下文硬撑，没有压缩和检索。

这些问题的答案都不是“更好的提示词”，而是工程结构：

- 正文与候选项**分两次独立调用**，格式各自保证；
- 每轮正文输出后，再做一次**独立结算**，把人物姿势总结成一句话，注入下一轮；
- 失忆问题通过**压缩、检索、游标式剧本召回**解决。

Agent 工程相比提示词工程，更适合大规模、长期任务。所以要做的是一个文字游戏版本的 Agent。


## 第一性原理：保持朴素

从第一性角度想，SillyTavern 的本质就是**注入上下文提示词，来控制游戏行为**。

所以 dsh-tavern 不做更多功能堆叠，只做最小必要的几件事：

- 简单的多轮调用：`context` 读状态 → 写正文 → `commit` 持久化；
- 独立的候选项生成：正文之外单独生成下一步行动/场景候选，不与正文抢同一次输出；
- 独立的姿势结算：正文之外单独总结一句状态，供下一轮注入。

SillyTavern 无休无止的配置、参数调整、预设调整实在让人受够了，所以 dsh-tavern 把这些全部砍掉，尽可能开箱即用：唯一要做的是导入人物卡，然后就可以开始玩；剧本是可选绑定，除此之外没有其他配置。

其余能省则省——不建剧情节点状态机、不做语义向量预处理。不做复杂的程序逻辑控制，它仍然是提示词驱动的，只是进行了多轮调用，减轻一次输出全部内容的压力。架构刻意保持朴素。


## 为什么删掉了 SillyTavern 式预设

SillyTavern 的预设（Preset / 预设）其实混杂了两类完全不同的东西：

1. **控制流程**：候选项、姿势/状态总结、重掷、剧本召回、世界书检索、上下文策略等。这些不是提示词，而是流程。在 dsh-tavern 里，它们被拆成 Agent 的多次调用和工具：`tavern_session(context/commit)` 管理回合协议，候选项与正文分开生成，结算独立运行，剧本按游标召回。模型不再需要背着一大段流程指令，也自然不会出现“正文输出了，候选项没输出”这类格式问题。

2. **内容偏好**：语言风格、故事风格、人称、字数等“这张卡怎么写”的偏好，本来就应该跟着人物卡走，而不是跟着全局预设走。dsh-tavern 把它们保留在人物卡字段里：`description`、`personality`、`system_prompt`、`post_history_instructions`、`mes_example`、`first_mes` 等。换一张卡，内容偏好自然切换；不用再维护一堆预设和参数。

因此 dsh-tavern 不再提供“预设选择/预设编辑”。要调整内容偏好，去卡片模式里和设定对话 Agent 聊，改的是当前人物卡；要调整流程，改的是 Agent 工具和召回策略。两者各归其位，预设没有存在的必要了。


## 卡片模式

除了游玩模式，dsh-tavern 还有一个完整的卡片工作台，所有与人物卡有关的事情都在这里完成：

- **编辑人物卡**：进入设定对话，用聊天的方式修改人物卡；右侧还有字段编辑器，可以手动保存；
- **素材抽取成卡**：导入独立 txt/md 素材，确认谁是玩家（`{{user}}`）后，AI 通读素材并与你讨论，逐步提炼成一张新人物卡；
- **剧本绑定管理**：为人物卡绑定 / 替换 / 解绑独立剧本；绑定剧本的卡在游玩模式自动按剧本推进；
- **世界书编辑**：条目化编辑，不再是一整块 JSON；
- **历史管理**：设定对话与抽取会话统一归档在“卡片历史”里，可重命名、删除。

### 卡片设定 Agent

在卡片模式中，点开任意人物卡进入“设定对话”。这是一个专职的人物卡编辑助手，不进行角色扮演，不续写剧情，只和你讨论这张卡应该怎么改。

你可以直接用聊天的方式定制人物卡：

- **内容偏好**：语言风格（古白话、现代、细腻、克制、香艳露骨……）、人称与视角（`{{char}}` / `{{user}}` 模板，明确谁是角色、谁是玩家，角色用第三人称）、故事风格与字数、叙事节奏、心理描写与对白比例、场景切换偏好；
- **人物核心设定**：`name`、`description`、`personality`、`scenario`、`first_mes`、`mes_example`；
- **隐藏规则**：`system_prompt`、`post_history_instructions`、`creator_notes`；
- **标签与备选开场白**：`tags`、`alternate_greetings`；
- **世界书**：条目化编辑，每条只显示名称（触发词）与内容，其余字段保存时原样保留。

对话时 Agent 会分析、追问、给方案；只有你明确确认修改时，它才提交最小字段 patch。右侧字段编辑器也能直接手动保存，两者写回同一张卡。剧本绑定/替换/解绑也在这个模式里完成。

个性化定制因此从“选预设、调参数”变成了“和编辑 Agent 聊几句，改到这张卡上”。


## 核心设计（Agent 视角）

- **每轮协议**：模型先调 `tavern_session(context)` 读取人物卡与当前状态，输出正文后再调 `tavern_session(commit)` 持久化；
- **正文**：长度由剧情自然决定，独立生成，不与其他任务混在一次输出里；两阶段生成——初稿负责内容保真（剧本模式尽量贴合剧本，允许粗糙、重复、顺序不顺），再通过 `tavern_session(action=polish)` 整理成形（删重复、调顺序、补过渡、润色遣词造句；输入初稿 + 上一段正文结尾 + 当前人物姿势 + 本轮对应查看到的剧本块，模仿剧本的遣词造句与语言风格）；
- **候选项**：回复下方手动点“生成候选项”后独立生成；自由故事为 5 个候选（4 个人物行为 + 1 个场景变化），剧本会话为 1 个推荐候选；
- **Guide**：每个游玩会话可增删多条额外指导，直接注入正文与候选项生成上下文；
- **姿态结算**：正文 commit 后异步结算，只输出 `{"posture": "一句话"}`，下一轮注入；
- **世界书检索**：非恒定条目每轮用最近正文匹配一遍，由 LLM 挑出最多 3 条相关条目注入本轮（条目少时直接全部注入）；
- **剧本模式**：给人物卡绑定一份独立剧本，按游标参考剧本分块（约 500 字/块）；游标是"当前看哪里"的标记，由候选项模块生成候选时自由调整（向前/向后/不变），正文 context 按游标注入参考块，并可用 peek 前后扩大范围；剧本会话每轮只生成 1 个"剧本推荐"候选（玩家行动/角色行动/结束场景/新场景开始）；
- **两种 UI 模式**：
  - 游玩模式：自由故事 + 剧本（绑定剧本的人物卡必须走剧本）；
  - 卡片模式：设定对话编辑 + 素材抽取成卡（开始抽取时先确认谁是玩家）+ 剧本绑定。

## 为什么要剧本模式

- AI 在遣词造句上不输人类，但在剧情架构上仍然很弱；长线剧情需要外部剧本作为骨架支撑。
- AI 输出的文字往往有“AI 味”；让它阅读并参考真实剧本后，文字风格会自然向剧本对齐，从而消解 AI 味。
- 控制文风不需要复杂的预设：人类文风千姿百态，最好的办法是给案例让模型学习，而不是用提示词诱导。

## 经验记录

- LLM 在**细节想象上超越人类**，往往比原文作者更会补足场景、动作、情绪与留白。
- 但 LLM 的**剧情架构能力仍然薄弱**：缺乏长线推进，容易死抠细节。
- 剧本模式应该：**剧情走向以剧本为骨架，遣词造句和细节铺陈让 LLM 自由发挥**；照抄原文反而固定、失去灵气。
- 实践结果：参考剧本但允许自由发挥后，输出常常比原文更好。
- 正文生成也区分两件事：**内容（写什么）** 与 **形式（如何表达）**；先写初稿保证剧情素材（剧本模式尽量贴合剧本），再单独润色整理成形（去重、调顺序、补过渡、优化遣词造句）。分离是为了减轻 LLM 单次生成的压力。

## 快速开始

```bash
dsh --profile tavern
# 打开 http://127.0.0.1:3081
```

日常管理使用：

```bash
dsh-tavern status
dsh-tavern restart
dsh-tavern stop
dsh-tavern start
```

`dsh-tavern restart` 会安全确认 3081 端口上的进程确实是 Tavern profile，
再依次停止和启动服务。修改客户端代码后，重启完成仍需在浏览器按
`Cmd + Shift + R` 强制刷新，避免旧标签页继续运行内存中的旧版前端。
启动日志位于 `~/.dsh/logs/tavern.log`。

## 文档与数据

- `交接文档.md`：架构、数据流、关键路径、验证清单；
- `剧本模式.md`：剧本分块与召回的完整协议；
- `data/cards/`：人物卡；`data/chats/`：会话与状态；`data/scripts/`：独立剧本；`data/sources/`：抽取素材。
