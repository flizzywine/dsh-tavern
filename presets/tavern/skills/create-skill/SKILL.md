# 编写 Tavern Skill

成品用 `tavern_save_skill` 保存到用户 Skill 库。用户要用教学素材做场景写作 Skill 时改用 `create-writing-skill`。

## 写什么

读 Skill 的是另一个模型，它已经会写作、会用工具。只写会改变它做法的内容：

- **目标和完成标准**：交付什么，什么结果能证明做完了（例如「工具返回 valid 且回读内容与改动一致」）。不写「记得检查」「仔细思考」这类空话。
- **非显而易见的约束**：领域规则、工具的坑、容易误判的地方。每条写成「在什么情况下，做什么/不做什么，因为什么」，放在相关的步骤旁边。
- **判断依据而不是固定流程**：只有顺序本身影响正确性或安全时才规定步骤。
- **具体的反例**：要避免某种写法或做法时，点名具体模式，不写「避免 AI 味」这类笼统要求。
- **授权边界**：用户对任务的要求就是授权，Skill 里不要加「拿不准就问」这种笼统的确认。确实需要停下来的地方（例如会覆盖用户数据、超出任务范围）写成具体动作和理由。

不要写：通用常识、重复的说明、要求模型输出推理过程、对单次失败的全局禁令。一次失败只在确实会复发的条件下写进去，并限定在那个条件里。

## 组织

- **名称**：简短的 kebab-case。
- **简介**：做什么、在什么具体场景触发。与已有 Skill 可能抢同一类请求时，写清区分条件；不要用「任何任务」「务必使用」之类的强调语。
- **正文**：一个方法说得完就只写正文。有几种实质不同的场景、且各自内容较长时，正文只保留共同部分和「什么情况读哪份参考」，细节拆进 `references/*.md`；运行时用 `tavern_read_skill_reference` 按需读取。不要要求一次读完所有参考。
- **自包含**：用到的方法、例子和模板都写进正文或参考文件，删掉原始素材后仍然能用。保存接口只打包正文和 Markdown 参考，不能附带脚本或其他文件；确实需要可执行工具时改走 `advanced-capabilities`。

## 从报错总结经验

用户要求记住改卡偏好用 `tavern_memory_preference`；报错、失败尝试和修复经验先 `tavern_memory_search` 查重，再 `tavern_memory_experience` 新建或更新。具体卡片默认 scope=card，未确认原因标记 unverified。只有用户明确要求提炼可复用流程时才创建 Skill。

提炼流程时，从本次对话已有的证据中提取：触发条件、现象、有效的排查方法、已验证的处理和验证结果。未确认的原因和未验证的方案分开写并标明。先看已有 Skill 能否补充，避免为同类问题反复新建。去掉 API 密钥、私人对话和无关卡片正文，只保留重现所需的最小示例。简介写明适用的资源或错误类型，不要把一张卡的问题写成所有卡的规则。总结不代替修复当前问题。

## 保存

用户要求创建或修改时直接保存；只是讨论方案时展示草稿。

- 提交 `name`、`description` 和完整 `body`（不含 frontmatter，接口会生成）。
- `purpose`：`card` 卡片制作、`writing` 前台写作、`background` 后台任务、`image` 文生图。省略 `agents` 时按用途分配。
- 修改时省略 `references` 保留旧参考；传数组会整体替换，先读出仍需要的文件；空数组清空。
- 修改同名用户 Skill 设 `overwrite: true`。内置 Skill 不能覆盖，需要改版时换新名称并说明与原 Skill 的关系。
- 默认允许模型自动发现；只有用户要求手动调用时才设 `modelInvocable: false`。能被发现不等于获得额外的写入授权。

## 验证

保存成功只说明格式合格。检查：简介能否把真实的适用请求和一个相似但不适用的请求区分开；正文里提到的工具当前 Agent 是否真的有；参考链接是否齐全。实质性改写且用户同意时，在隔离的对话里用真实请求试一次。报告名称、用途、是否覆盖、实际做过的验证，没试运行的如实说明。
